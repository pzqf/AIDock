## 一、总原则

1. **骨架先行**：先把「项目空间 + 技能管理」跑通，其余能力都是往这个骨架上挂。
2. **安全与骨架同步建**，不做"先跑通再补安全"——安全门 / 进程隔离 / 凭据注入是不可替换的不变量（设计 §8.1），后补等于返工。设计 §14 已明确：安全**不是**独立阶段，而是第一阶段的底座。
3. **每阶段都要产出可独立使用的成果**，不允许出现"做很久还用不上"的阶段。
4. **CLI 是契约，界面是外壳**（设计 §10.0）：每个能力**先有 CLI，再有控制台入口**，且界面入口与 CLI 等价（同一条命令、不另起逻辑）。
5. **范围克制**：自研记忆引擎、远程访问模式、多记忆 MCP 的融合、团队功能等已明确列为**可选或不做**（设计 §13.2 / §9.4 / §7.5），**不在本计划内**。

## 二、阶段总览

| 阶段 | 名称 | 一句话目标 | 完成后你能做什么 |
| --- | --- | --- | --- |
| **0** | 工程脚手架 | 可编译、可测试、可运行的 CLI 空壳 | `aidock --help` 能用，CI 能跑测试 |
| **1** | 项目空间 + 自定义技能管理（**含安全底座**） | 先管理完整技能包，再安全应用和发布 | 创建/纳管项目技能，管理全局继承，应用到两工具，五副本同步且可恢复 |
| **2** | 记忆能力集成 | 接上现成的记忆 MCP | 在项目里检索 / 写入记忆 |
| **3** | 插件市场 + 技能分发 | 增加远程来源 | 搜索/安装市场插件和技能，审核固定版本更新 |
| **4** | 同步迁移 + MCP 网关 | 跨机、对外 | 换电脑一条命令恢复；AI 客户端可调 AIDock |
| **5** | 自动沉淀 + 多 AI 并行 | 收尾 | 会话自动摄取，多工具同时同步 |

> 阶段 **1–5 与设计 §14 的五个阶段一一对应**，新增的只有 **阶段 0**（设计文档里没有工程脚手架这一环）。

## 三、阶段 0：工程脚手架

**目标**：把工程地基铺好，后续每个阶段都能"写—测—发"。

**范围**
- Go module 初始化；仓库目录结构（`cmd/` `internal/` `web/` 等）。
- CLI 框架选型与骨架：`aidock --help`、子命令注册机制、退出码约定。
- **CLI 结果/退出码约定落地**（设计 §19.12）：普通命令支持人类可读 + `--json`；stdio 协议命令不混入普通结果/进度。
- 数据根解析：`--home` / `AIDOCK_HOME` / 用户配置 / 默认路径的优先级链（设计 §7.8）。
- 测试骨架：单元测试 + golden 文件比对的基础设施（设计 §20.4 的快照测试要用）。
- CI：编译 + 测试 + lint。

**交付物**：一个**什么都没做但结构完整**的 `aidock` 二进制。

**验收标准**
- [ ] **S0-01** `aidock --help` 的命令名称/参数与设计 §7.7 一致，按阶段标出已实现/预留；预留命令返回 `FEATURE_NOT_IMPLEMENTED`、退出码 4，零业务写入，不假装执行成功。
- [x] **S0-02** `aidock version --json` 输出合法 JSON。
- [ ] **S0-03** 数据根优先级链有单元测试覆盖。
- [ ] **S0-04** YAML 规范源及 SKILL 包清单的机器 Schema / golden 示例与 §19 一致：Profile v2、skills.yaml v1 和其它 v1 类型独立校验，拒绝重复键、未知自有字段、非法标签和不兼容版本。Profile v1 只供兼容读取/迁移预览，歧义不自动选边。
- [ ] **S0-05** CI 在干净环境能编译并跑通测试。

**前置依赖**：无。

**主要风险**：文档命令面不等于功能全部落地；维护“命令→阶段→实现状态→验收证据”清单，功能开放时移除预留状态。后续新增命令需回填设计 §7.7。

## 四、阶段 1：项目空间 + 技能管理（含安全底座）

**目标**：整个产品的地基。项目空间立住，个人沉淀才有地方放、多 AI 输出才有源头。

**范围**（设计 §7.1 / §7.3 / §7.4 / §10.8 / §9.1 / §9.2 / §9.6 / §19.2 / §19.3 / §19.5 / §19.6）
- `.aidock/` 项目目录结构与规范配置格式（`project.yaml` / `profile.yaml`）。
- Profile 与 **`全局默认 → extends 链 → 项目共享覆盖 → 副本本机覆盖 → 临时会话`** 的合并算法（§19.6）——**必须确定性**，同输入必同输出。
- 全局/项目资产与继承关系的本地管理；稳定技能 id、固定 revision、完整包索引与引用，不以同名推断覆盖。
- 项目自定义技能只读盘点、模板创建、本地目录/归档导入、原源登记/授权编辑、正文/附件/脚本编辑、覆盖/分叉、改名/删除、依赖/兼容检查、批量启停与已取得版本采纳。远程下载/市场搜索在阶段 3。
- `skill plan` / `skill apply --plan` 的源事务：写前快照、摘要过期检测、引用协调、失败/中断恢复、tombstone 和草稿保护。源保存、原生 apply、跨副本发布分别预览，不把“保存”当成已生效。
- 适配器机制：把配置**编译**成 Claude Code + Codex CLI 原生格式；其它工具/App 独立进入后续适配。
- 编译报告 + 漂移检测（§7.2 / §8.3）。
- **安全底座（与上面同步建，不是后补）**：安全门（§9.1，含 L1–L4 信任等级）、进程隔离（§9.2）、凭据库与注入（§9.6）、审计日志（§9.5，追加写 + 哈希链）。
- MCP 会话启动器 `aidock mcp exec --project <stable-id> --copy <id> --plugin <id>`，安装锁验证、能力探测、授权中继、与子进程同寿命的出口 broker；管理网关属于阶段 4，二者不是同一组件。
- 原生 JSON/TOML 字段所有权、Markdown 托管区块、实际目标锁、plan 摘要绑定和多目标事务恢复（§8.3 / §20.1 / §20.3）。
- **首期回退能力**：第一次写入前就有自动快照、失败自动恢复、`replay` 项目回退及撤销回退；阶段 4 扩充历史时间线与迁移，不能将基本修复能力推迟。
- **同项目多副本**（§7.12 / §19.11）：逻辑项目、copy、作用域身份；任意源手动发布、逐目标三方比较/冲突决策、完整技能包/开关同步、本机覆盖排除、逐目标重新生成与批次恢复。先接入一个已授权的外部生成器；不支持暂存生成/恢复清单时只诊断。
- **配置合理性与分层生效检查**（§20.8）：默认静态检查；显式探测依次验证工具发现、新会话加载与无业务写入探针，输出 UNKNOWN/SKIP/STALE 的具体原因。

**交付物**：可用的 CLI + **最小控制台**（项目导航 + 项目详情页的「技能」「规则」「AI 工具」三个 tab）。

多副本首期交付另含「同步与迁移 → 跨副本」及诊断矩阵，均调用同一 CLI 契约；云端 Git 同步仍在阶段 4。

**阶段内顺序与开放门槛**

1A–1E 是阶段 1 的递进交付，不增加产品大阶段。每步 CLI 到位即提供等价的最小控制台入口，1E 再完成联合流程与体验；预留 UI 只展示实现状态。

| 子阶段 | 可独立使用的结果 | 完成门槛与下一步写入边界 |
| --- | --- | --- |
| **1A：只读盘点与能力原型** | 登记场景的只读来源/技能清单、重复名称/覆盖/依赖报告；测试夹具上的适配/隔离报告 | 区分原源、镜像、插件包与未知来源；验证两个工具精确版本/发现入口，在独立临时目录做适配和 Windows 隔离负向原型。真实五工作区此步只读；失败能力保持不开放 |
| **1B：技能源与版本管理** | 项目/全局技能创建、本地导入、完整包编辑、固定继承/覆盖/分叉、改名/删除、源回退 | 机器 Schema 与 Profile v1→v2 映射测试通过；第一笔源写入前锁/持久事务/完整包快照/恢复具备。动态依赖未知、镜像接管、重名碰撞、外部编辑和删除引用有负向证据；先在专用测试项目验收 |
| **1C：两个工具应用与恢复** | 单 copy 的确定性合并、原生预览/应用、回退/撤销、分层 doctor、受管 MCP 启动 | 两个工具的版本/字段所有权/包结构通过；幂等、保留手写项、预览过期、第二目标失败和进程中断恢复通过。插件执行须具备对应 OS 能力/授权，技能 external 执行独立标注 |
| **1D：五副本桥接与发布** | 三作用域外部源桥接、三方比较、任意源手动发布、批次恢复、逐目标重新生成 | 一个外部生成器先完成暂存/恢复清单适配；按无冲突小集合→冲突/故障夹具→五副本受控样例推进。缺共同基线/branch 不兼容/local 遮盖/删除均可解释；未经通过的生成器仅诊断，不开放真实批量写入 |
| **1E：联合验收与首期收口** | 最小控制台贯通技能、规则、工具、同步/诊断与时间线；完整交接 | 从自定义技能创建/纳管到附件修改、单 copy 应用、五副本发布、发现/新会话证据、失败恢复/撤销形成一条可复核记录；真实浏览器、CLI/UI 等价和秘密值不落文件通过，才声明阶段 1 完成 |

1A 的工具/隔离可行性验证先行，1B 的纯源管理不依赖市场或记忆。适配器/生成器缺能力时可以交付已通过的只读/源管理子阶段，但阶段 1 的两工具、五副本和恢复总验收不能降低或标作已完成。任何真实工作区写入另按实施任务的明确范围授权，本设计任务不代替该授权。

**验收标准**
- [ ] **S1-01** 项目自定义技能无需市场即可创建/导入并完整纳管；references/scripts/assets 的字节/摘要一致，生成镜像不会作为原源重复入库，导入不执行脚本/安装依赖。
- [ ] **S1-02** 固定版本继承、同 id 整包覆盖、另 id 分叉和恢复继承可核对；全局发布新候选不会自动改项目 pin/原生配置，项目开关不影响其它项目。
- [ ] **S1-03** 包路径逃逸、链接、大小写重复、损坏归档、缺附件/必需依赖、依赖环、重复 name 槽位、未知执行需求/工具能力均有明确结果；静态通过不标作执行隔离已通过。
- [ ] **S1-04** 源保存前就有恢复点；编辑期间外部改包阻断覆盖并保留草稿；导入/删除/批量编辑第二项失败或中断可恢复完整包、索引、Profile 引用与 tombstone。二进制附件不会被文本序列化破坏。
- [ ] **S1-05** 原生改名的旧托管产物只在 apply 事务中清理；引用未解除阻断删除，插件附带技能不原位修改；离线/未知引用阻止自动清理旧包。源回退后正确显示待 apply/待发布。
- [x] **S1-06** 100 个自定义技能、至少 2 个项目及多种来源的功能夹具可搜索/筛选/批量管理；同名独立资产不折叠，展示包版本、开关来源和每工具 L1–L4 状态。这是功能规模样例，不是性能承诺。v0.48 两项目各 100 owned + 10 inherited + 1 external 已验收；实际 L3/L4 保持未验证。
- [ ] **S1-07** 在一个真实项目里 `aidock apply`，能把技能编译并写入 2 个 AI 工具的原生配置；工具侧实际生效。
- [ ] **S1-08** 每个作用域只有一个规范源：AIDock 模式是 `.aidock/`，存量桥接是登记的外部源；`apply` 只重写托管部分，**托管区块外的手写内容一字不动**。
- [ ] **S1-09** 合并算法有**表驱动用例**，且断言确定性（同输入必同输出、跨机一致）。
- [ ] **S1-10** **重新 apply 是幂等的**：不改配置连跑两次，第二次 diff 为空。
- [x] **S1-11** 低于信任等级门槛 L2 的插件，安装时**必须显式放行且写审计**；放行记录可在 `aidock audit` 查到。
- [ ] **S1-12** 凭据**只落 OS 凭据库**——配置文件里 grep 不到明文。
- [ ] **S1-13** Windows 的绝对路径越界、junction/链接越界、绕过代理直连、本机服务访问、禁止 exec 的子进程均被 OS 拒绝；所需能力缺失返回 `ISOLATION_UNAVAILABLE`，非隔离选择明确显示且留审计。
- [ ] **S1-14** 安装锁固定来源/版本/产物摘要；运行不重新下载包。版本、权限或策略变化后重新授权；客户端参数不能提升 project/scope。
- [ ] **S1-15** 会话启动器在控制台/apply 退出后继续服务；客户端 EOF 后退出子进程与 broker；未授权写工具/无批准渠道返回结构化错误。
- [ ] **S1-16** 现有 JSON/TOML 的非托管字段及规则手写区保留；同名非托管项需要显式接管。共享用户文件的两个项目并发不互相覆盖。
- [ ] **S1-17** 预览后源/目标变化、第二目标失败、提交时崩溃、恢复时外部编辑均通过故障注入；未恢复事务阻断后续写入，不误报成功。
- [ ] **S1-18** 审计有分段完整性校验与可信锚点状态；区分检测能力和同用户攻击边界，不声称本地哈希链绝对不可改写。
- [ ] **S1-19** 每次写入前备份上次成功应用配置、目标原始字节及已保存草稿。应用/回退中途失败恢复全部目标，未应用草稿不丢失；程序中断后先恢复事务再允许新写入。
- [ ] **S1-20** 项目回退需预览/确认并重新验证当前权限；撤销回退能恢复原应用结果和原草稿。旧插件版本按项目锁恢复，不影响其它项目；备份/依赖缺失明确阻断。
- [ ] **S1-21** 快照不自动回退记忆正文、会话、审计、凭据或 Git 推送。未完成事务、最近成功恢复点、固定快照不可自动清理。
- [ ] **S1-22** 五副本的工作区/服务端/客户端边界独立；任意副本发起都能传播共享技能包与开关，保留本机路径/端口/环境历史/凭据/会话。两仓同名技能不会串写，目标生成物从当地有效源生成。
- [ ] **S1-23** 无共同基线、目标单边修改、双方修改、删除、权限扩大与分支不兼容均先协调；预览后改源/改目标/改策略返回 PLAN_STALE。没有按时间戳自动选边。
- [ ] **S1-24** 第二副本写入失败、进程中断和恢复时外部修改均有证据；整批恢复或明确 RECOVERY_CONFLICT，发布者改动保留。批次回退/撤销可核对源、生成物、草稿和基线，不回退会话。
- [ ] **S1-25** 默认 doctor 不启动进程/写配置；L1 一致不自动判定 L2–L4 生效。错误 cwd、local 覆盖、工具发现目录/版本、旧会话及未运行编辑器有分层结论；实际探测需授权。
- [ ] **S1-26** 同一 project id 可登记五 copy 而不覆盖绑定；本机覆盖进入有效值链，预览指出共享更新被 local 遮盖。副本移除只解除注册，保留恢复引用/删除 tombstone。
- [ ] **S1-27** Config/Local Root 解析后不重叠；Local Root 不具备所需文件系统能力时拒绝写入。事务元数据与提交标记通过断电/中断故障验证；取消写入走恢复。
- [ ] **S1-28** 外部生成器的直接 MCP 启动配置不标为已隔离/已治理；只开放通过锁定启动器的受管项，HTTP/SSE 明确不支持，非托管项不被同步接管。

**前置依赖**：阶段 0。

**主要风险**
- **合并算法涉及多个来源层与链式继承**，并包含整包覆盖、固定版本和依赖环；先定义来源链/摘要/冲突测试，再实现，不能把启停和包版本混成一个全局布尔状态。
- 自定义技能的原生 frontmatter/脚本引用并不统一；先做来源桥接和完整包保留，无法表达的能力明确阻断/提示，不以“编译成一段规则文本”替代技能语义。
- 适配器直接对接第三方工具的原生格式，**格式易变** → 适配器必须是**独立可更新单元**（§7.2），不能编译进 core。

## 五、阶段 2：记忆能力集成

**目标**：把记忆能力接上——注意 **AIDock core 不实现记忆引擎**（设计 §13.2）。

**范围**（设计 §7.5 / §9.3 / §13.2 / §19.4）
- 选定并接入**一个现成的记忆 MCP**（如 cgh），纳入 `mcp.yaml` 注册表。
- 记忆 MCP 的权限清单过安全门；写操作需授权 + 记审计。
- 按 §9.2 的模型隔离运行记忆 MCP。
- 检索作用域配置（默认本项目 + 跨项目知识 + 参考代码库，不串到别的项目）。
- 「待确认队列」：摄取内容**默认标 Internal**，可逐条调级；**Restricted 永不自动摄取**。

**交付物**：项目详情页「记忆」tab + 控制台「智库」视图。

**验收标准**
- [ ] **S2-01** 能在一个项目里通过 MCP 完成一次「存 → 检索」闭环，且**core 侧不产生任何记忆数据库文件**。
- [ ] **S2-02** **可携带性校验通过**（设计 §7.5 三条硬约束）：记忆权威内容是**纯文本且在 Config Root**；索引 / 数据库在 Local Root 且**可重建**；**无绝对路径与机器绑定信息**。
- [ ] **S2-03** **纯拷贝演练**：把 Config Root 目录直接复制到另一台机器（**不装 AIDock、不用 Git**），记忆正文**完整可读、条目数一致**。这是"沉淀能带走"的**最终判据**。
- [ ] **S2-04** **不满足契约的记忆 MCP 会被拦截**：默认拒绝接入；以「不可携带模式」启用时，界面**常驻提示"此记忆不受可携带性保护"**。
- [ ] **S2-05** `aidock doctor` 能报告 Config Root 自包含性 + 记忆正文条目数与最近更新时间。
- [ ] **S2-06** 记忆 MCP 进程按声明的隔离等级运行；越界访问（越目录 / 越网络）**被拒且有审计**。
- [ ] **S2-07** 检索作用域生效：项目 A 的会话**检不到**项目 B 的记忆。
- [ ] **S2-08** 同逻辑项目的 copy 会话只见当前 copy 及显式共享条目；缺少 origin_copy 的旧记录待绑定。加入副本组和换机导入不自动扩大可见范围。
- [ ] **S2-09** 记忆 MCP 崩溃时**返回结构化错误**，不拖垮 core。
- [ ] **S2-10** Internal 不进入远程/未知模型上下文；候选标题、引用展开、工具结果与最终请求使用同一目的地策略，切换 provider 后重新校验。未知外部客户端只默认返回 Public。
- [ ] **S2-11** Confidential 显式授权并默认脱敏；Restricted 不自动返回。个人智库管理可见不等于模型请求可引用。
- [ ] **S2-12** 知识条目保存保留用户选定等级、项目 id 与来源 MCP，默认 Internal；知识同步状态与配置待应用数量独立。

**前置依赖**：阶段 1（注册表、安全门、隔离、审计）。

**主要风险**：外部记忆 MCP 的接口/存储形态不由你控制 → **契约要稳**，别把某个 MCP 的特性写进 core。

## 六、阶段 3：插件市场 + 技能分发

**目标**：从"手工装"升级到"会装、会管"。

**范围**（设计 §10.17 / §11.1 / §11.2 / §7.2 / §19.5）
- 复用阶段 1 的全局技能库、继承、完整包/版本与源事务；新增 URL/Git 精确 commit 导入、来源搜索和固定版本更新，不再重复建设本地资产管理。
- 插件市场：聚合官方 Registry / npm / GitHub 搜索；**取数由 core 后端代理，浏览器不直连**（§10.17）。
- 缓存与离线降级：缓存于 Local Root，离线展示旧缓存并标注"可能过期"。
- 安装弹窗（§11.1）：三件事一眼读完 + 信任等级徽章 + 低于门槛的二次确认。
- 批量操作与一键更新（§11.2）：发现候选、完整包/权限 diff、显式采纳和更新角标；“全部更新”仍先预览，不改变固定版本和项目自定义分叉。
- 安装路径统一：市场 / URL / 团队索引**都走同一套安全门**。

**交付物**：控制台「插件市场」+「插件详情页」+「技能库」。

**验收标准**
- [ ] **S3-01** 从市场搜到一个插件 → 看到信任等级 → 安装 → 同步到 AI 工具，全流程走得通。
- [ ] **S3-02** 断网时市场**展示缓存并标注过期**，不报错、不清空。
- [ ] **S3-03** 安装**事务化**：中途失败整体回滚，不留半成品（§20.1）。
- [ ] **S3-04** 一处安装入口被绕过安全门 → **视为缺陷**（不允许存在"快捷安装"）。

**前置依赖**：阶段 1 的资产/安全门/适配器；普通插件与技能市场不依赖阶段 2。记忆类插件另需阶段 2 的记忆契约才能开放相应能力。

**主要风险**
- **取数协议与"评分"字段尚无定论**（§10.17 已标注属后续选型）：某些来源没有评分字段 → **取不到就隐藏该列，绝不用本地数据补造**。
- 市场的三方 API 会变 → 缓存与降级策略要早做。

## 七、阶段 4：同步迁移 + MCP 网关

**目标**：跨机器、对外暴露。

**范围**（设计 §7.6 / §7.7 / §7.9 / §19.10 / §20.2）
- Git 后端同步 **Knowledge 权威正文 + Capability 配置**（密钥、会话、缓存、日志一律不随行）。
- `push` / `pull` / `bootstrap` / `export` 与跨机 diff；阶段 1 的 replay/快照扩展为跨机依赖恢复，不重复实现。
- **快照与回滚**：每次 `apply` 前自动快照；快照仓库由 core 在 Local Root **本地自建**——**因此即使同步档位选②（云盘目录、无 Git 远端），时间线与回滚依然可用**（§10.15）。
- 冲突处理：以 Git 冲突为准、**不自动合并**；有可视化则并排选边，**无则明确提示手工解决并阻塞自动应用**（§20.1）——绝不允许默默选一边。
- MCP 网关：**v1 只做 `stdio`**，把 `aidock` 注册为 MCP 服务器，**由 AI 客户端按需拉起**，core 不需要常驻。

**交付物**：CLI 同步命令 + 控制台「同步与迁移」+「时间线」。

**验收标准**
- [ ] **S4-01** 换机演练：新机 `bootstrap` 后环境恢复，且**密钥不随行**（需重新授权）。
- [ ] **S4-02** 完整且依赖可用的历史快照可回放；回放需预览确认、走当前策略校验和多目标事务、写审计。元数据缺正文或依赖不可恢复时阻断，不报成功。
- [ ] **S4-03** 本体降级使用验签通过的旧程序与匹配 schema 备份；无法兼容的新数据保留副本并阻断，不能就地启动旧程序或默默丢数据。
- [ ] **S4-04** 同步冲突时**不会静默丢改动**。
- [ ] **S4-05** MCP 网关以 stdio 形态被 AI 客户端拉起后，能列出插件 / 应用 Profile；**core 无任何常驻监听端口**。
- [ ] **S4-06** 内置/外置项目迁移包包含稳定项目 id、知识条目 id/数量/正文 SHA-256 与配置/安装锁清单；新机逐项一致，索引可重建。外置配置保持 id 并显式重绑定目录。
- [ ] **S4-07** 知识导出/导入与记忆 MCP 的写入协调，正文与配置清单来自稳定版本；云盘多文件混代/缺项/冲突副本阻断自动应用。

**前置依赖**：配置/Git 迁移和管理网关依赖阶段 1，可在其完成后独立于市场/记忆推进；包含 Knowledge 的完整迁移另依赖阶段 2 的稳定正文导出/导入契约。未接入记忆时只声明 Capability 迁移，不声称知识已恢复。

**主要风险**：`bootstrap` 是**用户最容易失去信任**的一步（换机、数据迁移）→ 必须可 dry-run、可回滚。

## 八、阶段 5：自动沉淀 + 多 AI 并行

**目标**：从"手动用"到"自动积累"。

**范围**（设计 §7.1 / §7.2 / §7.5）
- 会话自动摄取：**主动上报优先，被动扫描为辅且默认关**（§7.5）；产出**必须经"待确认"队列**。
- 在阶段 1 的两个工具并行目标事务之上扩充更多工具/会话源适配器，能力矩阵标注 `native` / `degraded` / `unsupported`；首期多目标应用不等待本阶段。
- 项目类型自动识别 + **Profile 智能感知**（§7.1）：仅在明确不匹配时给**可忽略**的建议 chip。

**交付物**：自动摄取管线 + 多工具并行同步 + 智能 Profile 建议。

**验收标准**
- [ ] **S5-01** **不做"无授权自动读取全部对话"**：被动扫描默认关，开启后产出仍须人工确认。
- [ ] **S5-02** 一个工具不支持某能力时，**编译报告明确标注 `unsupported`**，不静默失败。
- [ ] **S5-03** Profile 建议**可忽略、可关闭**，忽略后不再重复打扰。

**前置依赖**：自动摄取需阶段 1 的 copy/会话边界 + 阶段 2 的队列/记忆契约；额外工具适配与 Profile 检测只依赖阶段 1。不强制等待市场/跨机迁移，涉及远程来源或 Knowledge 导出时再挂相应阶段门槛。

**主要风险**：被动扫描依赖各工具的**私有存储格式**（易碎）→ 会话源适配器同样要是**独立可更新单元**。

## 十一、本计划明确不做的事（v1 边界）

以下**不是遗漏，是决定**：

- ❌ **自研记忆引擎**（CogniBox）——列为可选项，v1 复用现成记忆 MCP（§13.2）。
- ❌ **远程访问控制台**（`--remote` / 绑 0.0.0.0）——明确不做，需要跨机请走 SSH 隧道（§9.4）。
- ❌ **core 常驻服务**——控制台用完即退，MCP 网关走 stdio 由客户端拉起（§10.0 / §7.6）。
- ❌ **多记忆 MCP 的结果融合（RRF）**——若有需要，交给独立的聚合 MCP，core 只做注册与编排（§7.5）。
- ❌ **`curl | bash` 安装方式**——一律走带签名校验的 `aidock bootstrap`（§10.6）。
- ❌ **自动合并同步冲突**——以 Git 为准，交用户决定（§20.1）。
- ❌ **自动覆盖其它副本**——首期变更发现仅提示；多副本共同基线与 Git 远端同步独立，冲突不按时间选边（§7.12）。
