# 正式同步恢复条件检查与任意副本发起验收 · v0.62.0-dev

正式同步中断后，CLI 和管理界面可以先检查恢复条件，逐目录查看被人工修改的路径、事务前后及当前的 SHA-256、大小和权限。检查保留文件正文、临时文件、恢复标记和事务记录；当前正文不会因检查而复制到 Local。

这是阶段 1D 的恢复可用性与联合验收增量。完整 Profile、外部生成器正式发布、技能 L3/L4、阶段 1E 总验收和后续阶段仍在继续，Goal 保持 active。

## 使用流程

从“跨副本 → 正式同步记录”打开待恢复事务，点击“检查恢复条件”：

- **恢复条件通过**：当前已观察路径符合事务前或事务后的已知字节；实际恢复仍重新取得全部锁并检查。
- **恢复被阻断**：冲突目录默认展开，显示具体原因与摘要。先另行保存人工修改，按已知版本处理冲突路径，再重新检查。界面禁用恢复重试，检查通过后重新开放。
- **仅需清理标记**：提交或恢复记录已结束，只清理对应标记，保留提交后的人工编辑。
- **没有待恢复事务**：当前无中断恢复工作。

此入口不强制覆盖、不删除备份或标记，不把检查报告当作写入授权。目标读取失败时显示“未能读取”，与文件不存在分别呈现。切换候选、发起目录或收到迟到响应，不会恢复旧的确认。

CLI：

```powershell
aidock replica publication inspect-recovery --publication <id> <原有绑定参数>
```

认证 API：`POST /api/replica/publication/inspect-recovery`，正文为 `{"publication_id":"..."}`。须使用原发起目录与副本绑定，不允许通过请求覆盖恢复根或事务输入。

## 实现边界

`workstore.Coordinator.InspectRecovery` 使用与整批恢复相同的根锁及原生项目锁，核对事务记录、屏障、全部备份和目标。prepared 事务逐根报告条件；已经结束的事务只核对标记清理，不将后续编辑判作需要覆盖的旧状态。

`Store.Observe` / `ObserveFile` 与完整备份共用路径、链接、大小写、大小限制和字节读取逻辑，但只计算摘要，不创建正文 blob。恢复检查复用恢复树判断的观察模式：已知中断临时文件只在内存观察中排除，检查不会删除它；不匹配的临时文件仍阻断。实际恢复仍使用原有写入与持久事务流程。

报告含路径与文件元数据，不返回当前正文。报告是本次锁内观察，既不缓存通过资格，也不降低恢复动作的重新检查要求。

## 已验证的上层场景

- 两个目录同时被人工修改时，一次报告所有冲突根；检查前后项目、Local、临时文件和事务记录字节保持。
- 目录与单规则文件的已知部分临时文件保留，人工改动的临时文件被识别；缺备份保持阻断。
