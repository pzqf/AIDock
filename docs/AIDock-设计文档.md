## 1. 项目概述

AIDock 是一个面向 AI 开发者的 AI 开发环境管理与个人知识库工具，**以 CLI 为核心、以本地网页作为管理控制台**。它把散落在各个 AI 编程工具中的配置、MCP 服务器、Skills、Plugins、Hooks、CLI 工具统一管理起来，并提供类似魔兽世界插件管理器的"傻瓜式"体验：在本地网页控制台里勾选插件，启用/禁用，切换 Profile，同步配置，检索个人代码智库。

**产品内核（一句话）**：

> AIDock 是一个以"个人"为圆心、以"项目"为边界、以"AI 工具"为出口的**能力中枢**。你在这里沉淀知识和技能，按项目组装配置，向任意 AI 工具输出。

围绕这个内核，产品目标是在 AI 编程工具之上构建一个 AI 开发环境的操作系统：

- **统一管理**：Claude Code、Cursor、Codex、Windsurf、Gemini CLI 等工具的配置与扩展。
- **插件化**：MCP、Skills、Plugins、Hooks、CLI 全部作为可插拔能力。
- **场景化**：通过 Profile 为不同项目、不同角色快速切换能力组合。
- **可移植**：换电脑一条命令恢复整个 AI 开发环境。
- **个人智库**：沉淀参考过的代码、设计决策、排错经验，成为"第二大脑"（引擎由**记忆 MCP** 提供，见 [7.5](#75-记忆能力与记忆-mcp)）。
- **MCP 暴露**：core 自身能力（插件 / Profile / 技能管理）经 MCP 网关暴露；**记忆类工具由记忆 MCP 自行提供**（见 [7.6](#76-mcp-网关)）。

## 2. 背景与问题

当前 AI 辅助开发存在几个核心痛点：

### 2.1 配置碎片化

每个 AI 工具都有自己的配置文件、路径和格式。MCP、Skills、插件、规则、模型提供者分散在不同目录中，改一处要同步多处。

### 2.2 换机迁移困难

直接拷贝 `~/.claude`、`~/.cursor` 等目录不可行，因为里面混杂了会话历史、缓存、认证令牌、机器本地路径等不可移植内容。

### 2.3 新项目适配繁琐

新项目需要重新思考：该装哪些 MCP？启用哪些 Skills？用哪套规则？缺少按项目类型自动匹配的能力。更进一步，不同项目往往需要**互相隔离**的技能、MCP 与记忆，而现有工具没有"项目空间"这一层抽象。

### 2.4 AI 失忆与知识流失

参考过的代码、架构讨论、排错经验散落在对话记录里，无法沉淀为可检索、可复用的个人知识库。

### 2.5 现有工具单点突破

社区已有配置管理、记忆层、插件管理器等工具，但缺少一个把环境管理、插件化、Profile、个人智库、同步迁移整合在一起的闭环产品。

### 2.6 供应链与信任风险

AI 编码工具的插件生态已经暴露出严重的供应链风险：2025 年的 "Rules File Backdoor" 事件显示，攻击者可在 `.cursorrules` 等文件中植入隐藏指令，让 AI 静默生成带后门的代码；Open VSX 注册表允许命名空间抢注，攻击者可发布看起来合法的恶意扩展。AIDock 管理的是开发者最敏感的资产，必须把"信任"作为第一优先级设计。

## 3. 设计理念

### 3.1 产品内核：四层嵌套模型

用户真实诉求可以收敛为四条：个人可以不断沉淀、多项目个性化配置、多种 AI 可用、各项目自己的技能管理。翻译成设计语言即：

| 用户诉求 | 设计语言 | 核心机制 |
| --- | --- | --- |
| 个人可以不断沉淀 | 个人智库 | 由记忆 MCP 提供，跨项目积累（见 [7.5](#75-记忆能力与记忆-mcp)） |
| 多项目个性化配置 | 项目空间 | 每个项目独立的 Profile + 技能 + 记忆 |
| 多种 AI 可用 | 多端适配 | 适配器层，一套配置编译到所有 AI 工具 |
| 各项目自己的技能管理 | 技能作用域 | 技能可绑定到项目，也可全局共享 |

**这四层不是并列的，而是嵌套的**：个人 → 项目 → 技能 → AI 工具。

```text
┌─────────────────────────────────────────────────────────┐
│  个人层（Personal）                                       │
│  · 全局 Profile（日常开发、写作、数据分析）                 │
│  · 全局技能库（跨项目复用的能力）                           │
│  · 个人智库（所有项目的知识沉淀，可跨项目检索）              │
│                                                          │
│  ┌───────────────────────────────────────────────────┐  │
│  │  项目层（Project）                                  │  │
│  │  · 项目 Profile（这个项目需要哪些插件、规则、模型）    │  │
│  │  · 项目技能（只在这个项目生效的技能）                 │  │
│  │  · 项目记忆（这个项目的代码、决策、排错经验）          │  │
│  │  · 项目 MCP 配置（只在这个项目启用的 MCP 服务器）      │  │
│  │                                                     │  │
│  │  ┌─────────────────────────────────────────────┐  │  │
│  │  │  AI 工具层（Adapters）                       │  │  │
│  │  │  · Claude Code 适配器                        │  │  │
│  │  │  · Cursor 适配器                             │  │  │
│  │  │  · Codex 适配器                              │  │  │
│  │  │  · Windsurf / Gemini CLI / ... 适配器        │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

- **个人层**是你长期积累的资产：跨项目复用的技能、全局 Profile、个人智库。换电脑时，这一层的**能力**可完整带走——但凭据（API Token、OAuth）按安全设计不随行，需在新机重新授权（见 [7.9 迁移流程](#79-迁移流程换电脑)）。
- **项目层**是每个项目的独立空间：这个项目用哪些技能、哪些 MCP、哪些规则、积累了什么记忆。项目配置随项目仓库版本化，团队可共享。
- **AI 工具层**是输出端：同一套项目配置，编译到 Claude Code、Cursor、Codex 等不同工具的原生格式。你换 AI 工具，配置不用重写。

> 这四层关系可提炼为 AIDock 的**产品设计宪法**：项目是容器，个人是圆心，AI 工具是出口，智库是沉淀。

### 3.2 魔兽世界插件管理器体验

- **开箱即用**：打开界面，看到所有可用插件。
- **卡片展示**：每张卡片显示名称、状态、类型、来源、功能简介。
- **一键启用/禁用**：保存配置开关，经预览应用后生成工具配置；新会话加载状态单独显示，无需手动改原生文件。
- **插件详情页**：简介、主要功能、使用方法、注意事项、配置项。
- **Profile 切换**：像 WoW 的角色配置一样，为不同场景保存不同插件组合。
- **一键更新**：检查更新、批量更新、版本回滚（回滚细则见 [7.7 快照与回滚](#77-同步引擎)）。

### 3.3 傻瓜化、本地优先、插件化

- 用户不需要理解每个 AI 工具的配置格式。
- 所有能力以插件形式描述，适配器负责"编译"到各工具原生格式。
- 默认本地运行，密钥加密存储，数据可自托管。
- 配置、Profile、智库笔记均可用 Git 版本化。

### 3.4 区分"能力"与"状态"

参考 Agent Brain 模型，明确哪些内容可移植：

| 类别 | 是否可移植 | 示例 |
| --- | --- | --- |
| **Knowledge（沉淀）** | ✅ **可移植（最高优先级）** | **个人智库的 Markdown 正文、项目记忆正文、参考代码库的笔记** |
| Capability（能力） | ✅ 可移植 | Skills、Plugins、Prompts、MCP 定义、Profile |
| Auth State | ❌ 不同步 | API Tokens、OAuth 凭据 |
| Runtime State | ❌ 不同步 | 会话历史、缓存、日志 |
| Machine-local | ❌ 不同步 | 硬编码路径、本地端口 |
| Generated | ❌ 不同步 | 工具自动生成的 schema、索引 |

> **Knowledge 独立成类，理由**：它是**用户唯一无法重新获得**的资产——技能可以重装、配置可以重写、凭据可以重新授权、索引可以重建，**但"我这些年积累的代码知识、设计决策、排错经验"丢了就是丢了**。因此它的可携带性**必须由设计强制保证**，不能依赖任何外部组件的自觉。见 [7.5 记忆可携带性契约](#75-记忆能力与记忆-mcp)。

AIDock 同步 **Knowledge + Capability** 两类，确保换机迁移干净、安全、可复现。

### 3.5 个人智库作为第二大脑

> **定位**：AIDock 本身**不实现记忆引擎**。记忆能力由**独立的记忆 MCP 服务器**提供（如 cgh、Skopus 等现成实现），AIDock 负责把它接通到所有 AI 工具，并管好权限、隔离与同步（见 [7.5](#75-记忆能力与记忆-mcp)）。自研引擎列为可选后续。

- 参考过的代码、设计决策、排错经验自动或手动流入智库。
- 由记忆 MCP 负责组织（AST、知识图谱、Markdown Wiki、向量检索）。
- 通过 MCP 暴露给任何 AI 客户端，让 AI 在会话中随时调用。
- 每个知识条目可追溯来源：哪个项目、哪个文件、哪次对话。
- **跨项目积累，按项目隔离检索**（见 7.5）。

## 4. 目标用户与核心场景

### 4.1 目标用户

- 独立开发者、全栈开发者、多项目并行开发者。
- 频繁更换电脑或工作环境的开发者。
- 重度使用 Claude Code、Cursor、Codex、Windsurf、Gemini CLI 等 AI 工具的开发者。
- 希望沉淀个人代码知识库、构建"第二大脑"的开发者。

### 4.2 核心场景

**新电脑初始化**
一条命令拉取 Git 仓库中的配置、Profile、插件清单，自动恢复整个 AI 开发环境。

**新项目启动**
工具检测项目类型（`package.json`、`pyproject.toml`、`go.mod` 等），推荐并应用合适的 Profile。

**多项目并行**
每个项目拥有独立的技能、MCP、记忆与规则，互不串扰；切换项目即切换能力组合。

**日常插件管理**
在控制台中搜索、安装、启用、禁用、配置 MCP 服务器和 Skills。

**跨 AI 工具使用智库**
在 Cursor、Claude Code 等工具中通过 MCP 调用 AIDock 的记忆检索能力。

**会话记忆沉淀**
从 AI 对话中自动提取值得保存的代码片段、设计决策、排错经验，确认后写入智库。

**插件市场探索**
接入官方 MCP Registry、npm、GitHub，展示下载量、评分、来源，一键安装。

## 5. 核心功能

### 5.1 统一配置管理

- 定义"规范配置"（Canonical Config），用 TOML/YAML 描述所有 AI 工具配置。
- 为每个目标工具实现适配器，将规范配置编译成原生格式。
- 支持模型提供者、API 密钥、MCP 服务器、规则提示词、工具特定设置。
- 提供 `plan`（预览）和 `apply`（执行）命令。

### 5.2 控制台插件管理

- 主界面为插件卡片列表。
- 每张卡片展示：名称、状态指示灯、类型标签、来源、功能简介、操作按钮。
- 支持搜索、筛选（已启用/全部/已禁用）、排序。
- 插件详情页包含：简介、主要功能、使用方法、注意事项、配置项、日志。
- 支持启用、禁用、卸载、配置、检查更新。

### 5.3 Profile 与项目空间

- 定义用户级 Profile 和项目级 Profile。
- **项目空间**是一等公民：每个项目拥有独立目录 `.aidock/`，存放项目 Profile、技能、MCP 配置、规则与记忆。
- 每个 Profile 包含一组插件、配置覆盖、规则提示词。
- 支持一键应用、编辑、复制、导入/导出。
- 项目级 Profile 可根据技术栈自动推荐。
- Profile 可版本化、可分享，形成内部"Profile 市场"。
- 详见 [7.1 项目空间](#71-项目空间核心抽象)。

### 5.4 个人代码智库（由记忆 MCP 提供）

> **已定（2026-10-10）**：智库是 AIDock 面向用户的**能力**，但**引擎不归 core**——由独立的记忆 MCP 服务器承载（见 [7.5](#75-记忆能力与记忆-mcp)）。以下描述的是**能力契约**；`CogniBox` 一名保留给「可选的自研 MCP 引擎」。

**摄取**

- 从 AI 对话、本地项目、手动导入中提取代码片段、设计决策、排错经验。

**组织**

- Tree-sitter 解析代码为 AST，建立符号级知识图谱。
- LLM 将非代码知识整理为 Markdown Wiki 页面。
- 每个条目关联来源、标签、项目、时间。
- 存储分层：个人智库（全局）→ 跨项目知识 / 项目记忆 / 参考代码库。

**检索**

- BM25 全文搜索。
- 向量语义搜索（本地嵌入模型）。
- 知识图谱遍历。
- 混合排序（词法 + 向量 + rerank）。
- **按项目隔离检索**：默认只检索当前项目记忆 + 跨项目知识 + 参考代码库。

**MCP 暴露**

通过 MCP 网关向 AI 客户端提供 `memory_save`、`memory_recall`、`code_search` 等工具。

### 5.5 同步与迁移

- Git 仓库作为可移植**配置与沉淀**的后端。
- 同步 **Knowledge + Capability** 两类，不同步认证状态、运行时状态、机器本地路径；**沉淀是其中最不可再生的一类**（见 [3.4](#34-区分能力与状态) 与 [7.5 可携带性契约](#75-记忆能力与记忆-mcp)）。
- 支持 `push`、`pull`、`bootstrap` 命令。
- 密钥值存 OS 凭据库；v1 同步/导出只带引用，凭据迁移需重新授权。
- **路径变量化**：配置中以变量（如 `${HOME}/projects`）而非绝对路径记录机器本地位置，`bootstrap` 时按新机环境映射重写。
- **密钥占位符**：配置中只存引用（如 `${SECRET:openai_key}`），真实值仅存在于本机密钥库，运行时注入。
- **依赖重装**：`bootstrap` 顺带恢复插件依赖（`npx` / pip / 预编译二进制），并**经安全门校验**（见 [9.1](#91-插件安装必须先审计后运行)）。
- **存储位置可配置**：数据根可指向任意路径（不强制 C 盘用户目录），配置根与本机根可分离（见 [7.8 存储布局](#78-存储布局与可配置数据根)）。
- 新电脑一次 `bootstrap` 恢复环境，完整流程见 [7.9 迁移流程](#79-迁移流程换电脑)。

### 5.6 插件化、技能与 MCP 网关

- 统一插件注册表，每个插件描述类型、来源、版本、依赖、适配目标。
- 支持 MCP Server、Skill、Plugin、Hook、CLI 五种扩展类型（Hook / CLI 设计见 [7.11](#711-hook-与-cli-扩展)）。
- **技能区分三种作用域**：全局技能、项目技能、继承技能（见 7.3）。
- **规则/指令文件统一管理**：`CLAUDE.md`、`AGENTS.md`、`.cursor/rules` 等由规范规则编译生成，用托管区块避免覆盖手写内容（见 [7.10](#710-规则与指令文件管理agentmd-等)）。
- 适配器负责将插件安装到各 AI 工具的原生路径。
- MCP 网关把 AIDock 自身能力暴露给 AI 客户端。

### 5.7 项目环境自动适配

- 检测项目类型：Node、Python、Go、Rust、Java 等。
- 根据项目类型推荐 Profile。
- 自动启用所需 MCP、Skills、规则。
- 支持项目级 `.aidock/` 配置目录，随项目版本化。
- 检测依据与推荐规则见 [7.1](#71-项目空间核心抽象)。

## 7. 关键模块设计

### 7.1 项目空间（核心抽象）

**项目**是四层模型里最需要设计好的部分，必须做成一等公民。

> 项目支持**可折叠分组**（**仅组织视图**，不新增配置继承层级，也不改变技能作用域），详见 [10.1](#101-主导航以项目为中心)。

项目目录结构：

```text
my-project/
├── .aidock/
│   ├── project.yaml          # 项目元信息、技术栈、AI工具偏好
│   ├── profile.yaml          # 这个项目的 Profile（技能、MCP、规则）
│   ├── skills.yaml           # 技能身份、来源、版本、包清单和依赖
│   ├── skills/               # 项目专属技能
│   │   ├── api-conventions/
│   │   │   └── SKILL.md
│   │   └── db-migrations/
│   │       └── SKILL.md
│   ├── mcp.yaml              # 项目专属 MCP 配置
│   ├── rules/                # 项目规则
│   │   └── coding-standards.md
│   └── memory/               # 项目记忆（可选，也可存本地智库）
│       └── decisions.md
├── src/
└── ...
```

> `.aidock/` 仅为**默认**目录名与位置：可改名，也可外置到项目外（集中式项目库）。详见 [7.8 存储布局](#78-存储布局与可配置数据根)。

> `memory/` **默认关闭**：记忆的权威源在全局智库，项目仓库默认不存记忆正文，避免内部决策泄露到共享仓库（见 [7.5](#75-记忆能力与记忆-mcp)）。

> 各文件（`project.yaml` / `profile.yaml` / `skills.yaml` / `mcp.yaml` / `SKILL.md`）的完整字段定义见 [第 19 章](#19-规范定义schema-与契约)。

项目配置的来源，最终配置 = 全局默认 + Profile 继承链 + 项目共享覆盖 + 副本本机覆盖 + 临时会话：

| 层级 | 来源 | 示例 |
| --- | --- | --- |
| 全局默认 | 个人层 Profile | 默认启用 cgh、Skopus |
| 项目覆盖 | `.aidock/profile.yaml` | 这个项目额外启用 Figma MCP，禁用浏览器自动化 |
| 副本本机覆盖 | Local Root 的 copy 绑定；桥接模式使用当地 local 文件 | 本机路径/端口、此副本的工具开关和明确保留的共享项覆盖；不参与同步 |
| 临时会话 | 运行时开关 | 今天临时禁用某个插件 |

好处：新项目开箱即用（继承全局），特殊项目精准定制（项目覆盖），不污染其他项目。

**临时会话语义**

- 仅**运行期有效**，不写入任何配置文件；进程退出即清除。
- 不参与 Git 同步，也不影响其他项目。
- 若希望保留，需显式执行“**转为持久覆盖**”并选择项目共享层或副本本机层，预览后写入对应来源。
- 优先级最高，覆盖项目覆盖层（见 [19.6](#196-技能与配置的合并算法)）。

项目类型自动识别：打开一个新项目时，AIDock 检测项目类型并推荐 Profile。

| 检测依据 | 推荐 Profile |
| --- | --- |
| `package.json` + React/Vue | 前端 Profile |
| `pyproject.toml` + FastAPI | Python 后端 Profile |
| `go.mod` | Go 服务 Profile |
| `Cargo.toml` | Rust Profile |
| `docker-compose.yml` + 多个服务 | 全栈 Profile |
| 无识别标志 | 默认开发 Profile |

识别后弹窗确认，例如：

> 检测到这是一个 React 项目，推荐应用"前端 Profile"（包含 cgh、Skopus、Figma MCP、浏览器自动化 MCP），是否应用？

**检测规则**

- **优先级**（从高到低）：多服务编排（`docker-compose.yml`）> 语言清单文件（`go.mod` / `Cargo.toml` / `pyproject.toml` / `package.json`）> 框架特征（React / Vue / FastAPI …）。
- **多标志冲突**：命中多个且无法归一（例如同时有 `go.mod` 与 `package.json`）→ **不自动选**，列出候选交由用户选择，或落到"默认开发 Profile"。
- **持续轻量检测（不打扰）**：仅在**首次创建项目**时弹窗推荐一次；此后只有当**检测结果与当前生效 Profile 明确不匹配**时，才在控制台顶栏给出一个**可忽略的建议 chip**（如"检测到 Go 项目，是否切换到 Go 服务 Profile？"）。用户可一键应用、也可忽略，忽略后不再重复打扰；整个检测能力可在设置中关闭（见 [10.10](#1010-设置界面) 的"检测"分区）。
- **以既有配置为准**：若项目已有 `.aidock/profile.yaml`，直接采用，不再推荐。
- **结果落盘**：确认后写入 `project.yaml` 的 `stack` 与 `profile`（见 [19.2](#192-projectyaml)），下次不再询问。
- **可关闭**：检测与推荐可在设置中关闭（见 [10.10](#1010-设置界面)）。

### 7.2 插件注册表与适配器

每个插件用标准化 `plugin.yaml` 描述：

```yaml
schema_version: 1
name: cgh
type: mcp-server          # mcp-server | skill | plugin | hook | cli
version: 0.3.2
source:
  type: github            # github | npm | registry | local
  url: https://github.com/xxx/cgh
  package: cgh-mcp
  version: 0.3.2           # 示例值，不代表已验证该包可用
  install: { command: npm, args: [install, --ignore-scripts, cgh-mcp@0.3.2] } # 仅安装阶段；参数数组，不拼 shell
description: "将代码库解析为图结构，提供符号级代码记忆"
tags: [memory, code-graph, context]
compatibility: [claude-code, codex-cli, cursor, windsurf]
permissions:              # 安全门与 Tier 判定依据
  fs:
    paths: ["${HOME}/projects"]
    mode: ro              # ro | rw
  net:
    allow: []             # 域名白名单；空数组 = 无网络
    default: deny         # deny | allow
  exec: false             # 是否允许执行外部命令
config_schema:            # 配置界面自动生成
  index_dir:
    type: directory
    label: "索引目录"
    default: "${HOME}/projects"
  languages:
    type: multi-select
    options: [python, typescript, go, rust, java]
profile_exclusive: false  # 是否与同类型插件互斥
```

**权限字段定义**（`plugin.yaml` 的 `permissions`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `fs.paths` | string[] | 允许访问的目录，支持变量（`${HOME}` 等） |
| `fs.mode` | `ro` \| `rw` | 只读或读写 |
| `net.allow` | string[] | 允许的域名白名单；空数组 = 完全无网络 |
| `net.default` | `deny` \| `allow` | 默认网络策略，建议 `deny` |
| `exec` | bool | 是否允许终端执行外部命令 |

> 该字段是 [9.1](#91-插件安装必须先审计后运行) 安全门展示的"权限清单"、[9.2](#92-mcp-服务器进程隔离与凭据隔离) 的 Tier 判定、以及 [10.4](#104-插件详情页) 详情页"🔐 权限"行的**唯一数据源**，三处必须一致。

适配器层负责将统一描述编译成各 AI 工具的原生配置：

```text
AIDock 规范配置（.aidock/）
        │
        ├──→ Claude Code 适配器 → .claude.json + .claude/
        ├──→ Cursor 适配器      → .cursor/mcp.json + .cursor/rules/
        ├──→ Codex 适配器       → config.toml
        ├──→ Windsurf 适配器    → .windsurf/
        └──→ Gemini CLI 适配器  → .gemini/
```

| AI 工具 | 原生配置 |
| --- | --- |
| Claude Code | `.claude.json`、`.claude/` 目录 |
| Cursor | `.cursor/mcp.json`、`.cursor/rules/` |
| Codex | `config.toml` |
| Windsurf、Gemini CLI 等 | 各自原生格式 |

**工具能力的差异处理**：

- **能力映射**：某个工具不支持 MCP，就把 MCP 工具降级为提示词描述。
- **格式转换**：Skill 在 Claude Code 中是 `SKILL.md`，在 Cursor 中是 `.cursor/rules/`，适配器负责转换。
- **优雅降级**：如果某个工具不支持某类插件，在控制台中标记为"此工具不支持"，而不是静默失败。

**多工具并行**：可同时启用多个 AI 工具，AIDock 把同一套项目配置同步到所有工具。在项目 A 中，可以用 Claude Code 写代码、用 Cursor 做重构，两者共享同一个智库和项目技能。

**能力矩阵与保真等级（解决"编译过去会丢信息"）**

各工具能力不等价，一套配置编译过去必然有损。每个适配器必须声明它对每类能力（MCP / Skill / Rule / Hook / CLI）的支持度：

| 保真等级 | 含义 | 处理 |
| --- | --- | --- |
| `native` | 原生等价支持 | 直译到原生格式 |
| `degraded` | 近似支持 | 降级映射（如 MCP 工具降级为提示词描述），并在报告中标注 |
| `unsupported` | 不支持 | 控制台明确标注"此工具不支持"，**不静默失败** |

每次 `apply` 生成**编译报告**（变更 diff + 降级清单 + 不支持项），让用户看到"这一套配置到了该工具变成了什么"。

**适配器演进策略**

- 适配器以**独立版本单元**发布，可独立更新，不与核心版本绑定——工具格式一变，只改一个适配器。
- 首期治理适配器固定为 **Claude Code + Codex CLI**（§18.4），验证契约后再横向扩。其它工具及 Codex 桌面 App 的加载/配置优先级独立验证；同品牌 CLI 验收不能覆盖 App。
- 适配器属于 [8.2](#82-可以开放为插件的部分) 允许开放的层，可由社区贡献；但它调用的安全门、隔离、凭据注入是不可替换的不变量。

### 7.3 技能作用域与 MCP 的关系

技能既要有项目特异性，又要有跨项目复用性。全局/项目是资产归属，继承是引用关系；副本本机覆盖是有效值层，不新增一个可共享项目。目录随 §7.8 的配置位置解析，下表是默认布局：

| 作用域 | 存储位置 | 生效范围 | 示例 |
| --- | --- | --- | --- |
| 全局技能 | `<Config Root>/skills/` | 显式引用它的项目 | 代码审查、提交信息生成 |
| 项目技能 | `<project>/.aidock/skills/` | 当前项目 | API 约定、数据库迁移规范 |
| 继承技能 | 引用全局/父 Profile 的固定技能版本，可有项目整包覆盖 | 当前项目 | 通用审查技能 + 项目审查规则 |

在项目空间中可对技能执行以下操作：

- **创建与本地导入项目技能**：从模板新建，或导入已有技能目录/本地归档；无需等插件市场。导入默认禁用，预览后启用。
- **登记已有自定义技能**：沿用原技能源和生成器，以 `external-source` 桥接纳管；镜像不是另一份可编辑源。
- **从全局技能库启用**：引用明确版本，不复制成未知来源，也不让全局更新自动写入所有项目。
- **覆盖全局技能**：为同一技能身份创建项目层完整包，保留基础版本；移除覆盖可恢复继承。
- **独立分叉**：生成新技能 id，记录上游 id/版本；以后自行维护，更新不自动合并。
- **禁用全局技能**：某个全局技能在这个项目不生效（例如该项目不用 TypeScript，禁用 TS 相关技能）。
- **版本、改名、删除与恢复**：查看附件、依赖和受影响引用，再执行源级事务；每次源写入本身有备份，不等下一次 apply 才保护。

**项目自定义技能是首期资产**，与市场技能采用同一包清单和预检。最小管理单元是整个目录：`SKILL.md`、`references/`、`scripts/`、`assets/` 及显式依赖，不能只编辑/同步正文。完整契约见 §19.5，管理入口见 §10.8。

**接入与生命周期**

| 操作 | 首期行为与边界 |
| --- | --- |
| 盘点 | 只读扫描已登记的源目录，列出项目自定义/全局引用/插件附带/生成镜像/未纳管候选；显示 project/scope/copy、真实来源和生成关系。没有生成器证据时来源标 UNKNOWN，不因目录叫 `.claude/skills` 就认定镜像 |
| 创建/导入 | 创建默认模板；本地目录或归档先暂存，验证路径、包闭合、名称冲突、依赖和信任，再预览落源；不执行附带脚本、不安装依赖、不自动 apply。URL/Git 远程取包在阶段 3，固定来源和 commit/摘要 |
| 纳管原源 | `external-source` 默认只读登记。可编辑能力必须经桥接声明允许的源路径、保留原格式和恢复清单；不具备这些能力只诊断。转为 AIDock 所有权是显式迁移，停止旧生成器后才切换 |
| 编辑 | 编辑正文/附件/元数据，验证整个包和当前基础摘要；并发外部修改阻断覆盖，保留用户草稿。保存生成待应用版本，已应用状态保持可核对；源保存、原生 apply、跨副本发布是三个独立操作 |
| 继承/覆盖/分叉 | 引用固定 revision；项目覆盖保留同一 id 和 base revision，正文/附件不字段级合并；分叉另建 id 并记来源。全局新版本只产生更新提示和受影响清单，项目采纳需新 plan |
| 批量启停/更新 | 按显式条目集预检，显示依赖、目标工具、权限和副本影响；默认整批事务。缺依赖、未知身份或不兼容项使所选集合阻断，移除该项后重新预览；不以静默跳过伪装全部成功 |
| 改名/删除 | 展示名修改不改变 id；原生 name/目录改名须预览旧产物清理和冲突。删除与禁用分开：引用未解除先阻断；解除 Profile/依赖引用和删除可纳入同一事务。插件附带技能先项目禁用或独立分叉，不直接改安装包 |
| 恢复 | 源编辑、导入、删除和批量操作都进入时间线，保留完整包、引用、草稿和 tombstone；回退需要当前依赖/权限与目标摘要校验。仅回退源会显示待 apply/待发布，不自动向其它 copy 传播 |

资产记录用 `(owner project/global, scope_id, skill_id)` 定位，副本共享同一稳定 UUID；覆盖记录显式链接上层 owner/scope/id 和基础版本，只有这条关系允许不同层沿用同 id。新独立资产不得复用其它资产 id。版本、展示名、原生 name 和路径独立；不同项目/作用域的同名技能仍是不同资产。同一工具输出槽位重名必须明确选用/改名，不能按目录顺序覆盖。静态引用只能验证声明的闭合关系；脚本的动态加载/工具调用无法证明时显示 UNKNOWN，不能声称整个包已验证安全。

**技能与 MCP 的关系**：两者是不同的扩展类型，AIDock 统一管理，但在 UI 上用类型标签区分。

| 类型 | 层次 | 形态 | 回答的问题 |
| --- | --- | --- | --- |
| Skill | 指令与辅助材料 | `SKILL.md` + 引用/脚本/资产 | 告诉 AI"怎么做"；附带脚本不因启用而自动执行 |
| MCP Server | 工具层面的能力 | 提供可调用的函数 | 告诉 AI"能做什么" |

一个项目可能同时需要两者。例如"数据库迁移"这个能力可能包含：一个 Skill（描述迁移规范与命名约定）+ 一个 MCP Server（提供 `list_migrations`、`create_migration` 等工具）。

**执行保证单独说明**：技能声明的脚本/网络/写入需求用于发布预检和授权影响分析，不能使外部 AI 客户端自动拥有 AIDock 的 OS 隔离。AIDock 不提供绕过插件启动器的 `skill run`，创建/预览/导入不会执行技能代码；原生客户端自行运行的命令标为 external，其限制由客户端决定。需要受管执行的能力应绑定受管 MCP/CLI 插件，满足 §9.1/§9.2。原生工具不能表达的技能字段不得静默删除或展平，编译报告须说明 degraded/unsupported，并由用户明确选择目标。

### 7.4 Profile 引擎

Profile 用 YAML 定义：

```yaml
schema_version: 2
name: 前端项目
description: 适用于 React/Vue/Next.js 项目
plugins:
  enable: [cgh, skopus, figma-mcp, browser-automation-mcp]
  disable: []
config_overrides:
  cgh:
    languages: [typescript, javascript]
rules:
  - "优先使用函数式组件"
  - "遵循项目 ESLint 配置"
```

- 用户级 Profile：日常开发、写作、数据分析。
- 项目级 Profile：随项目存储在 `.aidock/profile.yaml`。
- 应用 Profile 时，自动启用/禁用对应插件，并同步到所有 AI 客户端。
- 最终生效配置遵循 §19.6 的共享层 → 副本本机覆盖 → 临时会话叠加规则；保存或切换 Profile 不自动重启旧会话。

### 7.5 记忆能力与记忆 MCP

> **已定（2026-10-10）：记忆能力由独立的记忆 MCP 服务器提供，不是 core 的一部分。**
>
> AIDock core 是**配置与编排**（Go、轻量文件状态、**无数据库**）；记忆的**存储与检索**由一个独立的 MCP 服务器承担（优先复用现成实现，如 cgh / Skopus）。这与 [9.2](#92-mcp-服务器进程隔离与凭据隔离) 既有的「MCP 服务器 = 独立进程」模型完全一致，无需为记忆特开进程模型。
>
> 自研引擎（`CogniBox`）列为**可选后续**；若自研，也应做成独立 MCP 而非内嵌 core（选型见 [13.2](#132-记忆能力由记忆-mcp-提供非-core-职责)）。

**职责划分**

| 层 | 负责 |
| --- | --- |
| AIDock core | 注册与配置记忆 MCP、过安全门、进程隔离、凭据注入、审计、同步其**配置**（不同步其索引 / 数据库） |
| 记忆 MCP | 摄取、存储（SQLite 等）、索引、检索，并对外暴露 `memory_*` 工具 |

**记忆可携带性契约（硬性，接入时必须校验）**

AIDock 不实现记忆引擎，但**必须保证"你的沉淀能带走"**（见 [3.4](#34-区分能力与状态)）。因此对要接入的记忆 MCP 立三条硬约束：

| # | 约束 | 为什么 |
| --- | --- | --- |
| ① | **权威内容必须是纯文本**（Markdown / JSON），存放于 **Config Root 的 `knowledge/`** | 纯文本才可 diff、可评审、可长期存活；二进制库不可评审、易腐坏、易锁死 |
| ② | **索引 / 数据库必须在 Local Root，且必须可重建** | 它们属 Generated，不随行；能重建即可恢复检索能力 |
| ③ | **不得依赖绝对路径与机器绑定信息** | 否则拷贝到新机即失效（见 [19.1](#191-跨平台路径变量)） |

**执行方式**

- **接入时校验**：注册记忆 MCP 时，AIDock **验证它是否满足上述三条**。不满足则**默认拒绝接入**；用户可在明确风险提示后以「**不可携带模式**」启用，此时界面**常驻提示"此记忆不受可携带性保护"**。
- **启动时巡检**：`aidock doctor` 检查 Config Root 是否自包含（有无绝对路径、有无指向 Local Root 的引用），并报告记忆正文的**条目数与最近更新时间**（见 [20.8](#208-自检aidock-doctor)）。
- **两条带走路径都成立**：
  - **Git**：Config Root 进 Git → `aidock push` 即带走（正文随行；索引与凭据不随行）。
  - **纯拷贝**：因为 ①③ 成立，**直接复制 Config Root 目录即可**——不需要 Git、不需要装 AIDock。

> **一句话**：**能力可以重装，凭据可以重新授权，索引可以重建，但沉淀不可再生。** 三条里 ① 是红线——**记忆的权威副本永远是可读的纯文本**；任何把权威副本锁进私有二进制格式的记忆 MCP，都不满足"可带走"。

**多记忆 MCP 并存（可选）**

core 允许同时注册多个记忆 MCP（如 cgh 找代码符号、另一类查个人笔记），并负责三件事：

- **命名空间**：注册时对工具名加来源前缀（如 `cgh.memory_recall`），避免工具名冲突。
- **来源标签**：控制台在记忆条目上标注来源 MCP，让用户知道"这条记忆来自谁"。
- **逐项启用**：在 Profile 的 MCP 配置里按项启用 / 禁用。

> **边界**：以上三项都属 core 的**注册与编排**职责。**跨 MCP 的结果融合（RRF / 重排）不在 core**——那属于检索引擎逻辑，会破坏"core 不含数据库、不长引擎逻辑"的约定（见 [13.2](#132-记忆能力由记忆-mcp-提供非-core-职责)）。若需要统一检索体验，应由一个**独立的聚合记忆 MCP** 承担，core 仍只负责注册与编排。

以下描述记忆的**能力契约**，以及 core 需要为它做的**集成职责**。

**摄取**

- 从 AI 对话中提取代码片段、设计决策、排错经验。
- 手动导入参考过的代码项目、文档、笔记。
- 监听本地项目变更，增量索引。

**摄取来源（会话从哪里来）**

两条路径，**主动上报优先，被动扫描为辅**：

| 路径 | 做法 | 说明 |
| --- | --- | --- |
| 主动上报（主） | AI 客户端在会话中通过 MCP 调用 `memory_save` 写入 | 不依赖读取工具私有存储，最稳定、最可控 |
| 被动扫描（辅，默认关） | 会话源适配器读取各工具本地会话存储 | 需用户显式开启，只读、只提取，结果入"待确认"队列 |

会话源适配器要面对各工具不同的存储形态（Claude Code 本地 `jsonl`、Codex `~/.codex/sessions/*.jsonl`、Cursor 本地 SQLite 等），统一转换为**规范事件流**。它与工具适配器一样易受格式变化影响，因此同样是**独立可更新单元**（见 [7.2](#72-插件注册表与适配器)）。

> 设计取舍：**不做"无授权自动读取全部对话"**。一是隐私，二是各工具会话存储无公开契约、易碎。被动扫描只在用户显式开启后运行，且产出必须经"待确认"入库。

**组织**

- Tree-sitter 解析代码为 AST，提取函数、类、方法、导入、调用关系。
- 存入知识图谱（**默认用 SQLite 邻接表**；仅在需要复杂图遍历时才启用 Neo4j，可选）。
- 非代码知识由 LLM 整理为 Markdown Wiki 页面。
- 每个条目关联来源、标签、项目、时间。

**存储分层**：沉淀是跨项目的，但检索是有边界的。

```text
个人智库（全局）
├── 跨项目知识
│   ├── 设计模式、架构决策、通用排错经验
│   └── 可被任何项目检索
│
├── 项目A 记忆
│   ├── 代码片段、API 约定、项目特定决策
│   └── 只在项目A上下文中检索
│
├── 项目B 记忆
│   └── ...
│
└── 参考代码库
    ├── 你参考过的开源项目代码
    ├── 技术文章摘要
    └── 可被任何项目检索，但标注来源
```

**存储归属（单一权威 + 显式发布）**

- 记忆的**权威源只有一个**：全局智库，**由记忆 MCP 持有**（Config Root 的 Markdown + 该 MCP 自己的索引），**默认不写入项目仓库**。core 只保存其**配置**，不持有其索引与数据库。
- `.aidock/memory/` 仅是可选的"项目记忆快照"，**默认关闭**；若要团队共享，走**显式发布**（脱敏 + 按 [9.3](#93-本地智库的数据分级) 分级），而不是自动提交进项目 Git——避免把内部决策泄露到共享仓库。
- 每条记忆标注 `scope: global | project:<id> | reference`，检索按 scope 过滤，从根上避免"双存储打架"。

多副本记录另有 `origin_copy` 与 `visibility: copy | project-shared`。从 copy 会话/扫描摄取的内容默认 copy 可见；标为 project-shared 或 global/reference 需独立确认共享范围与敏感度。默认项目查询为“当前 copy 内容 + 已显式共享的项目内容 + 允许的 global/reference”，相同 project id 不自动暴露其它 copy 的任务记忆。旧条目缺少 copy 归属时先列为待绑定，不自动向全部副本开放；换机导入必须显式确认旧/新 copy 的可见性映射。记忆 MCP/中继不能可靠过滤这些维度时不开放多副本治理检索。

**检索作用域控制**：在项目 A 中默认检索可见的 A 项目内容 + 允许的跨项目知识/参考资料，不检索项目 B。多副本按上述 copy 可见性进一步过滤；敏感度/目的地策略仍生效，切换 scope 或项目不能作为外发授权。

**沉淀的触发方式**：

| 触发方式 | 说明 |
| --- | --- |
| 自动摄取 | 从 AI 对话中自动提取代码片段、决策、排错经验，经确认后入库 |
| 手动保存 | 在控制台中选中一段对话或代码，点击"存入智库" |
| 项目扫描 | 定期扫描项目代码，提取架构决策、API 约定、变更历史 |
| 参考导入 | 导入参考过的 GitHub 仓库、技术文章、文档 |

关键原则是**自动摄取 + 人工确认**，而不是全自动。AI 提取的内容先进入"待确认"队列，审核后正式入库，避免噪音污染智库。

**检索**

- BM25 全文搜索（SQLite FTS5）。
- 向量语义搜索（sqlite-vec + 内置 ONNX 嵌入模型；Ollama 可选）。
- 知识图谱遍历（默认 SQLite 邻接表；Neo4j 可选）。
- 混合排序：默认 **RRF 融合**（词法 + 向量）；cross-encoder rerank 可选、默认关闭。

**MCP 工具与权限**

MCP 是外部 AI 客户端的入口，**写操作必须显式授权并记审计，只读操作默认开放**——否则任一被注入的客户端都能改环境，绕过 [8.1](#81-必须钉死的不变量不可被插件-patch-掉) 的安全门：

“默认开放”仅指已授权项目、插件与处理目的地内的只读工具；项目、敏感度与外发策略仍须检查。原生客户端配置指向 §9.2 的 `aidock mcp exec` 会话启动器，客户端经 stdio 中继访问记忆 MCP。记忆 MCP 提供检索与存储，中继执行授权和审计；不经过 §7.6 的管理网关。

| 工具 | 提供方 | 说明 | 权限 |
| --- | --- | --- | --- |
| `memory_recall` | 记忆 MCP | 检索记忆 | 只读（默认开放） |
| `code_search` | 记忆 MCP | 按符号或语义搜索代码 | 只读（默认开放） |
| `memory_save` | 记忆 MCP | 保存记忆 | 写入（需授权，入"待确认"队列） |
| `plugin_list` | core 网关 | 列出可用插件 | 只读（默认开放） |
| `profile_apply` | core 网关 | 应用 Profile / 切换插件 | 写入（**需显式授权 + 审计**，不得静默生效） |

### 7.6 MCP 网关

> 网关暴露的是 **AIDock core 自身的能力**（插件 / Profile / 技能管理）。**记忆类工具由记忆 MCP 自己提供**，不经过本网关（见 [7.5](#75-记忆能力与记忆-mcp)）。

- 将 AIDock 自身能力以 MCP 服务器形式暴露。
- 任何支持 MCP 的 AI 客户端均可调用。
- **v1 以 `stdio` 形态接入**：把 `aidock` 注册为一个 MCP 服务器，**由 AI 客户端按需拉起、随客户端退出**——与 [10.0](#100-载体本地-web-控制台) 的"不常驻"一致，**core 不需要常驻监听**。
- **SSE / Streamable HTTP 属后续可选**：只有当"多个客户端共享同一网关实例"时才需要；届时应做成**独立进程**，而不是让 core 变成长驻服务。
- 提供鉴权、速率限制、日志。
- **读写分级**：只读工具默认开放；写入工具（`memory_save`、`profile_apply`）需显式授权并记审计，且不得绕过安全门（见 [7.5](#75-记忆能力与记忆-mcp)）。

### 7.7 同步引擎

- Git 仓库作为后端。
- 同步 **Knowledge + Capability** 两类：**智库 / 项目记忆的 Markdown 正文**、插件清单、Profile、规则、配置模板。
- 不同步：认证令牌、会话历史、缓存、日志、机器本地路径、**记忆的索引与数据库**（属 Generated，可重建）。
- 凭据值仅在 OS 密钥库；普通同步/导出只保留引用，v1 不提供携带凭据值的导出。

命令：

| 类别 | 命令 | 说明 |
| --- | --- | --- |
| 配置 | `aidock plan` | 预览合并与编译结果（含合并报告 / 编译报告） |
| 配置 | `aidock apply [--plan <plan-id>] [--all]` | 应用当前绑定 project/scope/copy 的原生配置计划；`--all` 仅指该绑定所有启用的 AI 工具，不扩展到其它项目或副本 |
| 同步 | `aidock push` / `pull` | 推送 / 拉取配置 |
| 同步 | `aidock bootstrap <repo>` | 新电脑一键初始化 |
| 同步 | `aidock export` | 导出 ZIP / Git Bundle |
| 同步 | `aidock diff` | 对比差异 |
| 同步 | `aidock replay <snapshot> [--copies <copy-ids>]` | 回退项目或副本批次；省略 copies 恢复整个批次，指定则需重新预览局部回退（§10.15 / §7.12） |
| 副本 | `aidock replica list` / `add` / `rm` | 注册同一逻辑项目的工作副本；映射工作区内的配置作用域（§7.12） |
| 副本 | `aidock replica plan --scope <id> --from <copy-id> --to <copy-ids>` | 只读生成跨副本差异、冲突、排除项与生成预检；保存有摘要的计划 |
| 副本 | `aidock replica apply --plan <plan-id>` | 确认计划后同步选定真相源并在各目标生成；检查过期、备份、事务恢复 |
| 项目 | `aidock project add` / `list` / `rm` | 注册 / 列出 / 移除项目（维护项目注册表，见 [7.8](#78-存储布局与可配置数据根)） |
| 插件 | `aidock plugin install` / `enable` / `disable` / `update` | 插件生命周期 |
| 技能 | `aidock skill list` / `show <id>` / `scan` | 列表/包详情/只读盘点；包含来源、依赖、固定版本和生效层，不递归扫整个工作区 |
| 技能 | `aidock skill plan <action> ...` | action 为 create/import/adopt/edit/override/fork/rename/remove/enable/disable/update；产出锁定包、引用影响和恢复清单的源变更计划（§19.5） |
| 技能 | `aidock skill apply --plan <plan-id>` | 确认后提交技能源/引用事务，默认不写原生配置或其它副本；原生配置仍用顶层 apply，跨副本仍用 replica apply |
| 技能 | `aidock skill enable` / `disable` | 当前绑定的计划快捷入口；输出 plan，不直接跳过确认写入。全局操作必须显式 `--global`，与 project/scope/copy 互斥 |
| 记忆 | `aidock memory save` / `search` | **代理到当前绑定的记忆 MCP**——core 只转发，不存数据（见 [7.5](#75-记忆能力与记忆-mcp)） |
| 运维 | `aidock mcp start` / `stop` / `restart` / `retire` | **独立起停单个 MCP 做调试与健康检查**（不改变 AI 客户端的拉起方式）；`retire` 为安全下线（见 [9.2](#92-mcp-服务器进程隔离与凭据隔离)） |
| 运维 | `aidock mcp exec --project <id> [--copy <id>] --plugin <id>` | 客户端会话启动器/中继；协议输出为 JSON-RPC，诊断只写 stderr，区别于普通命令的 `--json` 输出 |
| 运维 | `aidock update` | 检查并升级 core 本体（见 [20.2](#202-升级与分发)） |
| 运维 | `aidock doctor [--scope <id>] [--copy <id>] [--probe]` | 默认静态诊断；显式 `--probe` 才启动受限探测，分层报告生效证据（§20.8） |
| 运维 | `aidock audit` | 查看审计日志（见 [9.5](#95-审计日志)） |
| 界面 | `aidock config`（别名 `aidock ui`） | 启动本地 Web 控制台并调起浏览器；聚焦配置 / 查看 / 审计，写操作入口与 CLI 等价（见 [10.0](#100-载体本地-web-控制台)） |

**输出约定**：所有命令默认输出**人类可读文本**；加 `--json` 输出**机器可读结构**，便于脚本集成与 AI 客户端调用（如 `aidock doctor --json`，见 [20.8](#208-自检aidock-doctor)）。

离线无网络时，可用 `export` 导出的 ZIP / Git Bundle 作为迁移载体代替远程仓库。

**同步架构选型（三档，按需选择）**

| 档位 | 载体 | 说明 |
| --- | --- | --- |
| ① Git（默认） | 私有 Git 仓库 | 版本、审计、回滚天然具备，对开发者零门槛 |
| ② 云盘目录 | Config Root 指向 Syncthing / Nextcloud / iCloud / OneDrive 等同步目录 | **无需任何服务端代码**，靠文件同步即得准实时同步 |
| ③ 远程 MCP 网关（未来可选） | 自建服务端，暴露智库检索入口 | 仅用于多机共享同一智库检索；属可选增强，非架构必需 |

**为什么不做 Chrome 式的客户端-服务器托管同步**

- 与"本地优先、隐私优先"的定位直接冲突：托管意味着代码与记忆要过第三方服务器。
- 目标用户是开发者，**Git / 云盘目录同步对他们零门槛**，托管带来的便利不足以抵消成本与信任成本。
- 自建一个同步服务（账号、存储、合规、可用性）是产品之外的一整套负担。
- 档位 ② 已用"文件同步"这一通用能力覆盖了绝大部分实时同步需求，且数据不离开用户自己的同步方案。

> 结论：**保留本地优先，不做托管式客户端/服务器；"自建云存储"通过档位 ② 天然获得，不需要新增服务端组件。**

**快照与回滚**

Local Root 的独立快照仓库保存恢复点；同步远端不是回退前提。回滚使用完整快照重新编译，跨文件事务按 §20.1 执行，不能仅靠 Git reset 恢复工具侧状态：

- 每次 `apply` 前保存上次成功配置、当前已保存草稿、锁定版本清单和目标字节备份；成功后追加已应用节点。恢复点不放进 Knowledge/Capability 同步仓库。
- 回滚粒度：

| 粒度 | 方式 |
| --- | --- |
| 插件版本 | 依据版本锁定回退到指定版本，并**重走安全门** |
| 配置 / Profile | 回到指定快照 commit，重新 `apply` 编译到各 AI 工具 |
| 整体 | 回到上一个"已知良好状态" |

- 回滚动作本身写入审计日志（见 [9.5](#95-审计日志)）；凡涉及插件版本变更的回滚，必须重新过安全门。

### 7.8 存储布局与可配置数据根

原设计里全局固定 `~/.aidock/`、项目固定 `<project>/.aidock/`，两处位置都写死了。改为**三层可配置**。

**1. 数据根（Data Root）可指定**

解析优先级：

```text
--home <path>  >  环境变量 AIDOCK_HOME  >  用户配置文件  >  默认 ~/.aidock/
```

可指向支持的磁盘/目录（D 盘、移动硬盘、加密卷），**不强制落在 C 盘用户目录**。Config Root 可置同步盘；Local Root 必须具备经验证的排他锁、原子替换、持久化与 ACL。网络盘或云同步目录不满足这些能力时，Local Root 不开放写入，报告 `STORAGE_UNSUPPORTED`。

**2. 配置根 / 本机根分离**

复用 [3.4](#34-区分能力与状态) 的划分，把"可移植"与"本机"拆成两个根，可放同一 Data Root 下的不同子目录，也可分盘；解析最终路径后不得相同、互为祖先或经链接重叠，防止恢复字节备份/本机状态被同步出去：

| 根 | 内容 | 是否进 Git | 建议位置 |
| --- | --- | --- | --- |
| Config Root（可移植） | `profiles/`、`skills/`、`rules/`、`knowledge/`（Markdown）、插件清单 | ✅ | 同步盘（Git / 网盘） |
| Local Root（本机） | `index/`、`cache/`、`logs/`、`snapshots/`、`transactions/`、注册/绑定/基线与凭据引用元数据；凭据值仍在 OS 库 | ❌ | 具备所需文件系统能力的本地盘 |

典型用法：Config Root 放同步盘实现跨机共享，Local Root 放本地盘保证索引性能。

**3. 项目目录名 / 位置可配置**

- 默认 `<project>/.aidock/`，但允许：
  - 改目录名（团队不想用 `.aidock` 时）；
  - 外置到项目外（集中式项目库，按项目 id 索引），适配"不污染仓库""不提交到项目 Git"的场景。
- 项目注册表保存逻辑项目元信息与 `(project_id, scope_id, copy_id) → 实际项目路径、配置位置` 绑定，不能用一个 project id 只对应一个根目录。单副本也有 copy id；新绑定先确认身份，禁止覆盖旧绑定。§19.11 的副本注册表引用此绑定，以注册表版本/摘要保持一致，不能各自维护互相矛盾的路径。
- 项目注册表属 **Machine-local**（含本机绝对路径），存放在 **Local Root**（如 `<Local Root>/projects.json`），**不进 Git**；迁移到新机时重建（见 [7.9](#79-迁移流程换电脑)）。

**4. 存储位置迁移**

设置中提供“迁移存储位置”：先预览目标、空间、权限与根不重叠检查，停止本次绑定的写入/受管会话，再复制并校验配置、受保护本地状态与引用。目标校验成功后原子切换注册绑定，失败保留原位置；不先删除旧数据，不把 OS 凭据值作为普通目录文件迁移。

### 7.9 迁移流程（换电脑）

迁移的本质是「**备份 Knowledge 正文 + Capability 规范源 → 到新机校验正文 + 重新编译 + 重新授权 + 重建索引**」。

三处存放，分别怎么走：

| 层 | 迁移载体 | 机制 |
| --- | --- | --- |
| 个人层 | 一个 Git 仓库（如 `ai-env.git`） | 全局 Profile、全局技能库、个人智库 Markdown 笔记、配置模板；老机 `push`，新机 `bootstrap` |
| 项目层（内置） | 项目仓库 | `.aidock/` 随项目自己的仓库提交，`git clone` 项目即一起带回 |
| 项目层（外置） | Config Root 的 `projects/<stable-id>/` 或显式导出包 | 配置与项目知识正文一起打包；本机目录映射留在 Local Root，新机确认路径重绑定，保持项目 id |
| AI 工具层 | 不带 | 新机由适配器重新编译成 `.claude.json` / `.cursor/mcp.json` / `config.toml` |

> 个人层即 [7.8](#78-存储布局与可配置数据根) 的 **Config Root**（可进 Git）；**密钥始终位于 Local Root，不进 Git、不随行**；索引与缓存随本机重建、凭据重新授权。

明确**不迁移**的四类（对应 [3.4](#34-区分能力与状态) 的能力/状态区分）：

| 类别 | 具体 | 新机处理 |
| --- | --- | --- |
| Auth State | API tokens、OAuth 凭据 | 重新授权 / 重新登录 |
| Runtime State | 会话历史、缓存、日志 | 丢弃 |
| Machine-local | 硬编码路径、本地端口 | 按路径变量映射重写 |
| Generated | SQLite 索引、向量索引 | 后台重建（见第 12 章） |

操作序列：

```bash
# 老机
aidock push                          # 推 Knowledge 正文 + Capability；密钥、会话、日志不随行

# 新机
1. 安装 AIDock
2. aidock bootstrap git@github.com:you/ai-env.git   # 拉回全局 Profile / 技能库 / 笔记
3. 交互式补齐"不可移植项"：
   - 重新登录 Claude Code / Cursor 等 AI 工具
   - 把密钥写入本机 keyring（不写入配置文件）
   - 确认路径映射（如 ~/projects 指向新机实际目录）
4. aidock apply --all                # 适配器重新编译到所有 AI 工具
5. 后台重建代码索引（增量，不阻塞）
6. aidock diff                       # 对比差异，验证一致
```

知识正文与 Capability 导出须基于同一已确认版本清单；记忆 MCP 通过只读导出/暂停写入等契约提供稳定正文，不能边摄取边读取多文件并宣称快照一致。缺少稳定导出能力时阻断“完整迁移”承诺。导入/远端 pull 不在记忆 MCP 正在写正文时强行覆盖；由其确认导入、刷新索引并校验清单，保留旧版本至验证成功。

支撑上述流程的三个机制：

| 机制 | 做法 | 解决的问题 |
| --- | --- | --- |
| 路径变量化 | 配置写 `${HOME}/projects`，不写绝对路径；`bootstrap` 时映射重写 | Machine-local 路径不可移植 |
| 密钥占位符 | 配置只存 `${SECRET:openai_key}`，真值在 keyring，运行时注入 | 配置文件可安全进 Git，凭据不随行 |
| 依赖重装 | `bootstrap` 依据 `plugin.yaml` 的 `install` 字段恢复依赖，**经安全门校验**（见 [9.1](#91-插件安装必须先审计后运行)） | 新机没有插件运行环境 |

> 注意：**"能力完整带走，凭据需重新授权"**——这既是安全设计（见 [9.2](#92-mcp-服务器进程隔离与凭据隔离)），也是用户预期的正确表述。

**迁移验收清单**：导出包带 schema 版本、项目稳定 id、知识条目 id/数量/相对路径/正文 SHA-256、配置及安装锁哈希。新机逐项比较，不只比较配置 diff；知识正文缺失或哈希不同即迁移未完成。索引可重建，授权/凭据/会话/日志不导入。外置项目必须先确认新目录绑定，再编译；同名目录不得触发重新生成项目 id。纯拷贝也必须通过正文可读性、id、数量和哈希检查。

### 7.10 规则与指令文件管理（AGENT.md 等）

AI 工具的"指令/规则文件"是一类特殊配置，AIDock 统一管理。

原生文件对照：

| 工具 | 指令/规则文件 |
| --- | --- |
| Claude Code | `CLAUDE.md` |
| Codex | `AGENTS.md` |
| Cursor | `.cursor/rules/*.mdc`（旧 `.cursorrules`） |
| Windsurf | `.windsurfrules` / `.windsurf/rules/` |
| Gemini CLI | `GEMINI.md` |
| GitHub Copilot | `.github/copilot-instructions.md` |

设计：

- 规则是一类**受管理配置**，与 Skill、MCP 并列；规范源写在 `.aidock/rules/`（项目）或全局规则（个人层），内容工具无关。
- 适配器把规范规则**编译**成各工具的原生指令文件，保证同一套规则在所有工具中行为一致。
- 这属于 [7.4 Profile 引擎](#74-profile-引擎) 中 `rules` 字段的落地形态。

**托管区块（Managed Block）——避免覆盖手写内容**

`CLAUDE.md` / `AGENTS.md` 这类文件用户经常手写内容，不能整体覆盖（这是 [8.3 生成物原则](#83-插件目录结构与生成物原则) 的例外）。做法是用标记圈定 AIDock 管理的区间：

```markdown
<!-- 用户手写内容，原样保留 -->

<!-- aidock:begin -->
...由规范规则生成的段落...
<!-- aidock:end -->

<!-- 用户手写内容，原样保留 -->
```

- 只重写 `aidock:begin/end` 之间的内容，标记外的手写段落原样保留。
- **漂移检测**：若标记内被手工改动，`apply` 时报"漂移"并给出选择（覆盖 / 保留 / 合并）。
- **同步模式**：默认**单向**（规范源 → 原生文件）；标记**之外**的手写内容**永不覆盖**，标记**之内**的手改走上面的漂移提示。**双向回写**（把原生文件的手改升格为规范源的一部分）列为**可选后续**；即便日后实现，也必须"**显式确认才回写、绝不自动**"，避免破坏唯一规范源（AIDock 模式为 `.aidock/`，存量桥接为 §7.12 登记的来源）。
- **导入**：能把已有 `CLAUDE.md` / `AGENTS.md` 的规则区导入为规范规则，降低迁移摩擦。

### 7.11 Hook 与 CLI 扩展

**Hook（钩子）**

Hook 是在特定时机触发的动作，对应各 AI 工具的原生 hooks 能力。

| 时机 | 说明 |
| --- | --- |
| `pre-apply` / `post-apply` | 配置编译前后 |
| `pre-install` / `post-install` | 插件安装前后 |
| `pre-sync` / `post-sync` | 推送 / 拉取前后 |
| `on-memory-capture` | 会话摄取产出后 |

规则：

- Hook 以**子进程**执行，受 [9.2](#92-mcp-服务器进程隔离与凭据隔离) 隔离约束（env 白名单 / 工作目录 / 网络策略）。
- Hook 必须声明 `permissions`，**走安全门**；其依赖安装同 [9.1](#91-插件安装必须先审计后运行)。
- **失败处理**：默认 **fail-closed**（阻断主流程），可配置为 warn 后继续。
- **超时熔断**：每个 hook 有超时上限，超时即中止（呼应 [8.1](#81-必须钉死的不变量不可被插件-patch-掉) 的"超时熔断"）。
- 执行写审计日志。
- 编译：工具原生支持 hook 则直译；否则由 AIDock 在自身流程中**代执行**（能力矩阵 `native` / `degraded` / `unsupported`，见 [7.2](#72-插件注册表与适配器)）。

**CLI 扩展**

登记可被调用 / 执行的命令行工具：

- 形态：由 AIDock 管理其参数模板、工作目录、权限；可被用户手动执行，也可**包装为 MCP 工具**暴露给 AI 客户端（可选）。
- 隔离与凭据同 Hook（[9.2](#92-mcp-服务器进程隔离与凭据隔离) / [9.6](#96-凭据生命周期)）。
- 执行结果统一为**结构化输出 + 标准化错误**；超时熔断同 Hook。
- 与 MCP Server 的边界：本身是 MCP 协议的归 `mcp-server`；纯命令行工具用 `cli` 类型登记。

### 7.12 同项目多工作副本同步

**用户场景**：`E:/work`、`E:/work2`、`E:/work3`、`E:/work4`、`E:/work5` 是同套项目的独立工作区。任意副本改技能或共享配置后，可预览并传播到选定其它副本；各副本继续保留自己的任务、分支、本机设置和会话。

**身份和边界**

- `project.id` 表示逻辑项目；每个实际工作副本有独立 `copy_id`。加入同项目副本时保留 project id、新建 copy id；新独立项目则新建 project id。目录改名/搬家只修改本机绑定，不能由同名目录或相同 Git remote 自动认定身份。
- 工作区根是容器，不是自动共享的配置层。显式登记 `workspace`、`server`、`client` 三个独立 `scope_id` 和对应逻辑项目；同名技能用 `(scope_id, skill_id)` 区分。每个作用域可选择不同成员与策略。
- 共享的是能力配置。会话、授权、环境历史、代码索引和诊断证据按 copy 隔离；知识正文是否共享仍由 §7.5 的独立策略决定，加入副本组不扩大记忆检索范围。
- MCP 启动器在多副本场景带 `--copy <copy-id>`：`aidock mcp exec --project <id> --copy <copy-id> --plugin <id>`。cwd、路径变量、授权、索引和本机覆盖按该绑定解析；缺省时只能从实际 cwd 唯一定位 copy，歧义则阻断。会话/审计保留 project、scope、copy 三个维度。

**此次只读摸底确认的来源（不是生效验收）**

| 作用域 | 技能真相源 | MCP 真相源 | 目标生成入口（在对应根目录） |
| --- | --- | --- | --- |
| 工作区根 | `.claude/skills/workspace-env-history/`；默认归副本本地 | `.ai-config/mcp-servers.json` | `python .ai-config/sync_ai_configs.py --write` / `--check` |
| 服务端 `dragonsvr` | `skills/` | `.ai-config/mcp-servers.json` | `python script/ai_config/sync_ai_configs.py --write` / `--check` |
| 客户端 `dragoncli/trunk/client` | 通用 `skills/` + 领域 `.claude/skills/`；插件技能另行引用 | `.ai-config/mcp-servers.json` | `python -m tools.ai_config.sync_ai_configs --write` / `--check` |

服务端与客户端同名通用技能刻意分叉，不能跨作用域整包统一。`code-intelligence-tools` 的共同工具说明可经独立白名单共享。服务端 `.claude/.kimi-code/skills` 为全量生成镜像，`.kiro/.codex/skills` 主要是 openspec 镜像；客户端 `.agents/skills` 为生成/适配入口。镜像数量不同不等于缺失或未生效。

**存量接入的所有权选择**

- 新项目由 `.aidock/` 持有规范源并使用 AIDock 适配器；存量项目首期使用 `external-source` 桥接：现有源文件继续权威，AIDock 只登记同步范围、基线、字段映射和生成入口。每个作用域必须选定一种所有权模式，不能让两个生成器同时维护一个目标。
- 外部生成器按插件/CLI 扩展走版本锁和执行授权，不因在项目目录就视为可信。接入前声明全部读写路径、检查方式、临时目录运行能力与依赖；能在隔离暂存目录生成、校验且所有目标纳入备份/锁才开放写入。做不到则只诊断，提示生成器适配缺口。
- `.aidock/` 唯一规范源约束适用于 AIDock 所有权模式；桥接模式的权威相对路径登记在副本组规范（§19.11）。切换模式是独立迁移，先预览、备份、停用旧生成器；不能自动迁移或手改其镜像。
- 外部生成器能产出配置不代表它受 AIDock 运行治理。每个 MCP 条目标注 `governed` / `external`：governed 必须生成 §9.2 的锁定启动器；external 只显示原有状态/诊断，不继承隔离、授权中继或数据分级保证。v1 不新增/传播直连 external MCP 的运行字段；技能/规则等可独立同步，未托管的原有外部项保持原值。SSE/HTTP 接入在治理适配实现前明确排除，不能借桥接模式绕过 stdio 边界。

**可同步内容**

| 内容 | 默认处理 |
| --- | --- |
| 技能正文、frontmatter、引用附件和脚本 | 同作用域同步完整技能包及相对依赖；越界引用报缺口。脚本/权限变动重新授权 |
| 技能开关、规则托管段、Profile、MCP 共享定义及精确版本锁 | 按登记的文件/字段所有权同步；本机项拆分后才加入 |
| `mcp-servers.local.json`、绝对路径、端口、环境历史、机器绑定 | 留在各 copy；共享定义通过 `${PROJECT}` 等变量映射，各目标独立展开 |
| 凭据值、旧授权、会话、日志、索引、缓存 | 排除；检测到疑似密钥时阻断待审条目并脱敏展示 |
| 原生工具生成配置、技能镜像 | 各目标从自己的有效源重新生成，检测漂移；不从源副本复制 |
| 未知文件、非托管字段、未登记规则段 | 排除并显示原因；不得通过整目录复制隐式接管 |

共享 MCP 条目若混入硬编码路径，不做全文件字符串替换：按登记的路径字段提取本机覆盖或转变量；无法无损拆分时阻断该条目，显示每个目标的最终值。策略/工具权限只能通过各目标当前安全门，源副本的授权不随行。

**从任意副本发起的流程**

1. 注册五个 copy 与三个作用域，读取实际 Git/SVN 身份、分支/版本及配置状态；只记录，不更新/提交。首次没有共同基线的差异为 `BASELINE_UNKNOWN`，必须逐项选边或设为本地覆盖，不能默认以 work 为最新。
2. 选择本次源副本、作用域、条目和目标副本。共享变更与本地覆盖分别显示；副本组没有永久主目录。
3. 使用双方最近确认的共同版本做三方比较：目标未改则可传播，双方相同则无操作，只有目标改则提示从目标发布/保留，双方不同则 `CONFLICT`。不按修改时间、目录顺序或技能数量决定胜负；不自动合并正文。选择源版本必须显式，保留目标可登记为本地覆盖；删除使用 tombstone，单独确认，不因源文件缺失就删除其它副本。
4. 生成每目标有效配置、原生目标 diff 和预检；预览显示来源链、排除项、版本兼容性、目标当前未提交改动、恢复点及生效检查范围。与未提交改动重叠时保留并要求选边，无关改动不受影响。
5. 确认后重新检查 plan 中所有源/目标/依赖/基线哈希、copy 路径、生成器/适配器版本与安全策略；变化返回 `PLAN_STALE`。按实际解析路径锁全部已选目标，先持久化事务日志和每 copy 的原始字节、源、草稿及生成物备份，再写入。
6. 源更新、目标重新生成、静态校验都成功后才提交基线；任一目标失败恢复本事务所有已改 copy，保留发布者改动。默认整批成功或恢复；用户需要缩小目标集合须重新预览。
7. 显示“已同步 / 已生成 / 待新会话验证”独立状态。旧会话不自动重启；新会话与实际探测失败不删除已同步源，作为运行问题另行处理。

本机覆盖高于共享层时，预览必须显示“共享版本已更新，但本副本有效值仍由本地覆盖决定”。显式选择保留目标可分为本次跳过与持久本地覆盖，二者不能混同；清除本地覆盖是另一个有 diff 的写操作。缺少目标、副本离线、生成依赖缺失或分支/Schema 不兼容时不得宣称全部同步：选定集合内任一不可用则阻断；取消该目标后重新 plan。取消发生在提交前则无正式写入，提交中取消走整批恢复；不能强制退出并遗留半批次。

多目录文件替换不能提供 OS 全局原子性：写入期间外部工具可能读到中间状态。批次日志记录每目标阶段，崩溃后先恢复；恢复期间外部编辑返回 `RECOVERY_CONFLICT`，保留双方字节、阻断后续写入，不能强行覆盖。真实验收须含第二副本失败、程序中断、目标被编辑和 junction 越界。

**回退和变更发现**

- 一次跨副本批次对应一个恢复点，关联每 copy 的旧源、草稿、原生字节、所有权与基线。时间线可回退整个批次或选定副本；局部回退形成新的共享差异，不能悄悄向其它副本扩散。撤销回退复用 §10.15 的预览、备份和过期检测。
- 首期手动刷新/同步；控制台打开时可观察已登记源，连续稳定读取后只提示变更，不自动写入。不递归扫描整工作区、不生成常驻服务；关闭控制台停止观察。未来自动同步需单独授权作用域/条目/目标，冲突、权限扩大、删除和不兼容版本一律暂停。
- 不执行 Git/SVN 更新、提交、推送、还原或部署；策划目录不加入默认写入白名单。跨副本同步与云端 `push/pull` 是两条操作，状态和恢复点独立。

## 8. 插件架构原则：钉死不变量，开放可替换层

"一切皆插件"听起来很美，但过度插件化会带来组合爆炸和权限审计失控。参考 DeepSeek Harness 的实践：**先钉死不变量 bundle（权限、审计、验收、超时熔断），再把模型、工具、循环、UI 开放为可替换插件。**

### 8.1 必须钉死的不变量（不可被插件 patch 掉）

| 不变量 | 说明 |
| --- | --- |
| 插件安装前的安全门检查 | 任何插件安装都必经审计，插件的插件不能绕过 |
| MCP 服务器的隔离执行底线 | 隔离等级下限由 AIDock 决定，插件无权降低 |
| 凭据注入的加密与隔离机制 | 密钥库、注入路径不可被插件替换 |
| 审计日志 | 谁安装了哪个插件、谁授权了哪个权限，完整性可检测、不可关闭 |

### 8.2 可以开放为插件的部分

- AI 工具的适配器（新增一个工具的支持）。
- 上下文压缩策略。
- 记忆 MCP 的嵌入模型和检索算法（若为自研 MCP）。
- 控制台的主题和布局。

### 8.3 插件目录结构与"生成物"原则

参考 `plugin-kit-ai` 的目录结构：

```text
plugin/
├── plugin.yaml               # 规范源（Single Source of Truth）
├── mcp/
│   └── servers.yaml          # MCP 服务器定义
├── skills/
│   └── **                    # 技能定义
└── targets/
    └── <platform>/           # 各平台原生配置生成物
```

核心原则：

- **每个作用域只有一个规范源，各 AI 工具的托管配置只是编译输出。** 新项目源在 AIDock 目录；存量 `external-source` 使用 §7.12 显式登记的权威源及锁定生成器，不建立第二份可编辑真相源。
- 原生配置中的 **AIDock 托管部分**是编译产物；其余部分继续由用户或第三方工具拥有。
- 每个适配器声明托管文件、Markdown 区块以及 JSON/TOML 字段路径。MCP 默认只拥有注册过的命名空间项（如 `mcpServers.aidock-<project-id>-<plugin-id>`）；多副本共享用户级配置时加入 copy id，避免启动器绑定互相覆盖。不得拥有整个 `mcpServers`、模型配置或整份用户配置文件。
- 首次遇到同名非托管项或托管部分漂移时阻断写入，展示冲突，允许显式导入到规范源、改名或确认接管；不得凭同名直接覆盖。导入也需重新经过权限校验。
- Markdown 保留区块外内容；JSON/TOML 保留非托管字段，格式允许时保留注释与排版。适配器无法无损保留时必须报告限制并阻断该目标，不能整文件重建后宣称保留成功。
- Local Root 的所有权清单记录目标规范路径、托管字段/区块、适配器版本、上次生成哈希。规范源、目标哈希与事务行为见 §20.1；多个项目共享用户文件时按实际目标锁定（§20.3）。

## 9. 安全设计：把"信任"作为第一优先级

AIDock 管理的是开发者最敏感的东西：API 密钥、源代码、MCP 服务器配置、个人知识库。安全不是附加功能，而是产品的生存底线。

### 9.1 插件安装必须"先审计，后运行"

在插件安装流程中内置一个**默认启用**（而非可选项）的"安全门"：

| 检查项 | 说明 |
| --- | --- |
| 来源验证 | 检查发布者历史、是否有已知 CVE、GitHub 仓库活跃度 |
| 权限清单 | 在安装确认弹窗中明确展示插件请求的权限（文件系统读写范围、网络出口、终端执行能力），来源为 `plugin.yaml` 的 `permissions`（见 [7.2](#72-插件注册表与适配器)） |
| 代码可审计性 | 优先推荐开源、且可与已知良好构建进行 diff 的插件 |
| 版本锁定 | 默认锁定插件版本，更新需用户显式确认 |

**信任等级（Trust Level，四级累积）**

安全门的结论不是"通过 / 拒绝"二元判断，而是一个**累积式四级评级**——每一级在下一级的基础上叠加更强的证明要求：

| 等级 | 名称 | 徽章色 | 检查项（**含所有低级项**） | 定位 |
| --- | --- | --- | --- | --- |
| **L1** | Basic 基础 | 灰 | 能生成 SBOM、无已知恶意代码、`plugin.yaml` manifest 有效 | 最低可安装线 |
| **L2** | Standard 标准 | 蓝 | ＋ 依赖固定版本与哈希、静态分析通过、作者身份可查（发布者历史 / 仓库归属） | **默认安装门槛** |
| **L3** | Verified 已验证 | 绿 | ＋ 发布包签名、构建来源证明（provenance）、仓库健康度（活跃度 / 维护者） | 推荐 |
| **L4** | Attested 已存证 | 金 | ＋ 行为分析、可复现构建、构建产物可关联到具体 commit | 最高 |

- **评级与分值**：展示为「L3 · 87」——**等级**表示"达到了哪一级"，**分值**（0–100）表示该级内各检查项的加权通过度。
- **门槛策略**：**默认门槛为 L2**。低于门槛的插件仍可安装，但必须在安装弹窗中给出明确风险提示并**显式放行**，放行写入审计日志（与下方"离线降级"走同一条路径）。
- **离线可得性**：L1 完全可离线判定；L2 的身份核验与静态分析、L3 / L4 的签名与存证需要网络或本地缓存（见下方"离线降级"）。
- **展示位置**：等级徽章出现在**插件市场卡片 / 列表行**与**插件详情页**两处，让用户在安装前即可判断可信度（见 [10.3](#103-插件管理面板) / [10.4](#104-插件详情页)）。

**判定者分层（谁算这个等级）**

等级不由单一主体判定——**判定者的分层，直接决定了哪一级能离线拿到**：

| 等级 | 判定者 | 离线可得 |
| --- | --- | --- |
| **L1** | **core 本地**（读 manifest、本地 CVE 快照、生成 SBOM） | ✅ |
| **L2** | **core 本地 ＋ 外部数据缓存**（发布者历史、静态分析库） | ✅ 缓存命中；⚠️ 未命中则**降级为 L1 结论**并标注 |
| **L3 / L4** | **外部签名 / 存证服务**（签名验证、构建证明、行为分析） | ❌ 不可得 → 标注"**未验证**" |

- **插件信任评估不引入重依赖**：core 不内建大型静态分析器或第三方存证服务；外部评估/缓存必须绑定产物摘要、来源和有效期，缺证据显示未知，不能自动给 L2。core/适配器分发验签、锁摘要核对是 core 必需的验证能力，独立于插件 L3/L4 存证服务，不能因“评估委托”跳过升级验签。
- **SBOM 的边界**：core **只为"本机已安装的插件"生成轻量 SBOM**——读 `plugin.yaml` 声明的依赖清单，**不做传递依赖解析**。完整的传递依赖分析与漏洞扫描属 L2/L3，**不在 core**。
- **L3 / L4 的"外部服务"具体是什么**：**不要求 AIDock 自建服务**。候选是公开的签名与存证基础设施（如 Sigstore、GitHub Artifact Attestations）；**自建签名密钥**是兜底方案（个人开发者给自己的插件签名）。**具体选型属后续**，本文档只约定接口语义：能判定"验签通过 / 来源可追溯"即可。
- **L3 / L4 不可得 ≠ 拒绝安装**：只标注"未验证"，是否放行由**最低信任等级门槛**决定（见 [10.10](#1010-设置界面)）；低于门槛才需显式确认 + 写审计。
- **缓存过期与刷新**：外部数据缓存设 TTL；**有网络时**后台刷新，刷新失败则沿用旧缓存并标注时效。

参考 PROMETHEUS 的做法（安装任何 agent 插件前先运行 nemesis 安全门检查），AIDock 把"安全门"设计为安装默认流程。

**依赖安装同样走安全门**

`bootstrap` / 安装时解析 `plugin.yaml` 的固定版本，在安装隔离上下文中执行包管理器或展开二进制——**这本身可能执行第三方代码**，因此：

- 依赖安装与插件安装**走同一道安全门**，不得单独放行。
- 默认**不自动执行构建脚本**（如 npm `postinstall`），需用户显式允许。
- 依赖版本必须锁定（固定版本号、校验哈希），禁止 `latest` 之类浮动引用。
- 安装生成 `plugins.lock`：来源、精确版本、完整解析依赖及产物摘要、运行时版本约束、平台、入口相对路径。摘要必须来自经验证的来源，不能把“刚下载后自算哈希”当来源验证。未知来源/未验证信任等级标为 L0，不自动补成 L2。
- 运行阶段只启动经锁文件验证的本地产物（例如固定 Node 运行时 + 本地脚本），不执行 `npx -y <浮动包>` 或现场下载安装。更新、新平台重装、版本/权限/信任证据变化必须重新走安全门；项目授权绑定锁摘要与权限，不因全局安装而获得授权。

**离线降级**

安全门的"来源验证"依赖外部数据（GitHub API、CVE 库）。**无网络时**：

- 降级为"仅本地已知信息"（本地缓存的安全门结论、已知 CVE 快照）；**L3 / L4 的判定不可用**，只能给出 L1 / L2 结论。
- 低于默认门槛（L2）的插件，默认**拒绝安装**；用户可在明确风险提示后显式放行，该放行写入审计日志留痕。

### 9.2 MCP 服务器：进程隔离与凭据隔离

MCP 服务器的本质是"以你的用户身份运行的独立进程"。它继承环境变量，能读取 SSH 密钥、云凭据、浏览器 profile，并能向任意地址发起网络连接。**stdio 传输不是沙箱——客户端和服务器共享同一信任域。**

**不要求 Docker / runc**。隔离必须由 OS 执行；工作目录、env 白名单、HTTP 代理设置、Job Object 单独都不构成文件/网络沙箱。插件直接使用绝对路径或套接字也必须受同一策略约束。

**平台能力矩阵（实现候选，未经运行验收）**：首期以 Windows 为隔离验证主平台，其余平台逐项启用能力；跨平台 CLI 可用不等于隔离能力相同。

| 平台 | 文件读写强制边界 | 网络强制边界 | 子进程/资源 | 上线门槛 |
| --- | --- | --- | --- | --- |
| Windows | AppContainer/能力 SID + 专用目录 ACL；只读/可写分别授予，不扩大已有用户目录权限 | 无网络能力的隔离进程 + 经受控 IPC 访问出口 broker；直接套接字与本机服务均不可绕过 | Job Object 限额与退出清理，禁止 breakaway；禁 exec 时用适用的子进程创建限制 | 必须验证目标运行时、匿名管道/句柄、目录 ACL、junction 与直连拒绝；受限令牌本身不足以宣称完成 |
| Linux | 可用的 user/mount namespace + Landlock 或等效强制访问控制，路径挂载 ro/rw；仅 chdir 不算 | 独立 network namespace 无默认出口；只给受控 IPC/broker，不能借宿主 localhost 绕过 | cgroup 可用时限额；seccomp/等效策略约束 exec 与子进程 | 探测内核、namespace/LSM/cgroup 权限；任一所需能力缺失则拒绝对应 Tier |
| macOS | 尚未选定受支持、可分发的 OS 强制机制 | 尚未验证 | 尚未验证 | 默认报告隔离不可用；不得将已弃用机制或代理设置当成已支持 |

启动返回实际能力 `fs_ro/fs_rw/net_deny/exec_deny/resource_limits`、策略摘要与模式。要求的能力不足时返回 `ISOLATION_UNAVAILABLE`，不启动插件；用户可单独选择仅面向自有可信插件的 `unisolated` 模式，必须显示实际状态并写审计，不能冒充 Tier 1/2。所有路径在可信 broker 中按最终对象/句柄授权，拒绝符号链接、junction、硬链接和重命名竞态造成的越界；网络 broker 默认拒绝未声明域名、重定向目的地和解析到本机/私网的地址，只有显式授权才放行。

**MCP 会话启动器（v1 stdio）**：

```text
AI 客户端 ↔ aidock mcp exec --project <stable-id> [--copy <copy-id>] --plugin <id> ↔ 隔离中的锁定 MCP
                          └─ 会话策略/凭据注入/stdio 授权中继/出口 broker/审计
```

- 适配器输出 `command: aidock` 与独立 `args` 数组，不输出任意 shell 字符串。启动器解析已注册项目、有效配置和锁摘要，先校验能力与授权再启动；记忆检索/存储仍归记忆 MCP，不在 core 引入记忆引擎。
- `--project` / `--copy` 是绑定选择，**不是授权证明**。授权绑定由用户确认的项目、作用域、副本、规范配置摘要、插件锁摘要、权限、数据级别和处理目的地；各副本不得复用另一副本的有效授权。仅有 stdio 的客户端无法证明自身不可被同用户进程伪造；威胁模型不承诺防同用户恶意客户端。调用参数不得提升到另一个项目或共享范围；无法可信过滤项目/等级的记忆 MCP 拒绝接入治理模式。
- 中继维护 JSON-RPC 请求身份、工具能力清单与读/写分类；未知工具默认需确认或拒绝。`memory_save` 等写调用在转发前向当前用户请求授权，AI 文本不能作为授权；无交互批准渠道时返回 `AUTHORIZATION_REQUIRED`，不得挂起无限等待。返回结果在交给客户端前执行项目/敏感度/目的地检查，审计记录元数据和结果摘要，不记录密钥/正文。
- 出口 broker 和子进程与 `mcp exec` **会话同寿命**。`apply` 只写配置，不负责维持出口。控制台关闭不影响客户端会话；客户端 EOF、取消或启动器退出时有序关闭子进程与 broker，无全局常驻 daemon。broker 若有本地端口仅回环监听并绑定会话鉴权；隔离侧只能通过受控连接访问。
- 调试实例与客户端会话分别带实例 id、project/plugin/owner；“停止调试实例”不意味着所有客户端实例都已停止。崩溃/退役/授权拒绝返回结构化错误；stderr 用于诊断，stdout 只承载协议。

分级**隔离**（同一套手段的强度组合，非容器分级）：

| 等级 | 适用场景 | 组合 |
| --- | --- | --- |
| Tier 0 / unisolated | 用户显式选择的自有可信插件 | 环境变量白名单 + 凭据按需注入；明确标为非隔离，不保证文件/网络边界 |
| Tier 1 | 社区插件，来源可信 | Tier 0 + 默认断网（经代理白名单放行）+ 工作目录白名单 |
| Tier 2 | 来源不明或高权限插件 | Tier 1 + 工作目录只读 + 网络全禁或极小白名单 + 资源/子进程限制 |

治理原则（可直接采纳）：

- **凭据隔离与版本锁定**：凭据永远不写入插件的 `.env` 文件，由 AIDock 密钥库在运行时注入。
- **隔离强制底线**：最低隔离等级由平台强制，插件不能自行声明降级。
- **结构化错误与故障降级**：每个 MCP 服务器进程崩溃时，向 AI 客户端返回结构化错误，而不是裸连接错误。
- **生命周期管理**：提供服务器的启动、健康检查与有序 Retire（安全下线）流程。
- **一键清理**：提供"一键移除未使用服务器"入口——MCP 官方安全指南第一条即"打开配置，删除不再使用的服务器，确保你知道每个剩余服务器的来源并锁定版本"。

### 9.3 本地智库的数据分级

记忆 MCP 会存储代码片段、设计决策、排错经验，其中可能包含 API 密钥、内部架构信息、客户数据。AIDock 通过安全门与检索作用域对这批数据施加分级管控；参考 GuardRAG 的四级数据敏感度体系：

| 等级 | 内容示例 | 检索/外发策略 |
| --- | --- | --- |
| Public | 开源代码片段、通用设计模式 | 可自由检索、可外发 |
| Internal | 项目内部架构决策、API 使用方式 | 仅向确认在本机处理的模型/调用链自动返回；远程或未知目的地默认不返回 |
| Confidential | 含凭据引用的配置片段、内部文档 | 需显式授权，默认脱敏 |
| Restricted | 客户数据、合规相关记录 | 通过 MCP 暴露给外部客户端时**默认不返回** |

**客户端运行位置与模型处理位置分别建模**。本地客户端连接远程 API 仍按远程处理；未知 endpoint、未知转发链默认按远程。控制台在装配上下文及每次模型请求前检查目的地策略，覆盖候选标题、记忆正文、代码片段、引用展开与工具结果；切换 provider 后重新校验。Internal 向远程发送必须按具体目的地、等级、用途取得独立明确授权，不能使用插件安装授权代替。

外部客户端若不能可信声明并约束后续处理目的地，中继默认只返回 Public；不能承诺控制未知客户端收到正文后再次外发。受支持客户端的本地处理也需包含本地 embedding/rerank 等所有环节；Confidential 默认脱敏且显式授权，Restricted 不向外部客户端自动返回。个人管理视图读取敏感记忆不等于允许将其放入模型上下文。

> 该分级与 7.5 的"按项目隔离检索"是两层正交的边界：项目边界控"哪个项目的知识"，敏感度分级控"哪类知识能出圈"。

### 9.4 本地 Web 控制台的安全模型

界面的载体是**由 CLI 按需拉起的本地 Web 控制台**（见 [10.0](#100-载体本地-web-控制台)），而不是常驻的桌面应用。控制台本质上是"一个监听本地端口的、能读写数据根的高权限服务"，因此下面几条必须钉死：

- **只监听回环地址**：控制台 HTTP 服务**只 bind `127.0.0.1`**，绝不监听 `0.0.0.0` 或任何对外网卡。
- **一次性启动令牌**：随机 token 放在首次 URL fragment，换取与当前控制台进程绑定的短期会话，交换后移除 fragment；不放 query、访问日志或导出。API 必须带会话认证与防 CSRF 绑定，启动 token 单次有效，退出/超时失效。
- **Host / Origin 校验**：拒绝 `Host` 头非 `127.0.0.1` / `localhost` 的请求，拒绝跨源 `Origin`，**不下发宽松的 CORS 头**。
- **按需启动、用完即走**：服务仅在命令执行期间存在，控制台关闭或空闲超时后进程**自杀**，不常驻端口。
- **路径按操作授权**：数据管理只访问当前 Config/Local Root；项目文件浏览只访问已注册 copy 根；应用只写 plan 中已授权的真实目标及托管部分。三类边界分别校验，外置配置/原生用户配置不通过任意路径 API 获得权限。解析链接、目录别名和实际对象后再授权，不用字符串前缀判断。
- **CSP**：正式控制台不引入外部脚本/CDN，不开放 `unsafe-inline` / `unsafe-eval`；脚本使用受约束资源与事件绑定。当前 Demo 的内联脚本/事件仅是原型，不能原样作为正式前端安全验收结果。
- **不提供远程访问模式**：控制台**不设**绑定对外网卡的开关（如 `--remote`）。若确需跨机查看，请自行经由 SSH 隧道等既有通道，**不改变控制台自身的监听约束**。
- **依赖扫描**：定期用 Snyk 等工具扫描 Go 与 JavaScript 依赖。

### 9.5 审计日志

审计日志是 [8.1](#81-必须钉死的不变量不可被插件-patch-掉) 规定的不变量之一；安全事件记录不可关闭，core API 不提供改写历史的接口。

**记录内容**

| 事件 | 说明 |
| --- | --- |
| 插件/依赖安装 | 装了哪个、什么版本、来源、安全门结论 |
| 权限授权 | 谁授权了哪项权限（`fs` / `net` / `exec`），含离线放行 |
| MCP 写操作 | `memory_save`、`profile_apply` 的调用与结果 |
| 隔离等级变更 | Tier 调整 |
| 回滚 | 回滚动作及其目标快照（见 [7.7](#77-同步引擎)） |

> **与"指标日志"的区别**：使用量类数据（Token 消耗、调用频次）**不进本日志**，另存于"指标日志"（见 [10.14](#1014-指标)），保持安全事件与用量事件分别记录。

**存储与留存**

- 存放在 **Local Root**，追加写 + 哈希链提供**有条件的完整性检测**。插件隔离策略禁止写审计目录；不宣称能防同用户管理员重写全链、删尾或替换日志。
- 每段封存时保留段序号、首尾摘要、前段引用；更强检测需要签名及存放在可信位置的外部锚点。只存在同目录的链头/链尾不能独立证明日志未被整体替换。
- 按天数/大小封存，每段 ≤ 10 MB。保留期到期不直接清空链：默认保留；显式归档后可清理已封存正文，保留摘要、锚点引用和清理事件。未封存活动段禁止修改/清理。

**跨机断档的处理**

审计日志默认随本机、不迁移，换机后历史会断档。解决办法是提供**归档导出**：

- 可将审计归档（可选签名）放入 Config Root 或独立备份，实现跨机可查。
- 归档**只含审计记录，不含密钥**。
- 新机 `bootstrap` 后可验证并引用旧机封存链，生成关联事件；各机链与缺口分别展示，不把导入归档宣称为一条无间断原始链。

### 9.6 凭据生命周期

| 环节 | 说明 |
| --- | --- |
| 添加 | 在密钥库写入"名称 → 值"；值只存 OS 凭据库（keyring），**不落配置文件** |
| 引用 | 配置 / 插件中以 `${SECRET:NAME}` 引用（见 [19.1](#191-跨平台路径变量)），文件里永远看不到明文 |
| 绑定 | 插件通过 `secrets: [NAME]` 声明需要哪些凭据；**只有被声明的才会注入** |
| 注入 | 运行时按需注入，随进程结束消亡 |
| 轮换 | 更新值即可，所有引用方下次启动自动生效，**无需改配置** |
| 删除 | 删除前检查引用方，仍有引用则警告 |
| 导出 | v1 只导出 `${SECRET:NAME}` 引用；`--include-secrets` 返回不支持。跨机重建 OS 凭据库，避免把普通备份误当安全凭据迁移 |
| 审计 | 添加 / 轮换 / 删除 / 授权注入均写审计 |

**注入作用域原则**：一个插件只能拿到它**显式声明**的凭据——防止"装了 A 插件却读到 B 插件的密钥"。

**「添加凭据」弹窗**

| 项 | 规则 |
| --- | --- |
| 名称 | 必填；**唯一性校验**（重名直接报错）；建议 `[a-z0-9_]` 小写加下划线 |
| 值 | 密文输入（默认遮蔽，可切换显隐）；**只输一次**，不做二次确认——减少输入负担 |
| 落盘 | 只写 OS 凭据库；配置文件里**永远只留 `${SECRET:NAME}`** |
| 绑定 | 添加后可立即勾选"绑定到哪些插件"，也可稍后在插件配置里引用（遵循上方注入作用域原则，见 [9.2](#92-mcp-服务器进程隔离与凭据隔离)） |
| 审计 | 添加动作**写审计日志**（见 [9.5](#95-审计日志)） |

## 10. 界面设计（本地 Web 控制台）

### 10.0 载体：本地 Web 控制台

AIDock 的界面**不是常驻的桌面应用，而是由 CLI 按需拉起的本地 Web 控制台**：

- `aidock config` 启动一个**只监听 `127.0.0.1`** 的本地 HTTP 服务，并调起系统默认浏览器打开控制台页面。
- 服务进程随控制台关闭或空闲超时**自动退出**，不常驻端口。安全约束见 [9.4](#94-本地-web-控制台的安全模型)。
- 静态资源由 Go 二进制 `embed` 打包，core 单文件分发、无单独前端服务器；插件可有独立运行时依赖。现有原型可演进，但正式前端须完成 §9.4 的 CSP/事件绑定与认证改造，需要工程化时再引入 Vue 构建。
- 控制台与 CLI **共用同一套引擎与数据根**，不做第二套逻辑：界面只是引擎的一个前端。

**为什么不用原生桌面应用**

| 维度 | 本地 Web 控制台 | 原生 app（如 Tauri） |
| --- | --- | --- |
| 开发速度 | 复用网页原型，无原生壳与打包链 | 需额外工具链与原生壳 |
| 分发 | 单二进制，浏览器零安装 | 需按平台签名打包 |
| 能力边界 | 无托盘 / 全局快捷键 / 原生通知 | 具备完整 OS 集成 |

**边界**：控制台聚焦**配置 / 查看 / 审计**；`apply`、`plan`、`push` / `pull` 等**始终保证可纯 CLI 使用**，这是可脚本化的主路径。但这**不等于**界面上不能有按钮：

- 控制台**可以为写操作提供入口**（如同步面板的推送 / 拉取、时间线的回滚）。
- 前提是**等价**：界面入口必须执行与 CLI **同一条命令**，不得另起一套逻辑、不得绕过安全门与审计。
- 原则：**CLI 是契约，界面是外壳**。

**后路**：Tauri 本质是 webview 承载网页，若日后确需托盘 / 开机自启，可直接把同一套前端塞进 webview，前端投入不会浪费。

### 10.1 主导航（以"项目"为中心）

基于四层模型，主导航分为三大块：

| 分组 | 内容 | 归属 |
| --- | --- | --- |
| **项目** | 每个项目一个入口；项目内管理全部就地完成（见 [10.2](#102-项目详情页)） | core |
| **工作区** | AI 对话、文件树、插件市场、技能库、智库、模板库、指标、时间线 | 界面属 core；**记忆类数据来自记忆 MCP**（见 [7.5](#75-记忆能力与记忆-mcp)） |
| **系统** | 同步与迁移、审计日志、设置、首次引导 | core |

> 原型 `demo/index.html` 即按此三分组实现，**以原型为准**。

**项目分组（仅组织视图）**

侧栏的"项目"支持**可折叠分组**，把一组相关的项目归在一起（如"前端工作流"含 3 个 React 项目），便于一并查看与切换。

> **注意：分组只是组织视图，不是新的配置继承层级。**
> - 项目间的配置共享由**既有机制**承担：各项目在自己的 `profile.yaml` 里写 `extends: <共享 Profile>`（见 [19.3](#193-profileyaml)），改共享 Profile 即对所有成员生效——**不需要**在分组上再挂一层配置。
> - 因此**技能作用域维持三种**（全局 / 项目 / 继承，见 [7.3](#73-技能作用域与-mcp-的关系)），继承链维持 `全局默认 → extends 链 → 项目覆盖 → 临时会话`（见 [19.6](#196-技能与配置的合并算法)），**均不因分组新增层级**。

**分组交互**

| 问题 | 规则 |
| --- | --- |
| 分组可以是空的吗 | 可以。空分组仍在侧栏显示，便于"先建组、再归入项目" |
| 一个项目能属于几个分组 | **只能一个**——对应 [19.2](#192-projectyaml) 的 `group` 单值字段；若需要"多归属"，应改用 Profile 继承而非分组 |
| 分组名与 `project.yaml` 如何同步 | 侧栏分组名即 `group` 字段的值；**改名会批量改写组内所有 `project.yaml`**，改名前提示影响范围 |
| 创建项目时能直接指定分组吗 | 能。命令行为 `aidock project add --group <name>`，控制台新建项目时提供分组下拉 |
| 未分组的项目 | 归入默认分组「未分组」（**不可删除**） |

**MCP 生命周期 UI（呼应 [9.2](#92-mcp-服务器进程隔离与凭据隔离) 的"生命周期管理"）**

MCP 是独立进程，因此列表必须体现"它现在活着吗"：

| 要素 | 说明 |
| --- | --- |
| 运行状态 | 四态：**运行中 / 已停止 / 异常 / 未启动**，带颜色语义（同 [9.1](#91-插件安装必须先审计后运行) 的徽章体系） |
| 操作 | **启动 / 停止 / 重启**；另提供轻量的「**重新加载**」用于改配置后生效 |
| 健康检查 | 可手动触发一次探测，结果行内显示（耗时 + 结论） |
| 安全下线（Retire） | 停止服务 → 等待在途调用结束 → 标记为已退役；**不静默 kill** |
| 日志入口 | 每行可直接打开该 MCP 的运行日志（见 [9.2](#92-mcp-服务器进程隔离与凭据隔离)） |

- 生命周期操作**等价于执行对应 CLI 命令**（`aidock mcp …`，见 [7.7](#77-同步引擎) 命令表），不是第二套逻辑——同 [10.0](#100-载体本地-web-控制台) 的"CLI 是契约，界面是外壳"。
- **平时 MCP 由 AI 客户端自行拉起**（同 [7.6](#76-mcp-网关) 的 stdio 约定）；这里的启动 / 停止**是为了调试与健康检查**而独立起停一个实例，**不改变 AI 客户端的拉起方式**，也不需要 core 常驻。

项目详情页是**项目级管理的唯一归属地**：技能、MCP、记忆、规则、AI 工具同步都在本页内完成，页面定位为**信息展示与就地管理**，因此不再设置跳转到工作区视图的"快速操作"入口。**工作区**（技能库、插件市场、智库、模板库等）与**系统**（同步、审计、设置）只承载跨项目的库与系统级设置（见 [10.1](#101-主导航以项目为中心)）。

每个标签页顶部提供就地操作入口（如「＋ 添加技能」「＋ 添加 MCP」），弹窗内只列出**当前项目尚未拥有**的条目，确认后就地生效，不跳转到工作区视图。引入 MCP 时弹窗内直接展示来源与权限清单（读安全门），与在插件市场安装走同一套校验。

### 10.9 规则编辑界面

- 编辑规范规则（`.aidock/rules/` 或全局规则），内容工具无关。
- 侧栏**实时预览**编译到各工具的产物（`CLAUDE.md` / `AGENTS.md` / `.cursor/rules` …）。
- **托管区块可视**：AIDock 管理区间与用户手写区间分色显示，手写部分只读灰显（见 [7.10](#710-规则与指令文件管理agentmd-等)）。
- **就地展开**：编辑器直接嵌在项目详情页的「规则」标签页内（左右双栏：规范源 + 编译产物实时预览），不再设独立视图，也不需要额外的跳转与返回。

**规则同步模式的 UI（呼应 [7.10](#710-规则与指令文件管理agentmd-等)）**

| 要素 | 位置 | 说明 |
| --- | --- | --- |
| 模式切换器 | 编辑器顶部 | v1 两档 `unidirectional`（默认）/ `prompt`；`bidirectional` 仅显示后续版本禁用状态，不进入有效 Schema |
| 漂移状态条 | 编辑器顶部 | 如"检测到 2 处手改，未回写"；**无漂移时不显示**（常态安静，见 [11.1](#111-插件安装弹窗三件事一眼读完)） |
| 漂移处理 | 点击状态条展开 | 三个操作：**保留手改**（升格为规范源）/ **覆盖回规范源** / **稍后处理** |
| 导入确认 | v1 显式导入操作 | 解析托管区块的漂移，展示规范源差异，用户确认后写入规范源；导入与后续 apply 分开 |

- 手写区间在编辑器里**只读灰显**（见上方"托管区块可视"），因此"保留手改"是让手写内容变成可编辑规范源的**唯一入口**。

### 10.12 AI 对话

控制台内置的对话面板，用于在**当前项目上下文**里直接与 AI 交互，就地验证配置是否生效。

- 会话区：新建 / 重命名 / 删除 / 搜索 / 排序，按项目归属。
- 消息区：Markdown 渲染、代码块一键复制、引用回帖、重新生成、删除。
- 输入区：回车发送、`@` 引用（文件 / 技能 / MCP）弹出选择器、发送状态提示。
- 顶部：选择本次对话使用的**模型提供者**与 Profile（**不是 AI 工具**——见下方通道说明）。
- 右侧上下文栏：本次挂载的项目 / 技能 / MCP、可用工具、会话统计（Token / 工具调用 / 耗时）。
- **上下文栏是只读的**：内容由**当前项目的 Profile 决定**，不能在这里单独增删技能 / MCP——要改就改 Profile（见 [7.4](#74-profile-引擎)）。
- **顶部 Profile 选择器只影响本次对话**：切换它**不改项目配置**，只改变这次对话装载的上下文；会话结束后**不留痕**。
- **它不内置模型**：控制台对话 v1 只接用户自配的模型提供者，凭据走 §9.6；不把其它 AI 工具应用作为对话后端。这是产品范围决定，不假定所有工具没有非交互接口。配置/技能发现和临时验证会话仍可通过已适配的工具接口完成，与长期对话集成分开验收。
- **AI 工具集成属后续可选**：若某工具日后提供稳定的非交互接口，再按适配器模式接入（见 [7.2](#72-插件注册表与适配器)）。

**会话存储**

会话是**有状态数据**，必须回答"存在哪、谁负责、是否随行"：

| 数据 | 归属 | 位置 | 进 Git |
| --- | --- | --- | --- |
| 会话记录（标题 / 消息 / 时间） | **core** | `<Local Root>/sessions/`（JSON 文件） | ❌ |
| 会话统计（Token / 工具调用 / 耗时） | **core（视图，不落盘）** | 由**指标日志**按会话 id 查询得出（见 [10.14](#1014-指标)） | ❌ |
| 会话中触发的**记忆写入** | **记忆 MCP** | 由该 MCP 自行决定 | ❌ |

- **单写入点，避免双写**：Token / 调用次数**只写指标日志这一处**；会话统计是**按会话 id 查询出的视图**，不另存一份。否则两边一旦不一致，长期极难发现。
- **默认只存本机、可关闭**：关闭后会话不落盘，仅当次会话内存中有效（此时"搜索 / 重命名"不可用）。
- **按项目 `id` 归属**（不是按路径），因此项目外置再内置、或改名后仍能对上。
- **为什么不由记忆 MCP 管会话**：① 记忆 MCP 存的是从对话中**提炼**出的知识（经确认、脱敏、结构化），**不是对话本身**；② 会话需要"临时性（可关闭即不落盘）""按项目过滤""与界面强绑定"——这三条都是 core 界面层的需求；③ 若交给记忆 MCP，等于强迫**所有**记忆 MCP 实现临时会话语义，会限制生态。
- **隐私与随行**：会话文件的权限要求**与审计日志同级**（仅当前用户可读）；任何导出必须**显式脱敏**（同 [9.6](#96-凭据生命周期)）；属 Machine-local，**永不进 Git、不参与同步**（见 [3.4](#34-区分能力与状态)）。这是**显式声明**，而非"位置在 Local Root"的隐含结果。
- **不违反"core 不含数据库"**：该约束针对的是**记忆引擎**，不是禁止 core 持有状态文件（**文件 ≠ 数据库**）；判定判据**统一见 [13.3](#133-core-的本地状态层)**，本节不重复展开。
- **会话摄取是独立开关**：开启后内容进入 [7.5](#75-记忆能力与记忆-mcp) 的"待确认队列"，**确认后由记忆 MCP 入库**（core 不存记忆）。
- **摄取的路由与分级**：
  - **路由**：`memory_save` 默认走**当前项目绑定的记忆 MCP**；若绑定了多个（见 [7.5](#75-记忆能力与记忆-mcp) 的多 MCP 并存），会话顶部提供**选择器**，默认取第一个；界面上的工具名**带来源前缀**（如 `cgh.memory_save`），避免歧义。
  - **分级**：进入"待确认队列"的内容**默认标为 Internal**（见 [9.3](#93-本地智库的数据分级)），用户可在确认时**逐条调级**；**Restricted 级永不自动摄取**，必须由用户手动勾选。
- **项目生命周期**：会话按项目 `id` 归属，因此项目外置 / 内置、改名都不影响对应关系；`aidock project rm` 移除项目时**提示"该项目下有 N 条会话，是否一并清理？"**——**绝不静默删除**。
- **归属**：面板本身属 **core**（界面与编排）；其中 `memory_*` 工具由**记忆 MCP** 提供（见 [7.5](#75-记忆能力与记忆-mcp)）。

### 10.13 文件树

浏览目录结构，供规则 / 技能编辑时定位文件。

**读取范围**：**只读**浏览**项目根目录**（含源码与 `.aidock/`），**不写、不编辑**。

| 项 | 规则 |

### 10.14 指标

本机使用趋势的可视化，**只统计本地数据、不外传**。

**视图与采集来源**

> **覆盖范围**：§9.2 的会话启动器可记录经过其 stdio 中继的请求/结果元数据；客户端直接启动的非托管 MCP、MCP 内部调用、未上报用量均不可见。分别标注中继观测、MCP 上报与会话采集来源，不重复累计，不承诺全量统计。

| 视图 | 采集来源 | 前置条件 |
| --- | --- | --- |
| **编译成功率** | `apply` 完成时写入指标日志（与编译报告归档成对，见下） | **无**——默认即可用 |
| **记忆调用次数** | 会话中继元数据；记忆 MCP 主动上报作为另一个来源，按 request id 去重 | 需经会话启动器或开启上报；标注覆盖范围，不承诺全量 |
| **Token 消耗趋势** | **① 控制台对话**：模型提供者回执**直接可得**（默认可用）<br>**② 其它 AI 工具的用量**：需**会话源适配器**（[7.5](#75-记忆能力与记忆-mcp) 的"被动扫描"） | ① 无；② **需开启被动扫描（默认关闭）**——只影响②的覆盖范围 |

- **未采集时不留空图**：该图位置显示**引导态**（如"未开启会话采集，无法统计 Token 消耗 →［去开启］"），**不画一条 0 的线**。
- **视图名称已校正**：原型里的「MCP 调用频次」在设计中限定为**记忆调用次数**——因为只有它可被观测，叫"MCP 调用频次"会承诺一个拿不到的数字。

**数据源（三个，互不替代）**

| 数据 | 来源 | 位置 | 进 Git |
| --- | --- | --- | --- |
| 安全事件（安装 / 授权 / 写操作 / 隔离变更 / 回滚） | **审计日志**（见 [9.5](#95-审计日志)） | Local Root | ❌ |
| 使用指标（Token 消耗、工具调用次数） | **指标日志**（新增） | Local Root | ❌ |
| 编译统计（成功率、降级项数） | `apply` 的**编译报告归档**（见 [7.2](#72-插件注册表与适配器)） | Local Root | ❌ |

**写入关系（`apply` 完成后写两条）**

| 写入 | 性质 | 用途 |
| --- | --- | --- |
| **详细编译报告**（归档） | **证据**——单次 apply 的完整产物 | 供用户按需回看"那次 apply 到底改了什么" |
| **聚合统计记录**（写入指标日志） | **数据点**——本次成功率 / 降级项数 | 供"编译成功率"趋势展示 |

指标页面**只读指标日志**，**不解析编译报告归档**——避免归档格式一变、指标页就崩。

**可关闭性（三源不同）**

| 数据源 | 可关闭 | 说明 |
| --- | --- | --- |
| 审计日志 | ❌ | 不变量，不可关闭、完整性可检测（见 [9.5](#95-审计日志)） |
| 指标日志 | ✅ | 可关闭；关闭后仅不再写入，不影响其它功能 |
| 编译报告归档 | — | 是 `apply` 的**副产物**，归档但**绝不阻止 apply**；关闭指标采集**不删除已有归档** |

**其它契约**

- **指标日志**是 core 侧一条**追加写、可聚合、可重建**的轻量记录，**与审计日志并列但用途不同**：审计记"安全事件"（完整性可检测、不可关闭），指标记"使用量"（可关闭、可重建）。
- **聚合机制**：指标日志是**追加写的事件流**，**聚合视图由控制台按需现算、不持久化聚合结果**——因此不存在"派生数据不一致"，也没有需要单独重建的中间层。具体采样与滚动策略属实现细节，本文档不规定。
- **为什么要单列一条**：Token 消耗与调用频次**不属于安全事件**，用量应单独记录以明确采集范围与留存策略；而审计日志现有记录项（见 [9.5](#95-审计日志)）**也无法推导出** Token 数据。
- 全部数据**只在本机**，不依赖远程服务、**不上报**；指标采集可在设置中关闭。
- **归属**：**core**（符合 [13.3](#133-core-的本地状态层) 的三条硬约束：追加写、无索引、可重建）。

### 10.15 时间线

配置变更的时间轴，基于每次 `apply` 自动生成的 Git 快照（见 [7.7](#77-同步引擎)）。

- 每个节点显示：时间、触发命令、变更摘要（新增 / 修改 / 移除条目数，来源见 [19.10](#1910-时间线快照元数据)）。
- **「回退到此」**：等价于 `aidock replay <snapshot>`；执行前展示范围与差异并确认，走当前策略校验、回退前备份、全目标重新编译与事务恢复，写审计。只读查看、恢复草稿、应用回退分别标识。
- **只读查看是另一个动作**：节点上的「查看快照」只展示当时内容，**不触发任何写入**。两个动作在 UI 上必须**区分开**，不能用同一个按钮。
- 与 [10.11](#1011-审计日志查看) 的审计时间线**区分**：**时间线看"配置快照"，审计看"安全事件"**。
- **快照不依赖同步后端**：快照所需的 Git 仓库由 core 在 **Local Root 本地自建**（仅本机、不推远端）。因此**即使同步档位选②（云盘目录、无 Git 远端）**（见 [7.7](#77-同步引擎)），时间线与回滚**依然可用**。
- **归属**：**core**。

**回退是首期可靠性底座**，在第一次正式写入前即具备；不等同步/市场阶段才补实现。

| 恢复方式 | 恢复范围 | 执行规则 |
| --- | --- | --- |
| 应用失败自动恢复 | 本次修改过的托管目标与所有权清单 | 事务备份恢复，规范源草稿保留；不把失败的新配置标成已应用 |
| 项目配置回退 | 规则、技能正文/开关、Profile 展开的有效配置、项目 MCP 锁定版本/配置、工具绑定 | 预览 → 验证当前安全策略 → 回退前备份 → 全目标重新编译/事务恢复；共享定义转为项目覆盖，不改变其它项目 |
| 撤销回退 | 上一次回退前的已应用配置及已保存未应用草稿 | 走相同验证与事务；恢复旧应用结果后还原草稿，其待应用状态重新计算 |
| 本体降级 | 经签名验证的旧二进制与匹配 schema 的升级前备份 | 先检查恢复兼容性，不能让旧程序直接读已升级的数据；独立于项目回退 |

- 每次 apply、规则导入、依赖更新与 schema 升级前自动备份。配置快照保存上次成功应用状态，同时另存已保存草稿；新机目录/凭据重新绑定，不把旧绝对路径和旧授权直接恢复为有效。
- 回退预览绑定当前规范源、已应用状态、目标哈希、快照摘要、适配器版本与策略摘要。确认后变化则 `PLAN_STALE`。回退不能恢复更宽权限、降低信任门槛或恢复旧授权绕过当前策略。
- 插件安装产物按版本/摘要并存；项目锁引用旧产物，不全局降级其它项目。缓存缺失时先从可信来源恢复并重新验证；不可得返回 `SNAPSHOT_DEPENDENCY_MISSING`，保留当前配置，不能虚报回退成功。清理被快照/恢复事务引用的版本前提示会损失哪些恢复能力。
- 回退不默认删除或覆盖知识正文、会话、审计、凭据，也不改变 Git 推送状态。知识正文恢复必须是独立、有范围预览的恢复操作；core/schema 降级遇到无法兼容的新数据时保存副本并阻断，不丢掉升级后的数据。
- 快照规范源与原生文件字节备份分开：前者可重新编译，后者用于失败恢复。原生用户配置备份可能含用户自填密钥，存 Local Root、限制 ACL、禁止进入同步/普通导出。备份保留期可配置，未完成恢复事务与最近成功版本不可自动清理；用户固定的恢复点需显式解锁才清理。
- 成功回退记录新恢复节点而不是删历史；失败与自动恢复结果也记审计。启动自检在任何新写入前恢复未完成事务，无法安全恢复时提供 `aidock doctor --json` 的事务 id/目标/备份位置及手工恢复指引。

当前 Demo 演示的是内存快照、模拟目标恢复、旧版本选择和撤销回退；不是磁盘备份、进程中断恢复或二进制降级的实现证据。

### 10.16 模板库

从经过验证的技能 / 规则骨架快速创建新条目，降低从零编写成本。

### 10.17 插件市场

浏览、搜索、安装来自外部的插件。**这是工作区里唯一需要联网的界面**，因此数据源与离线行为必须写清。

**数据源（聚合，不自建）**

| 来源 | 提供什么 | 安装类型 |
| --- | --- | --- |
| 官方 MCP Registry | MCP 服务器条目 | 权威来源，优先 |
| npm | 以 npm 包形式发布的插件 | `package` |
| GitHub | 仓库形式的插件与技能 | `git` |
| 团队 / 个人索引（可选） | 私有仓库里的插件清单 | 见 [16.2](#162-从个人工具到可分享生态) |

> **不建自己的评分体系**：市场展示的「评分」「下载量」「Stars」**全部是聚合外部数据**（Registry / npm / GitHub），AIDock **不自建评分**——避免制造第二套信任信号，与 [9.1](#91-插件安装必须先审计后运行) 的信任等级各司其职。

> **协议与字段属后续选型**：各来源的取数方式（官方 Registry 的 API、npm registry API、GitHub REST / GraphQL）**本文档不规定具体协议**，只约定：**只读、可缓存、失败可降级**。另注意：**「评分」并非所有来源都有**（npm 有下载量、GitHub 有 Stars，Registry 未必有评分字段）——**取不到就隐藏该列**，绝不用本地数据补造。

> **取数通道：由 core 后端代理，浏览器不直连。** 市场页面通过 `127.0.0.1` 的控制台服务请求 **core**，由 **core 发起对外 HTTP 请求**——浏览器直连会绕过 Local Root 缓存，且受 CORS 限制。core 自身的出口请求**也记审计**（与 [9.2](#92-mcp-服务器进程隔离与凭据隔离) 对 MCP 出口的管控同级）。

**本地缓存与离线**

- 市场列表与索引**缓存在 Local Root**（符合 [13.3](#133-core-的本地状态层)：可清理、可重建、不承诺查询性能）。
- **离线时展示缓存结果并标注"数据可能过期"**，不阻塞、不报错、不清空。
- 缓存过期且仍无网络时**继续沿用旧缓存**，只在详情页提示"无法确认最新版本"。

**界面要素**

| 要素 | 说明 |
| --- | --- |
| 分类与标签 | 按类型（MCP / Skill / Hook / CLI）与场景筛选 |
| 搜索 | 匹配名称 / 作者 / 功能 / 标签，带搜索联想 |
| 排序 | 相关度 / 下载量 / 评分 / 最近更新 |
| 布局 | 卡片 / 列表双视图 |
| 信任等级徽章 | 见 [9.1](#91-插件安装必须先审计后运行)——点进详情前即可按可信度筛选 |
| 收藏 | **本地行为**，存 Local Root（`favorites.json`），**不进 Git** |
| 对比 | 并列比较 2–3 个插件的权限 / 依赖 / 信任等级 |
| 版本历史与依赖 | 见 [10.4](#104-插件详情页) |

**安装路径统一**：无论从市场、URL 还是团队索引进入，**都走同一套安全门与安装弹窗**（见 [9.1](#91-插件安装必须先审计后运行) / [11.1](#111-插件安装弹窗三件事一眼读完)）——**不存在"绕过安全门的快捷安装"**。

- **归属**：**core**（界面 + 聚合 + 缓存）；市场**自身不托管任何插件内容**。

## 11. 用户体验设计：从"能装"到"装得安心、用得顺手"

### 11.1 插件安装弹窗：三件事，一眼读完

核心原则：用户打开安装弹窗时，只想知道三件事——**这是什么、它会做什么、装之前要注意什么**。避免"文字层级反了"：最该读的插件描述用小灰字，数据口径说明反而更显眼。

```text
┌ 安装 cgh ─────────────────────────────────┐
│ cgh · v0.3.2 · ↓162.5k/近30天 · ★8k      │
│ [代码记忆]  🛡️ 信任等级 L3 · 87              │
│                                            │
│ 将代码库解析为图结构，通过MCP暴露给AI，     │
│ 支持符号级查找，减少40-60%上下文token。     │
│                                            │
│ ⓘ 它会做什么 ›                              │
│   # 安装命令 ›                              │
│                                            │
│ ┌ 安装前请注意 ──────────────────────────┐ │
│ │ ⚠ 首次索引大型项目需要几分钟。           │ │
│ └────────────────────────────────────────┘ │
│                                            │
│ 社区第三方插件，构建脚本默认不运行。        │
│                          [取消] [确认安装]  │
└────────────────────────────────────────────┘
```

排版规则：

- **常态安静，罕见才打扰**：第三方声明是每个插件都有的常态，用普通小字陈述即可，不要带警告图标。
- 只有真正罕见/高危的事项（如超出公示范围的权限）才使用警告样式。
- **信任等级与分类标签同行**：等级徽章（`L3 · 87`）紧跟在分类标签后展示，不另起大块；**仅当低于默认门槛（L2）时**才升级为警告样式，并把"确认安装"改为二次确认（见 [9.1](#91-插件安装必须先审计后运行)）。

### 11.2 批量操作与一键更新

真实痛点：装了很多插件后，一个个搜索、更新非常麻烦；每次安装/更新后页面整体刷新、闪回已安装界面，又需要重新切换到插件市场查找。

AIDock 必须支持：

- **一键更新全部**：在插件列表顶部提供"全部更新"按钮。
- **更新通知**：已安装插件有新版本时，在卡片上显示角标，而不是让用户自己去市场比对版本号。
- **原地刷新**：安装/更新后不刷新整个页面，只更新对应卡片的状态。
- **批量启用/禁用**：选中多个插件后批量操作。

### 11.3 首次激活引导

首次引导应帮助用户完成一次能验证的配置闭环；当前没有本产品留存实验数据，不使用未经来源核验的百分比作为设计依据。

首次启动引导流程（`aidock config` 首次打开控制台时触发）：

1. 检测本地已安装的 AI 工具（Claude Code、Cursor 等），展示检测结果。
2. 推荐一个"快速开始" Profile，只包含 2-3 个最通用的插件（如 cgh + 一个基础 MCP）。
3. 预览授权并应用，展示“配置已生成”；实际工具发现/新会话验证完成后才显示对应工具已就绪。
4. 引导用户完成第一次智库检索或第一次会话记忆保存，让用户立即感受到价值。

**检测为空时（一个已知 AI 工具都没检测到）**

引导**不中断**，改走兜底路径：

1. 说明"未检测到已知的 AI 工具"，并提供**手动指定配置文件路径**的入口（如"我的规则文件在 …"）。
2. 不强制选定目标：**允许只完成"个人层"初始化**（数据根 + 空 Profile），并明确告知"稍后可随时 `aidock config` 再配置"。
3. **跳过 ≠ 报错**：任何一步跳过都**保留已完成的部分**，不要求从头再来。

## 12. 性能：智库的索引策略

> **非 core 职责**：本章策略属于**记忆 MCP 的实现**（见 [7.5](#75-记忆能力与记忆-mcp)）。core 只需为它提供后台任务编排与进度展示，**不实现索引本身**。

Tree-sitter 解析和向量嵌入是 CPU 密集型操作。对于大型项目（100 万行以上），首次索引可能耗时数分钟。策略：

| 策略 | 说明 |
| --- | --- |
| 增量索引 | 只解析变更文件，而非全量重建（Tree-sitter 增量解析天然支持） |
| 后台索引 | 在后台线程/进程运行，控制台不阻塞，显示进度条与预估时间 |
| 索引范围可配置 | 允许排除 `node_modules`、`vendor`、构建产物等目录 |
| 延迟嵌入 | 代码片段先存入 SQLite，向量嵌入在空闲时批量生成，不阻塞摄取 |
| BM25 优先 | "找某个函数/类名"用 BM25 全文搜索即可，向量检索仅在语义查询时触发 |

**检索分层（默认轻量）**

- 默认只用 **BM25 + 向量**，用 RRF 融合两路结果。
- **cross-encoder rerank 与知识图谱遍历默认关闭**，作为可选项开启——本地 CPU 上它们是交互延迟的主要来源。
- 图谱查询默认走 SQLite 邻接表，不启用 Neo4j。

## 13. 技术选型

### 13.1 AIDock core（已定）

| 模块 | 推荐方案 | 理由 |
| --- | --- | --- |
| CLI / 引擎 | Go | 单二进制分发、交叉编译简单；标准库自带 HTTP 服务，静态资源用 `embed` 打包 |
| 界面载体 | 随 CLI 启动的本地 Web 控制台（Go 二进制 `embed` 静态资源）；前端原生 HTML/CSS/JS，工程化时可选 Vue | 不需要原生 GUI 壳；分发仍按 §20.2 验签，原型演进须补正式安全/浏览器验收 |
| 配置格式 | 规范源使用 YAML（project/profile/mcp/plugin/副本组）；技能正文为 Markdown；原生 JSON/TOML 由适配器输出 | 与 §19 示例统一，不同时建立两套可编辑规范源 |
| 同步后端 | go-git | 不依赖用户安装 git CLI |
| 密钥存储 | Go keyring（`zalando/go-keyring`，对接 Windows Credential Manager 等） | 加密存储，密钥轮换支持 |
| 进程隔离 | §9.2 的 OS 强制能力矩阵；首期 Windows AppContainer/ACL/broker 候选，Job Object 仅负责进程和资源 | 不依赖容器；运行时兼容性须先做原型，不以受限令牌单独证明沙箱 |
| 会话摄取 | 会话源适配器 + MCP 主动上报 | 统一为规范事件流，来源见 [7.5](#75-记忆能力与记忆-mcp) |
| 依赖扫描 | Snyk 等 | 定期扫描 Go / JavaScript 依赖 |

> **core 不含数据库**：记忆的存储归记忆 MCP（见下）；但 core 允许持有**状态文件**，判定判据见 [13.3](#133-core-的本地状态层)。

### 13.2 记忆能力（由记忆 MCP 提供，非 core 职责）

**已定（2026-10-10）**：AIDock core **不实现记忆引擎、不持有数据库**。记忆能力由**独立的记忆 MCP 服务器**提供（优先复用现成实现，如 cgh / Skopus），core 只做集成（见 [7.5](#75-记忆能力与记忆-mcp)）。

core 侧需要的部分：

| 模块 | 推荐方案 | 理由 |
| --- | --- | --- |
| MCP 注册与编排 | `mcp.yaml` 配置 + 生命周期管理 | 与其它 MCP 走同一套注册 / 隔离 / 审计（见 [19.4](#194-mcpyaml) / [9.2](#92-mcp-服务器进程隔离与凭据隔离)） |
| 记忆 MCP 本体 | 复用现成实现（cgh / Skopus 等），**不自研** | 避免范围爆炸；core 保持纯 Go 单二进制、无数据库 |

**可选后续：自研 CogniBox（不阻塞主线）**

若日后自研，**也应做成独立 MCP 服务器**（不内嵌 core），实现语言可自由选（Python 生态在检索侧更成熟）。届时可参考：

| 模块 | 参考方案 |
| --- | --- |
| 本地数据库 | SQLite（bundled，含 FTS5）+ sqlite-vec |
| 代码解析 | Tree-sitter（只内置常用语法子集） |
| 知识图谱 | SQLite 邻接表（默认）/ Neo4j（可选） |
| 本地嵌入 | 内置 ONNX 小型模型（如 bge-small）；Ollama 可选 |
| 检索增强 | RRF 融合（BM25 + 向量）；cross-encoder rerank 可选 |

### 13.3 core 的本地状态层

core **不含数据库**，但**允许持有状态文件**——两者不矛盾。为避免每新增一种状态就重开一次"这算不算数据库"的辩论，这里给出**可判定的三条硬约束**：

| # | 约束 | 含义 |
| --- | --- | --- |
| ① | **结构化状态/日志段 ≤ 10 MB，按 id 命名或分段，线性遍历足够** | 不建立持久化检索索引或关系查询引擎；按 id 引用和临时聚合不属于数据库 |
| ② | **普通缓存可重建/清理，受保护状态按保留契约管理** | 审计、注册/覆盖、共同基线、恢复事务及快照不是可随意删除的缓存 |
| ③ | **不承诺检索引擎性能** | Local Root 同时有缓存和恢复数据；需语义/图/大规模索引的能力迁给 MCP |

**违反任意一条，就必须迁出 core，做成独立的 MCP**（正如记忆能力所做的，见 [7.5](#75-记忆能力与记忆-mcp)）。

当前 core 持有的状态文件：

| 状态 | 位置 | 性质 | ② 可重建 / 可清理 |
| --- | --- | --- | --- |
| 注册/副本绑定/本机覆盖 | Local Root | 按稳定 id 的扁平记录 | ❌ 需备份；重扫目录不能自动还原身份/覆盖 |
| 共同基线与删除 tombstone | Local Root | 按作用域/副本/条目的确认版本 | ❌ 需保留；丢失进入未知基线，不能按时间猜 |
| 事务/快照清单与原始字节 | Local Root | 恢复资产，按事务/快照引用 | ❌ 未恢复事务、最近成功版本及固定恢复点不可自动清理 |
| 审计日志 | Local Root | 追加日志（哈希链） | ❌ 见下方例外 |
| 指标日志 | Local Root | 追加事件流 | ✅ 可重建 / 可关闭 |
| `sessions/` | Local Root | 结构化文件 | ✅ 可清理 |
| 编译报告归档 | Local Root | 单次产物 | ✅ 可清理 |

> 结构化清单与日志段遵守大小上限；原始字节备份、技能/安装产物、Git 快照对象是按摘要引用的恢复资产，不是查询状态，不受 10 MB 单段限制。需在 plan 中预检单项上限、总磁盘预算与备份可用性；空间不足在正式写入前阻断。任何清理必须检查事务/快照/基线引用，不能因 Local Root 名字或文件年龄就删恢复资产。

> **红线在哪里**：**"有搜索 / 排序"不是分界线，"需要索引"才是。** 会话少时遍历 JSON 即可；一旦某种状态需要索引、跨文件查询或语义检索，它就不再是"文件"而是"数据库"——届时应提示用户**清理旧数据**，或把该能力**迁给专门的 MCP**，**而不是在 core 里偷偷引入索引**。

## 14. 实施路径

基于"个人沉淀 / 多项目个性化 / 多 AI 可用 / 项目级技能管理"四个诉求，**先做"项目空间 + 技能管理"**——这是四个诉求里最核心的骨架：项目空间立住了，个人沉淀有地方放，多 AI 输出有源头，技能管理有归属。

| 阶段 | 重点 | 交付物 |
| --- | --- | --- |
| 第一阶段 | 项目空间 + 技能管理 + 多副本底座 | 两个治理适配器、静态/分层诊断、手动副本同步、回退/恢复及安全底座 |
| 第二阶段 | 记忆能力集成 | 接入现成记忆 MCP、权限 / 隔离 / 审计、项目级检索作用域 |
| 第三阶段 | 插件市场 + 技能分发 | 市场/远程来源安装、固定版本更新；全局管理与继承底座已在第一阶段 |
| 第四阶段 | 同步迁移 + MCP 网关 | Git 同步、新电脑 bootstrap、core 自身能力经 MCP 暴露 |
| 第五阶段 | 自动沉淀 + 多 AI 并行 | 会话自动摄取、多工具同时同步、项目类型自动识别 |

各阶段展开：

### 第一阶段：项目空间 + 技能管理（骨架）

- 定义 `.aidock/` 项目目录结构与规范配置格式。
- 实现 §19.6 的 Profile 继承、项目共享覆盖、副本本机覆盖与临时会话叠加规则。
- 全局/项目资产与继承的管理；自定义技能盘点、创建、本地导入、完整包编辑、依赖/兼容、覆盖/分叉、改名/删除与源级恢复（§7.3 / §19.5）。
- 适配器把项目配置编译到 Claude Code 与 Codex CLI；支持版本由实施证据白名单决定。
- 控制台主导航以项目为中心。
- 同步建设会话启动器、主平台隔离能力探测、安全门、凭据注入、审计、原生字段所有权与事务恢复；这些是首期底座，不等待市场/记忆阶段补建。首两适配器需在阶段 1 入口固定目标及支持版本，当前示例不代表已验证兼容。
- 同期完成五副本的作用域/绑定、外部源桥接预检、共同基线/冲突、整批恢复与批次回退，以及 §20.8 的分层生效检查。

阶段 1 内顺序为 **1A 只读盘点/能力原型 → 1B 技能源与版本事务 → 1C 两工具应用/恢复 → 1D 五副本桥接/发布 → 1E 最小控制台与联合验收**，每步的 CLI 有等价管理入口。事务/备份在 1B 第一次源写入前完成；1A 的隔离和适配探针先在测试夹具/独立临时目录验证，不能拿真实项目试写代替原型验收。精确门槛见开发计划；没有通过 1D 不开放五副本批量写入。

### 第二阶段：记忆能力集成

- 选定并接入一个现成记忆 MCP 服务器（如 cgh），纳入注册表。
- 记忆 MCP 的权限清单过安全门，写操作需授权 + 记审计。
- 记忆 MCP 按 [9.2](#92-mcp-服务器进程隔离与凭据隔离) 的模型隔离运行。
- 记忆的存储分层与"按项目隔离检索"，由 AIDock 通过检索作用域配置管控。

### 第三阶段：插件市场 + 技能分发

- 在首期全局技能库/继承之上增加来源搜索、远程导入和固定版本更新；不重复建设资产管理。
- 接入官方 MCP Registry、npm、GitHub 搜索，从市场安装插件。
- 卡片展示下载量、评分、来源。

### 第四阶段：同步迁移 + MCP 网关

- Git 后端同步 Knowledge 权威正文 + Capability 配置；按 §7.9 的 id/数量/哈希清单验证迁移，索引/凭据/会话/日志不随行。
- 实现 `push`、`pull`、`bootstrap` 命令，凭据引用随配置、值不导出。
- 实现 MCP 网关，把 **core 自身能力**（插件 / Profile / 技能管理）暴露给 AI 客户端；**记忆类工具由记忆 MCP 自行暴露**，不经该网关（见 [7.6](#76-mcp-网关)）。

### 第五阶段：自动沉淀 + 多 AI 并行

- 会话自动摄取（自动提取 + 人工确认队列）。
- 多工具同时同步，项目类型自动识别与 Profile 推荐。
- 引入 LLM 进行知识整理，把零散片段编译成结构化 Wiki 页面。

> 安全能力（安全门、进程隔离、凭据隔离）不是独立的"第六阶段"，而应作为第一阶段的底座同步建设——第四阶段的同步迁移、MCP 暴露都依赖它。

## 16. 社区与长期发展

### 16.1 插件市场的"信任信号"

参考 Chrome Web Store 的做法（评分聚焦近期评价、设"精选"徽章突出高质量扩展），插件市场应展示：

- **近 30 天下载量**（而非累计下载量，后者容易被早期刷量）。
- **最近更新日期**（超过 6 个月未更新标记为"可能不维护"）。
- **兼容性标签**：已测试的 AI 工具列表。
- **安全审计徽章**：通过安全门检查的插件获得标识。

### 16.2 从个人工具到可分享生态

在 Profile 版本化与分享能力之上，构建 **Profile 市场**：用户发布自己的"前端开发 Profile""数据分析 Profile"，包含一套经过验证的插件组合和配置。这比单个插件分享更有价值，因为它打包了经过实践检验的能力组合。

### 16.3 开放标准跟踪

MCP Bundle 格式（`.mcpb`）和 Agent Plugins 标准（`SKILL.md` + `mcp.json`）正在成为事实标准。AIDock 的插件描述格式应**兼容这些标准，而非自创封闭格式**。当用户从其他工具迁移时，能直接导入现有的 MCP 配置和 Skill 定义，降低迁移摩擦。

## 17. 风险与挑战

| 风险 | 说明 |
| --- | --- |
| 兼容性 | 各 AI 工具配置格式频繁变化，适配器需持续维护。 |
| 密钥安全 | 加密存储和脱敏导出必须可靠，避免凭据泄露。 |
| 供应链安全 | 插件来源不可信、权限越界、更新投毒；须由安全门与进程隔离兜底。 |
| 性能 | 大型代码库的 Tree-sitter 索引和向量检索需要优化。 |
| 生态变化 | MCP、Skills、插件标准仍在演进，需保持抽象层稳定。 |
| 命名冲突 | **产品名 AIDock** 与**命令名 `aidock`** 是两个标识，需**分别**检查 GitHub / npm / 域名 / 商标占用；`aidock` 是更常见的英文组合，**冲突概率高于原长名**，须优先查。 |
| 用户体验 | 插件配置项过多时，需提供合理默认值和引导。 |
| 隔离能力差异 | OS 原生隔离手段在各平台能力不一（Windows 受限令牌 / Job Object、Linux namespace），需提供逐级降级路径。 |
| 项目边界泄漏 | 项目记忆若检索串扰，会把 A 项目内部决策暴露给 B 项目；需严格作用域控制。 |
| 指令文件混编 | `CLAUDE.md`、`AGENTS.md` 含用户手写内容，托管区块需准确识别边界，避免误覆盖或漏更新。 |

## 19. 规范定义（Schema 与契约）

> 本章把此前散落的"示意"钉成契约。**只定义结构与规则，不涉及实现。**
>
> Schema 版本按文件类型独立管理：`project.yaml`、`mcp.yaml` 等保留 v1；新增 `skills.yaml` 为 v1，`profile.yaml` 在 v0.24 升至 v2，以稳定技能 id 代替名称引用。机器可读 Schema 与 golden 示例须在阶段 0/1 落地。增删字段不能默默改语义：须记录兼容性、更新相应 schema 版本并提供迁移（§20.2）。外部原生格式仍由其工具拥有，不能因 AIDock Schema 更新而重写未知字段。

### 19.1 跨平台路径变量

规范源中**禁止写绝对路径**，只允许变量或相对项目根的相对路径。

| 变量 | 含义 | Windows 映射 | macOS / Linux 映射 |
| --- | --- | --- | --- |
| `${HOME}` | 用户主目录 | `%USERPROFILE%` | `$HOME` |
| `${PROJECT}` | 当前项目根目录 | 同 | 同 |
| `${DATA}` | 数据根（Config Root） | 解析后路径 | 同 |
| `${LOCAL}` | 本机根（Local Root） | 解析后路径 | 同 |
| `${OS}` | 平台标识 | `windows` | `darwin` / `linux` |
| `${ENV:NAME}` | 引用环境变量 | 同 | 同 |
| `${SECRET:NAME}` | 引用密钥库条目（**不落盘**） | 同 | 同 |

规则：

- `${HOME}` 是跨平台抽象——**Windows 上映射到 `USERPROFILE`**（Windows 没有 `HOME`），否则"路径变量化"在 Windows 上是空话。
- 路径分隔符在规范源中统一用 `/`，运行时按平台转换。
- 未解析的变量在 `plan` / `apply` 时**报错阻断**，不得静默留空或猜值。

### 19.2 project.yaml

```yaml
# .aidock/project.yaml —— 项目元信息
schema_version: 1
id: 01a12f70-4688-73a1-b4ee-14043eb3b3dd # 初始化一次生成的稳定 UUID；与目录/名称分离
name: My Project
stack: [typescript, react]        # 检测到的技术栈（驱动 Profile 推荐，见 7.1）
profile: 前端项目                  # 引用的 Profile（可选；空则只继承全局默认）
group: 前端工作流                  # 所属项目分组（可选；仅组织视图，见 10.1）
ai_tools: [claude-code, codex-cli] # 首期治理输出目标；其它工具须另有支持证据
rules_sync_mode: prompt           # v1：unidirectional(默认) | prompt；bidirectional 未开放
created: 2026-10-09
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 逻辑项目稳定 UUID，初始化一次后随配置迁移；改名/移目录不变。显式加入同项目副本保留 id、新建 copy id；克隆成新独立项目新建 id。不能自动重绑原会话（§7.12） |
| `name` | | 展示名 |
| `stack` | | 技术栈标签，用于推荐 Profile |
| `profile` | | 引用的 Profile 名 |
| `group` | | 所属项目分组名。**仅组织视图**，不参与配置继承，也不改变技能作用域（见 [10.1](#101-主导航以项目为中心)） |
| `ai_tools` | | 本项目启用的 AI 工具集合 |
| `rules_sync_mode` | | v1 仅 `unidirectional`（默认）/ `prompt`；`bidirectional` 返回不支持，显式导入不改变单向规范源原则 |
| `created` | | 创建日期 |

### 19.3 profile.yaml

```yaml
# .aidock/profile.yaml（项目级）｜ ~/.aidock/profiles/<name>.yaml（用户级）
schema_version: 2
name: 前端项目
description: 适用于 React / Vue / Next.js 项目
extends: 默认开发                  # 继承的用户级 Profile（可选，构成继承链）
plugins:
  enable:  [cgh, skopus, figma-mcp]
  disable: [browser-automation-mcp]  # 显式禁用从上层继承来的插件
skills:
  enable:  []                      # 添加时写 skills.yaml 中的稳定技能 id
  disable: []
  pins: {}                         # id → 精确 revision，由 skill plan 生成/选择
mcp:
  enable:  [figma-mcp]
  disable: []
config_overrides:
  cgh: { languages: [typescript, javascript] }
rules:                            # 规则条目：默认追加（上层在前、项目在后）
  - "优先使用函数式组件"
  - "遵循项目 ESLint 配置"
rules_override: false             # true = 整体替换上层规则列表（见 19.6）
```

说明：

- 项目级 `profile.yaml` 即 [7.1](#71-项目空间核心抽象) 的**项目共享覆盖层**；某层“未提及”= 继承上层，`disable` 用于显式关闭继承项。
- 最终生效配置 = 全局默认 → `extends` 链 → 项目共享覆盖 → 副本本机覆盖 → 临时会话，合并规则见 [19.6](#196-技能与配置的合并算法)。
- v2 的 `skills.enable/disable` 引用稳定 id，不随技能改名变化；`skills.pins` 为 id→精确 revision 字典，按层逐 id 覆盖。每个最终启用项必须解析到一个已有完整包 pin；未指定可继承上层 pin，仍缺失时阻断，不能默认取最新。同 id 只允许显式基础/覆盖链，歧义阻断；禁用不删除其已固定版本。
- v1 名称引用只供兼容读取/迁移预览：在当前 project/scope 来源链唯一解析后展示 id/revision 映射，用户确认才写 v2；缺失/歧义/曾靠同名自动覆盖的项必须协调。未完成迁移的 Profile 不自动 apply，原 v1 文件和完整包备份保留。除 skills 的稳定引用与 pins 外，其它 Profile 字段语义保持不变。

### 19.4 mcp.yaml

```yaml
# .aidock/mcp.yaml —— 项目专属 MCP 服务器
schema_version: 1
servers:
  - name: figma-mcp
    source: { type: npm, package: figma-mcp, version: 0.8.4 } # 示例版本，待安装验证
    transport: stdio              # stdio | sse | http
    entrypoint: "node_modules/figma-mcp/dist/index.js" # 相对锁定安装目录，不是客户端直接执行命令
    tier: 1                       # 隔离等级 0 | 1 | 2（见 9.2）
    enabled: true
    permissions:                  # 与 plugin.yaml 同一契约（见 7.2）
      fs:  { paths: ["${PROJECT}"], mode: ro }
      net: { allow: ["api.figma.com"], default: deny }
      exec: false
```

> `permissions` 与 `tier` 是安全门与隔离判定的输入；声明值不得低于安全门按 `permissions` 算出的下限（见 [8.1](#81-必须钉死的不变量不可被插件-patch-掉)）。

以上是规范源，不是原生客户端配置。适配器输出 `command: "aidock"`、`args: ["mcp", "exec", "--project", "<stable-id>", "--copy", "<copy-id>", "--plugin", "figma-mcp"]`；启动器根据 `plugins.lock` 校验本地运行时/入口/产物摘要。v1 治理接入只支持 stdio；SSE/HTTP 声明在实现前返回 `UNSUPPORTED_TRANSPORT`，不能跳过中继直连。

### 19.5 SKILL.md

```markdown
---
name: api-conventions
description: 本项目的 API 设计与命名约定
---

# API 约定
（正文：指令及相对引用；保留技能包结构，由适配器输出到已验证的发现入口）
```

**原生文档与治理元数据分开**：`SKILL.md` 保留来源工具格式，其 `name` 是原生名称，不是资产主键。不向原文件强加 scope/version/targets/permissions；AIDock 属性放 `skills.yaml`。来源独有 frontmatter 由对应桥接/适配器解析并保留；无法表示的字段明确报告，不把所有技能默默展平成规则。例中是最小源样式，工具侧必填/限制以精确版本证据为准。

**技能索引 `skills.yaml`（schema_version: 1）**

全局索引在 `<Config Root>/skills.yaml`，项目索引在项目配置目录；副本覆盖的索引/包位于 Local Root 的对应绑定，禁止随共享索引同步。external-source 的路径映射保存在治理索引/绑定中，原目录继续权威，不复制出第二份可编辑源。

| 字段 | 契约 |
| --- | --- |
| 顶层 `schema_version` / `owner` / `scope_id` / `skills` | 版本 1；owner 为 `global` 或逻辑项目 UUID；scope_id 为登记的作用域；skills 是技能记录数组，id 在 owner/scope 内唯一。copy 和机器绝对路径只在本机绑定中 |
| `id` / `native_name` / `display_name` / `tags` | 初始化一次的 UUID；原生输出名称；可选展示名/检索标签。同 id 跨 copy 延续，目录移动/改名不重建 id；同名独立资产不自动合并 |
| `source` | `mode: owned | external-source | plugin`；登记相对源路径、原格式和来源引用。source path 相对相应 Config Root/项目配置根；外部路径经作用域绑定解析。插件附带技能使用固定 plugin id/锁摘要/包内路径，只读；不得指向生成镜像或未授权目录 |
| `version` / `revision` | version 是可选人工版本标签，不用于选边；revision 是 `sha256:` 加 64 位十六进制的完整包/语义摘要。标签相同但摘要不同仍是不同修订，时间戳不参与比较 |
| `package_format` / `files` | 格式 id/版本；每个文件的规范相对路径、字节数、原始字节 SHA-256 和 text/binary 类型；必须含 SKILL.md。文件集合属于审核包清单，不是整个目录递归复制通行证 |
| `dependencies` | skills 用 owner/scope/id + 精确 revision；plugins 用 plugin id + 安装锁摘要；runtime 用版本约束和明确入口；project_files 用项目相对路径声明运行时所需文件。区分 required/optional；必需项缺失、环、摘要不符阻断，optional 缺失需声明禁用的能力，不自动猜依赖 |
| `compatibility` | 平台、工具 id/版本约束、项目技术栈和声明的配置/标记文件条件；版本范围是作者声明，开放写入仍需支持白名单。无法验证的项目条件为 UNKNOWN，不根据同 Git remote 或目录数量判兼容 |
| `requirements` | 声明脚本入口、文件读写、网络及凭据引用需求，用于预检/当前策略授权；不保存凭据值、不代表 external AI 命令已受 OS 隔离。未知执行需求显示未验证，不自动升级信任等级 |
| `base_source` / `base_revision` / `upstream` | 同 id 的高层覆盖必须登记上层 owner/scope/id 与固定 base_revision，不能仅凭同 id 认定覆盖；基础包必须可取得。上层实际 pin 与 base_revision 不符返回 BASE_STALE，先协调再应用；只发布新候选不使基础失效。独立分叉的新 id 可带 upstream 的 owner/scope/id/revision，不字段级合并或静默覆盖自定义修改 |

启用状态仅存在 Profile/本机/临时层，不与包正文混存。索引记录的当前候选 revision 与已应用/项目引用版本分开：引用固定版本，全局库编辑只更新候选；项目采纳/编辑更新包与本层 pins 纳入同一源事务，仍待原生 apply。owned 模式在所属配置根的技能修订库保留所有被引用的不可变完整包；被项目固定引用的旧全局版本也必须能随导出携带。external-source 保存后得到新候选，旧批准包由受保护快照保留；外部生成器自行写入的动作只检测和报告，不声称可阻止或自动回退。

桥接 apply 的暂存输入必须与选择的 revision 一致；当前外部源与 pin 不一致时先显式采纳新版本或恢复原源，不能让外部生成器生成当前内容却报告旧固定版本已应用。迁移/导出清单须带每个被引用的完整技能修订（含覆盖基础和桥接旧包）；包不可取得时报告缺依赖并阻断，不能只导出本机快照路径。直接拷贝 Config Root 不会凭空携带外部项目源，外部源需单独携带/重绑定或使用完整迁移包。

**包闭合、摘要与平台规则**

- 包含 SKILL.md、references/scripts/assets 和明确纳入的文件；默认排除 `.git/`、缓存、环境目录、生成物、凭据文件。导入展示纳入/排除项，疑似密钥阻断并脱敏；无权威源的镜像只能经“升格为新源”独立迁移预览，不直接 adopt。
- 文件路径统一 `/`；拒绝绝对路径、`..` 逃逸、Windows 设备名/大小写重复、junction/symlink/reparse 越界、归档路径穿越与超出声明容量/文件数的包。v1 不跟随包内链接；确需内容时由用户先物化成普通文件并重新审核。文本按工具格式处理，二进制保持原字节。
- 本地 Markdown 引用/声明文件必须存在；项目外运行依赖须明确为 project_files 等受控依赖并在每个目标校验，不把整个项目打进技能包。远程引用不自动下载；脚本动态依赖的静态分析只提供有限证据，无法确定时标 UNKNOWN 并列缺口。
- files 按规范路径排序；文件哈希基于原始字节，换行/二进制变化都产生新 revision。revision 绑定文件清单及 native_name、格式、依赖、兼容和执行需求的规范化语义；不含自身、展示名/标签、时间戳、本机绝对路径和生成证据。规范化键序/编码/空值规则由机器 Schema + golden 固定，不能不同机器算出不同 revision。
- 包内容/依赖/执行需求变化重新预检；授权绑定完整 revision 和权限/策略摘要，不沿用旧包授权。技能资产没有插件信任证据时标未验证，不因为“项目自定义”自动给 L2；纳管/分发审查记录不能当作执行安全证明。

**技能变更 CLI 与事务**

`skill plan <action>` 使用结构参数/`--file <descriptor>`，明确 owner/project/scope/copy、层、id 与基础 revision；create/import 允许新 id，其余 action 必须引用现有身份。edit/rename/remove/override/fork/update/enable/disable 都生成相同形态的计划，输出包 diff、引用/依赖影响、目标冲突、授权和恢复清单。`skill apply --plan` 重新校验来源、引用、目标、策略与草稿摘要，先持久化完整包和索引/Profile 原字节，再提交源事务；失败或中断走 §20.1 的恢复。顶层 apply 只编译已保存的候选，不能隐含替用户保存未提交编辑。

删除定义需先解除所有已登记的 Profile/依赖/覆盖引用，不能自动级联删依赖。删除写 tombstone，跨副本传播单独确认；未登记/离线引用范围未知时只允许停用/退役并保留修订，不自动物理清理。旧 revision、基础包和恢复点被引用时禁止清理。改原生名清除旧托管产物与生成新产物属于后续原生 apply 的同一事务；不碰同名非托管文件。撤销源编辑与回退已应用配置分开显示，均可再次撤销，不回退会话、记忆或审计。

### 19.6 技能与配置的合并算法

**优先级（高 → 低）**：临时会话 → 副本本机覆盖 → 项目共享覆盖 → `extends` 链 → 全局默认。技能正文覆盖以完整包为单位，开关与配置使用相同层顺序。没有本机覆盖的项目保留原三来源行为。

冲突解决（**确定性**，保证结果可复现）：

| 情形 | 规则 |
| --- | --- |
| 同 id 技能覆盖 | 按稳定 id 和显式 base_source/base_revision 关系解析；高层整包覆盖低层，**不做正文/附件字段级合并**；最终启用项解析到精确 pin，包与开关来源分别展示 |
| 同名不同 id | 名称只用于原生输出槽位，不自动认作覆盖。同一工具/copy 槽位碰撞阻断，用户显式选择资产或改名；跨 scope 不合并。旧名称覆盖关系必须先迁移为明确身份/基础版本 |
| `extends` 链 | 链式解析，**子级覆盖父级**；检测到环即报错 |
| 插件 `enable` / `disable` | 全局默认 → `extends` 链 → 项目共享 → 本机 copy → 临时会话开关（最高） |
| `skills.pins` | 每层按稳定 id 覆盖精确 revision；pin 指向的完整包必须存在且满足覆盖关系/依赖/当前策略，不因为 id 在 enable 中就自动取索引最新候选 |
| 同层开关冲突 | `plugins` / `skills` / `mcp` 同一 id 同时出现在 enable/disable 时阻断，报 `AMBIGUOUS_OVERRIDE`；不暗定某一方优先。数组内部去重，未知 id 报错 |
| `config_overrides` | 字典按键递归合并；标量（含 null）整体替换；数组整体替换，空数组即清空。删除字段只用显式 `config_remove` JSON Pointer 列表；不能把 null 同时解释成删除 |
| `rules` 文本列表 | v1 不设“同名规则”语义。默认按继承链顺序追加，不按文本重排；`rules_override: true` 整体替换上层列表，空列表即清空；不隐式去重 |

- 层按继承链顺序执行；集合输出按 id 字典序稳定化，规则列表保留上述语义顺序。`config_remove` 在本层覆盖后执行；删除不存在字段或同层既设置又删除同一路径（含父子重叠）均报错；对象键序不参与语义，序列化按固定键序。
- 本机覆盖只接受登记字段/完整技能包，不同步；桥接 `mcp-servers.local.json` 保留其原生成器“按名称整项覆盖”语义，不擅自改成递归合并。权限/信任/目的地/隔离校验作用于合并后的有效配置，任何层不能以覆盖语义提升未授权能力。临时层不落盘；持久化到共享层还是本机层必须显式选择。
- 每次 `plan` 输出**合并报告**：生效项、被覆盖项、被禁用项（呼应 [7.2](#72-插件注册表与适配器) 的编译报告）。

### 19.9 指标日志

**追加写的事件流**（每行一条 JSON，JSONL）：

```jsonl
{"at":"2026-10-12T14:30:31+08:00","kind":"token","session":"s-20261012-1430-a1b2","project":"shop","tool":"claude-code","in":1820,"out":640}
{"at":"2026-10-12T14:31:02+08:00","kind":"tool_call","session":"s-20261012-1430-a1b2","name":"memory_recall","mcp":"cgh"}
{"at":"2026-10-12T15:10:00+08:00","kind":"apply","project":"shop","ok":true,"degraded":1,"unsupported":0}
```

| 字段 | 出现于 | 说明 |
| --- | --- | --- |
| `at` | 全部 | ISO8601，带时区 |
| `kind` | 全部 | `token` / `tool_call` / `apply` |
| `session` | `token` / `tool_call` | 会话 id，供 [10.12](#1012-ai-对话) 的会话统计**按需查询** |
| `project` | 全部 | 归属项目 id |
| `copy` / `scope` | 多副本会话及应用 | 副本/配置作用域 id；跨副本诊断和审计同样保留这些维度，不把逻辑项目相同视为同一会话 |
| `tool` | `token` | 用量的**来源**：控制台对话记**模型提供者**；被动扫描记 **AI 工具名** |
| `in` / `out` | `token` | 输入 / 输出 token 数 → 支撑「Token 消耗趋势」 |
| `name` / `mcp` | `tool_call` | 工具名与其来源 MCP；**由记忆 MCP 主动上报**，只覆盖上报的调用 → 支撑「记忆调用次数」 |
| `ok` / `degraded` / `unsupported` | `apply` | 本次编译结果 → 支撑「编译成功率」；与**编译报告归档**成对（见 [10.14](#1014-指标)） |

- **聚合不落盘**：趋势由控制台按需现算（见 [10.14](#1014-指标)）。
- 可关闭、可重建；文件过大时按时间滚动（**滚动策略属实现细节，本文档不规定**）。

### 19.10 时间线快照元数据

时间线基于 `apply` 前的 Git 快照（见 [7.7](#77-同步引擎)），每个快照附带元数据：

```yaml
# <Local Root>/snapshots/<snapshot-id>.yaml
id: snap-20261012-1530
at: 2026-10-12T15:30:12+08:00
trigger: aidock apply --all    # 触发命令
project: 01a12f70-4688-73a1-b4ee-14043eb3b3dd
copies: <per-copy-manifest-ref> # 跨副本批次才有：成员 id、源/草稿/生成物/基线恢复清单
commit: 9f3c1ab                  # 对应的 Git commit
kind: before-apply               # before-apply | applied | before-rollback | rollback
schema_version: 1
source_digest: sha256:<digest>   # 完整规范源清单摘要，不只保存 summary
applied_source: <snapshot-ref>   # 上次成功配置（包含有效技能正文，不能只引用当前全局库）
saved_draft: <snapshot-ref>      # 已保存但尚未应用的配置，供撤销回退恢复
plugin_locks: <manifest-ref>     # 精确版本、来源、产物摘要、平台/运行时
adapter_versions: <manifest-ref>
target_backups: <local-ref>      # 实际目标路径、原/新哈希、所有权、原始字节备份；不随行
transaction: <transaction-id>

  added: 2
  changed: 5
  removed: 1
  degraded: 1
```

- 摘要**在快照生成时一次写定**，时间线直接读，**不去解析 diff**（避免回放时再算一遍）。
- 回放语义见 [10.15](#1015-时间线)。
- 快照正文与引用清单必须完整、哈希可验证；只有元数据的节点不可恢复。回退需显示恢复能力/缺失依赖，不能让“查看快照”按钮掩盖正文缺失。

### 19.11 副本组、绑定与共同基线

```yaml
# Config Root/replica-groups/<group-id>.yaml —— 共享策略，无机器绝对路径
schema_version: 1
id: <stable-group-uuid>
name: Dragon 开发工作区
scopes:
  server:
    project: <server-project-uuid>
    relative_root: dragonsvr
    ownership: external-source      # aidock | external-source
    skills: [skills/]
    mcp_source: .ai-config/mcp-servers.json
    local_excludes: [.ai-config/mcp-servers.local.json]
    generator: <locked-generator-adapter-id>
  client:
    project: <client-project-uuid>
    relative_root: dragoncli/trunk/client
    ownership: external-source
    skills: [skills/, .claude/skills/]
    mcp_source: .ai-config/mcp-servers.json
    local_excludes: [.ai-config/mcp-servers.local.json]
    generator: <locked-client-generator-adapter-id>
# workspace 作用域独立登记；环境历史默认不在共享 skills 白名单
```

本机 `<Local Root>/replicas.yaml` 保存 `copy_id → group_id、实际工作区路径、各 scope 实际根目录、Git/SVN 身份、本机覆盖、工具版本和启用状态`。copy id 初始化一次，移动目录保留；复制该文件不能冒充另一个注册副本。绑定不进入跨机同步，junction/符号链接须解析最终路径后验证白名单、去重和锁定。

共同基线存于 Local Root，键为 `(group_id, scope_id, 两个 copy_id, entry_id)`；包含双方最后确认的共享正文/结构、SHA-256、删除状态与批次 id，不仅存一个时间戳或当前路径引用。基线不同/丢失重新进入首次协调，不自动认为某端没改。目标本地覆盖有独立策略与摘要；原始字节用于恢复，规范化结构用于字段 diff，不能把换行差异当成授权覆盖手写区的理由。

计划包含 `id、kind、scope、from、selected_copies、entries、resolutions、source/target/dependency/baseline_digests、resolved_paths、generator/adapter_locks、policy_digest、backup_manifest、probe_scope`。计划没有凭据值；确认后以摘要重新检查，不能复用其它 copy/作用域的计划。批次快照扩展 §19.10，包含每 copy 的源/草稿/生成目标/基线恢复清单；保留该清单才能完整回退批次。

诊断记录包含 `copy、scope、tool/version、layer、status、reason_code、source/target_digest、cwd、checked_at、session_id、evidence_ref、suggested_action`。状态用 `PASS / FAIL / WARN / SKIP / UNKNOWN / STALE`；没有工具侧证据时使用 UNKNOWN，预期未启用或未启动编辑器使用 SKIP 并给出理由。配置/版本/会话变化使关联证据过期，不沿用旧的 PASS。

### 19.12 解析、计划与 CLI 结果契约

- AIDock 自有结构化配置按类型标 `schema_version`：本版 Profile 为 2，其余既有配置和新增 skills.yaml 为 1。SKILL.md 的原生 frontmatter 不强加工具不支持的字段，由所属规范清单记录技能包格式/摘要。未标版本的外部原生文件只走对应桥接解析，不能猜成自有格式。
- 自有配置拒绝未知字段、重复键、循环引用、非法 YAML 标签/非安全对象构造和未解析变量；插件自定义配置仅在声明的 config_schema 内校验。外部非托管字段保留原字节/结构，不能因“不认识”删掉。库与机器 Schema 落地后必须用文档示例做解析/序列化 golden 验收。
- 安装/启动/生成器命令使用 `{command,args,cwd,env_refs}` 等结构参数，不把 manifest 文本拼为 shell；路径变量只在声明字段展开。共享 env/命令参数只接受允许同步的字段及引用，未知敏感字面量留在本机并阻断待同步条目；不能只靠密钥关键字正则承诺无泄漏。
- 普通写操作都需要明确 project/scope/copy 与计划。默认由实际 cwd 唯一定位；歧义阻断，跨副本需显式集合。计划记录 base、源/目标/依赖、兼容版本、生成器/策略、决策与恢复清单摘要；计划引用锁定正文而非重新读取当前路径，“确认旧 plan”不能成为批准新内容。
- 计划还固定 `kind: skill-source | native-config | replica`；对应 skill apply / 顶层 apply / replica apply 只接受本类计划，传错返回 `PLAN_KIND_MISMATCH`（退出码 2），零正式写入。预留功能返回 `FEATURE_NOT_IMPLEMENTED`（退出码 4），不得用成功空结果伪装已实现。
- 工具规范 id 首期为 `claude-code` / `codex-cli`；外部别名由适配器显式映射，不能用品牌名把 CLI/App 视为同一加载环境。普通 `--all` 不扩大 project/scope/copy；多副本操作始终使用显式目标集合。
- 普通命令 `--json` 的 stdout 为一个结果对象：`schema_version、ok、code、operation、project/scope/copies、plan/transaction、summary、items、recovery、warnings`，诊断/进度写 stderr。`mcp exec` / 管理网关 stdio 输出协议帧，不能混入此结果或日志。

| 退出码 | 含义 | 对应情况 |
| --- | --- | --- |
| 0 | 本次请求成功 | 无 diff 也是成功；预期跳过/可忽略警告在 items 明示，不宣称未检查层已通过 |
| 2 | 输入/Schema 无效 | 参数、未解析变量、重复/未知字段或无效配置 |
| 3 | 待协调或证据不足 | CONFLICT / BASELINE_UNKNOWN / PLAN_STALE / BASE_STALE；doctor 请求层为 UNKNOWN/STALE |
| 4 | 授权/支持能力不足 | AUTHORIZATION_REQUIRED / ISOLATION_UNAVAILABLE / UNSUPPORTED_TRANSPORT / STORAGE_UNSUPPORTED |
| 5 | 检查/执行失败，未留下待恢复写入 | 请求检查 FAIL，或操作失败且无正式写入/已完整恢复 |
| 6 | 未完成安全恢复 | RECOVERY_CONFLICT 或恢复依赖/字节缺失；必须带事务 id 与恢复指引 |

批量结果可同时包含多种原因；优先级为待恢复 6 → 执行失败 5 → 授权/支持 4 → 待协调 3 → 输入无效 2，逐项 code 不丢失。`ok` 仅指本次请求完成，L1 成功不能变为整环境健康。

## 20. 运维与可靠性

> 前面各章定义了"功能是什么"，本章定义"出问题怎么办"。这些不是锦上添花，而是决定产品能否长期使用的基础。

### 20.1 错误处理与恢复

| 场景 | 行为 |
| --- | --- |
| 适配器编译失败 | **不破坏已生效配置**：先写临时文件、校验通过后原子替换；失败时保留上一版可用配置并报告原因 |
| 插件安装中途失败 | **事务化安装**：依赖、文件、配置全部成功才提交，否则整体回滚；重试时重走安全门 |
| 同步冲突 | 以 Git 冲突为准，**不自动合并**；`plan` 展示差异，交由用户选择保留哪侧（UI 见下） |
| 变量 / 密钥解析失败 | **阻断 `apply`**，不静默降级（见 [19.1](#191-跨平台路径变量)） |

**原生配置写入事务（v1 必需）**：单文件原子替换不能保证多个工具、规则与 MCP 文件一起原子可见。AIDock 保证可检测、可恢复的事务，不宣称其它工具看不到中间状态；应用期间暂停启动新的托管会话，结束后报告各目标结果。

1. `plan` 解析并校验全部目标，展示所有权/漂移冲突；生成 plan id，绑定规范源、知识策略、插件锁、适配器版本、授权摘要、实际目标路径及读入字节哈希。未拥有字段保持原样，预览确认只适用于此计划。
2. `apply` 按 §20.3 取得项目与全部目标锁，再重验源/目标/授权摘要。任一变化返回 `PLAN_STALE`，重新预览；不能把过期确认应用到新内容。
3. 全部目标先编译、解析校验、落临时产物并保存原始字节备份与所有权清单。任一失败不改任何正式目标。Local Root 写恢复日志（事务 id、目标、原/新摘要、备份路径、阶段），持久化成功后才进入提交。
4. 对每个目标写前再验摘要并执行平台支持的原子替换/刷新；记录每个目标结果。外部工具不遵守 AIDock 锁时仍需操作系统排他访问；不支持排他访问的目标明确报告竞态限制，不能宣称绝对无覆盖风险。
5. 中途失败进入恢复：原/新内容与事务记录比对后回滚已替换目标；若被外部再次编辑，保留当前文件与备份并报 `RECOVERY_CONFLICT`，等待人工处理，绝不直接覆写第三方的新内容。下一次写操作前先检测未完成事务，恢复完成后才允许新 apply。
6. 全目标成功才提交已应用摘要、快照、编译报告与审计；失败/未恢复不得显示“已应用”。无源变化再次 apply 为幂等空差异。应用与 Git 提交/推送互相独立，知识正文修改也不虚增能力配置待应用数量。

事务提交标记在目标结果与必需元数据（已应用摘要、共同基线、所有权及恢复清单）持久化后才写定；快照/基线不是独立提前提交。重启时无提交标记的批次按日志检查并恢复，已提交批次核对完整性，不能靠“目标文件看起来是新版本”猜成功。API/CLI 取消或控制台关闭在提交阶段必须完成恢复再退出；强制终止留日志由下次启动恢复。

**冲突解决 UI**

`pull` 时本地与远端都改过同一文件，即为冲突。控制台提供可视化解决：

- **左右并排**：左"保留本地"、右"保留远端"，逐块高亮差异。
- **逐条选择**：可对**每个冲突块单独选边**，不是整个文件一刀切。
- **手动编辑**：允许直接改合并结果。
- **提交前预览**：确认后先展示"将写入的最终内容"，再执行。
- **CLI 等价**：等价于 `aidock diff` 查看 + 用户手工解决后 `aidock apply`，**不引入自动合并**。
- **v1 降级路径**：若暂不实现可视化，则**明确提示"存在冲突，请用 Git 工具手工解决"**并**阻塞 pull 的自动应用**——**绝不允许默默选一边**。

### 20.2 升级与分发

AIDock 有**三层需要独立升级，三者版本解耦**：

| 层 | 升级内容 | 机制 |
| --- | --- | --- |
| 应用本体（core） | 引擎 / CLI / 控制台前端 | 内置 updater：验签 → 下载 → 原子替换单二进制 |
| 适配器 | 各 AI 工具的适配器 | 独立版本单元（见 [7.2](#72-插件注册表与适配器)），可单独更新，**不要求升 core** |
| 插件 / 依赖 | 插件本体与其依赖 | 走 [7.7](#77-同步引擎) 快照回滚 + [9.1](#91-插件安装必须先审计后运行) 安全门 |

**签名与安全**

- core 与适配器的更新包**必须签名**，应用内置公钥验签，验签失败即拒绝安装——这是"严格版安全门"。
- 与插件同一原则：来源可信 + 版本锁定，不使用 `latest` 之类浮动引用。

**触发方式**

- 默认由 `aidock update` / 控制台手动检查；自动检查需用户开启并受缓存频率控制。只读诊断不因启动而下载、升级或迁移数据；控制台不常驻，不做后台静默下载。
- 通道可选：`stable` / `beta`。

**与数据 schema 的关系**

- 所有 schema 文件带 `schema_version`，启动时校验。
- 升级执行**单向迁移**，迁移前自动快照；迁移失败回退到快照。
- **降级注意**：新版迁移过的数据旧版可能读不了，因此回退 core **必须从备份恢复**，不能就地降级；保留上一版二进制以便回退。
- 遵守 §18.4 / §19 的基线变更契约：记录原因、兼容性与迁移，不让旧程序直接读取不兼容数据。

**兼容矩阵**

- 声明 core ↔ 适配器 ↔ schema 的兼容范围。
- 启动时校验：适配器要求 `core ≥ X`、schema 落在支持窗口内，否则**拒绝启动并提示**，不静默降级。

**原子性与审计**

- 更新写入采用"临时文件 + 原子替换"（同 [20.1](#201-错误处理与恢复)），中断不留半成品。
- 升级动作写入审计日志（见 [9.5](#95-审计日志)）。

### 20.3 并发与锁

| 场景 | 策略 |
| --- | --- |
| 单机多实例 | 数据根加锁（lock file），避免两个实例同时写同一 Config Root |
| 多项目并行 | 项目锁 + 实际目标文件锁；独立目标可并行，共享用户级工具配置必须互斥 |
| 多 AI 工具 | 全部编译/验证完成后才提交；目标按规范化绝对路径（解析别名与 Windows 大小写）稳定排序取锁，逆序释放，防止交错和死锁 |
| 云盘目录（档位②） | 单文件原子替换不足以保证多文件一致；读取按版本清单核对全部哈希/依赖，缺失/混代/冲突副本阻断 apply。写入者 id 与版本清单在内容完成后发布，不按 mtime 选边；跨机同步不提供 OS 全局锁 |

### 20.4 测试策略

| 对象 | 策略 |
| --- | --- |
| 适配器 | **快照测试**：规范配置 → 期望原生配置的 golden 文件比对；漂移检测做回归 |
| 合并算法 | **表驱动用例**：给定层级组合 → 期望生效集；断言确定性（同输入必同输出） |
| 安全门 | 用已知恶意样本做**负向用例**，确保被拒 |
| 进程隔离 | 越界用例（越目录 / 越网络）必须被拒 |
| 会话中继 | 伪造其它 project/scope、未授权写工具、未知处理目的地拒绝；UI 退出后代理仍可用，客户端 EOF 后子进程/broker 均退出 |
| 配置事务 | 保留已有 JSON/TOML 字段和 Markdown 手写区；共享目标并发、预览后源/目标变化、第二目标失败、替换后未记日志即崩溃、恢复期间外部修改均有可核对结果 |
| 迁移 | 内置与外置项目的知识正文 id/数量/SHA-256 一致，索引重建，凭据/日志/会话不随行 |
| 多副本 | 五 copy × 三作用域；任意源发布、未知基线、双方修改、目标单边修改、删除确认、附件遗漏、本机覆盖与路径映射、镜像手改、旧分支不兼容、第二副本失败及崩溃恢复；回退后再传播不能丢变更 |
| 生效诊断 | 不把文件存在、镜像数相同或 stdio 进程存活判为已生效；旧会话/错误 cwd/未信任项目/客户端开关关闭/未知版本给出对应层级与理由 |

### 20.5 性能目标与基准

给出可验收上限（示例值，需实测校准）：

- 冷启动到项目列表可交互：**< 2s**
- 单次 `apply`（≤ 20 插件、≤ 3 工具）：**< 3s**
- 首次全量索引 10 万行：目标 **< 2min**，超时给出进度且可中断（**属记忆 MCP 的实现指标**）
- 检索 P95：BM25 **< 100ms**；向量（含嵌入）**< 500ms**（同上，属记忆 MCP）

> core 自身不承诺上述索引 / 检索指标，只负责把后台任务与 UI 解耦、提供进度展示与取消（呼应 [12 章](#12-性能智库的索引策略)）。

### 20.6 备份与恢复

| 对象 | 策略 |
| --- | --- |
| Config Root | Git/显式 export 保存 Knowledge + Capability；工作区内外置项目/桥接源须在清单覆盖，不能只备份全局配置就称完整 |
| Local Root 的缓存/索引/指标 | 可重建或按策略清理；不是恢复点 |
| Local Root 的注册、本机覆盖、基线/tombstone、事务、快照及引用产物 | 受保护恢复数据；按 §10.15 / §13.3 保留/备份。缺失即丢失对应恢复/协调能力，不能“重扫目录”无损重建 |
| Local Root 的审计 | 按 §9.5 封存/显式归档；不能重建历史或随缓存清空 |
| 记忆 MCP 的索引与数据库 | 由该 MCP **自行管理并可重建**；core 不持有、也不备份 |
| 密钥库 | **不备份**（依赖 OS 凭据库）；换机重新授权 |
| 损坏恢复 | 控制台提供"重建索引"入口，用于**记忆 MCP** 的 SQLite / 向量索引损坏时恢复 |

`project rm` / `replica rm` 只解除注册，不删除工作区、外部源或恢复资产；未完成事务/仍被快照引用的绑定不能直接移除。删除传播的 tombstone 在相关成员确认或显式移除该成员之前保留，防止旧副本重入后复活已删除条目。普通跨机导出不包含原生字节备份（可能含手填密钥）；本机恢复包需独立保护 ACL/加密、校验清单与可恢复性。OS 凭据缺失只能重新录入，不能从普通快照“恢复”。

### 20.7 AI 工具更新检测

- 每个适配器声明**已验证的工具版本范围**（呼应 [7.2](#72-插件注册表与适配器) 的能力矩阵）。
- 检测到工具版本**超出范围**时，提示"适配器可能未适配该版本"，并**阻止静默写入**。
- 原生配置被工具或用户手改时，识别为**漂移**（见 [8.3](#83-插件目录结构与生成物原则)）。

### 20.8 自检（`aidock doctor`）

一键回答"我的环境还健康吗"。默认静态读取，不写配置、不启动服务；`--scope` / `--copy` 限定诊断对象，全部副本须显式选择。以下探测项在显式 `--probe` 时执行：

| 检查项 | 内容 | 不通过时 |
| --- | --- | --- |
| 数据根 | 路径、权限静态检查及根不重叠；实际可写性在写操作的暂存/事务预检验证 | 列出失效/重叠/能力缺口，不以静态 ACL 判断保证可写 |
| 密钥库 | OS 凭据库可用、已声明的凭据是否都存在 | 列出缺失项，引导补录 |
| 隔离可用性 | 当前平台支持到哪一档隔离（如 Windows 受限令牌是否可用） | 说明会降级到哪一级 |
| 记忆 MCP 健康 | `--probe` 下已绑定的记忆 MCP 能否启动、能否响应探测；默认为未探测 | 分别标注失败/未验证，**不影响其它功能** |
| 索引 / 缓存 | 可重建项是否损坏 | 提示"重建"（见 [20.6](#206-备份与恢复)） |

- 输出**人类可读摘要**；`--json` 供脚本消费。
- **不自动修复**：doctor 只诊断，修复动作交用户逐项确认。
- 有待恢复事务/不兼容 schema 时只读展示事务与恢复指引，不在 doctor 中恢复/升级；进入有授权的写操作前才完成相应恢复/迁移。

**配置合理性与生效是不同的结论**。每个 copy × scope × 工具输出以下层级，不能只用一个绿色“正常”：

| 层级 | 证据与检查 | 可以报告什么 |
| --- | --- | --- |
| L1 源与生成 | 解析/frontmatter/字段类型；来源优先级和覆盖链；技能包引用闭合；生成器 `--check` / 暂存输出比对；本机变量/cwd/命令依赖/权限合理性 | 源有效、生成一致；尚不证明工具读取 |
| L2 工具发现 | 已安装工具/适配器支持版本；项目信任状态；原生发现目录、父目录规则和 CLI/App 差异；工具自己的配置/技能/MCP 列表（能力可用时） | 该版本工具可识别；列表不可得则 UNKNOWN |
| L3 会话加载 | 新建、显式指定 cwd 的临时验证会话；工具侧加载清单/日志与本次源摘要匹配。区分自动发现、路由手动读取、明确禁用 | 当前验证会话已加载；不推断其它已有会话 |
| L4 实际能力 | `--probe` 通过 MCP initialize + tools/list，再调用已授权无业务写入探针；技能用工具侧加载证据及无副作用任务记录验证引用，不能只看 AI 自述 | 指定探针在该会话成功；不保证所有技能未来都会被模型选择 |

`--probe` 显示要启动的工具/进程、网络目的地、凭据引用、超时与费用边界；复用已有明确授权。没有安全探针、工具无可验证加载接口、编辑器未启动或未提供模型授权时报告 SKIP/UNKNOWN，不自动开 UE、不装包、不修改全局工具配置、不调用业务写入来“测试”。握手/列表不等于实际调用成功。

优先诊断此次用例容易出现的问题：启动在 `dragoncli` 却未进入 `dragoncli/trunk/client`；父/子目录同名 MCP 冲突；`mcp-servers.local.json` 覆盖共享项；Kiro 命名 agent 未内联 MCP 或工具不在白名单；Trae 项目 MCP 开关关闭；Codex 发现目录是否适用于当前版本；编辑器依赖不可用；配置更新后旧会话仍用旧快照。这些是检查规则，尚未构成五个工作区的现存故障结论。

每项显示位置、原因、影响、建议修复、证据时间和层级。修复入口先生成 plan/diff、备份，再执行 §20.1 / §7.12 的事务；检查命令本身不带 `--write`。重新生成后 L1 可更新，L3/L4 标成待新会话验证，不能自动继承旧结果。

## 21. 总结与愿景

AIDock（智坞）的目标是成为 AI 开发环境的 CurseForge + 魔兽世界插件管理器 + 个人代码智库。

打开界面，看到所有可用的 MCP、Skills、Plugins；勾选想要的，点击启用，配置自动同步到所有 AI 工具；换个 Profile，场景瞬间切换；换台电脑，一条命令恢复一切；参考过的代码和设计经验自动沉淀到你的记忆 MCP，任何 AI 工具都能通过 MCP 调用。

在此基础上，用"安全门 + 分级隔离 + 数据分级"守住底线，用"钉死不变量、开放可替换层"保证架构不被玩坏，用"安装弹窗 + 批量更新 + 首次引导"把体验做顺，用"信任信号 + Profile 市场 + 标准兼容"把生态做大。

### 产品设计宪法

> **项目是容器，个人是圆心，AI 工具是出口，智库是沉淀。**

展开为四层承诺：

- **个人层积累一切**，换电脑带走一切。
- **项目层隔离配置**，每个项目有自己的技能、MCP、记忆、规则。
- **AI 工具层输出一切**，同一套配置编译到所有 AI 工具。
- **智库跨项目沉淀**，按项目隔离检索。

> **停靠工具，带走记忆；一键切换，随处开工。**
