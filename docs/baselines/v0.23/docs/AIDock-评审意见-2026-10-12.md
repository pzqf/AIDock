# AIDock 设计与 Demo 评审

日期：2026-10-12。基线：`main`，提交 `118670e`，设计文档 v0.20。

结论：以项目为边界、统一规范配置、通过适配器输出到 AI 工具，这条主线可以继续。现在最需要补齐的是安全策略的实际执行位置、配置写入的所有权，以及原型中的项目状态隔离。建议先完成一个可信的「修改项目能力 → 预览差异 → 应用 → 工具侧验证」闭环。

本次证据包含文档审查、Demo 源码审查和 9 项隔离脚本验证。Demo 的完整内联脚本通过 JavaScript 语法编译；隔离验证使用原文件中的状态与函数，DOM、计时器及渲染函数按需替身处理，不连接模型、MCP 或外部网络。

**尚未完成页面视觉与浏览器实操验证**：浏览器工具拒绝 `file://` 协议；用户随后明确授权访问，但工具协议限制仍然存在。以下原型问题是源码及隔离验证结果，不是浏览器端到端结果；设计风险也不是对尚未实现的后端作漏洞认定。

优先级：P0 表示正式实现前应确定的安全契约；P1 表示核心行为或配置可靠性问题；P2 表示后续一致性与体验修正。

## 一、正式实现前需要补齐的设计

### D1 · P0：目录和网络白名单缺少强制执行机制

证据：[设计 §9.2](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1021)、[技术选型](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1723)。

当前方案提出环境变量白名单、受限工作目录、本地网络代理和 Job Object。设置工作目录不会限制进程读取其他绝对路径；环境变量白名单不会阻止读取 SSH 密钥文件；配置 HTTP 代理也不会阻止第三方程序直接建立套接字。Job Object 主要负责资源、子进程和生命周期约束，不能单独完成目录、网络隔离。

因此，若按 §9.2 的描述直接实现，插件的权限清单可能只是声明，不能保证越界访问被拒绝。§13.1 虽提到受限令牌和 namespace，仍缺少它们与文件、网络策略的具体对应关系。

建议补一个平台能力矩阵：每个平台如何强制限制文件读取、写入、网络及子进程，平台缺失能力时如何处理。隔离可用性不足时，应阻止运行要求该能力的插件，或让用户明确选择非隔离模式并持续显示实际状态。验收应包含插件直接读越界绝对路径、符号链接或 junction 越界，以及绕过代理直连网络的负向用例。

### D2 · P0：MCP 启动、授权、审计与代理生命周期没有闭合

证据：[记忆工具直接提供](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:665)、[代理生命周期](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1034)、[core 不在调用链上](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1516)。

文档明确：记忆工具由外部 MCP 提供，AI 客户端直接拉起 MCP，core 不在调用链路上。同时，core 又承诺写操作必须授权、写审计、按项目隔离和按需注入凭据。仅把这些要求写进配置，不能强制第三方 MCP 执行；也不能让客户端自由传入另一个项目 id 后就获得该项目的记忆。

生命周期还有一个具体矛盾：网络代理随 core 命令结束退出，但文档让需要联网的 MCP 提示先执行 `aidock apply`。`apply` 完成后代理也会退出，所以之后启动的联网 MCP 仍不能使用。控制台里的调试实例与客户端拉起的实例，也需要分别标识，避免「已停止」被误解为客户端实例已经停止。

建议定义统一运行入口，例如原生配置指向 `aidock mcp exec --project <id> --plugin <id>`，由这个会话进程执行隔离、凭据注入、调用授权与审计，并持有与子进程同寿命的网络代理。项目身份由启动上下文绑定；需要权限检查的调用必须经过明确的执行点。记忆 MCP 仍负责检索和存储，core 无须实现记忆引擎。Demo 文件样例已有 `aidock-proxy` 名称，但文档还没有对应的启动、协议和策略契约。

### D3 · P0：Internal 的策略需要按模型处理位置判断

证据：[数据分级](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1053)、[控制台使用模型提供者](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1466)。

「仅本地 AI 客户端可见」不等于「数据只在本机处理」。本地运行的客户端可能把 MCP 返回内容放进远程模型的请求中。控制台自身也计划接用户配置的模型 endpoint；数据是否外发取决于该 endpoint 和后续请求，而不是界面或客户端所在的位置。

建议把客户端位置、模型处理位置和数据等级分别描述。向远程模型发送上下文前，按实际目的地执行策略与必要授权；Internal 默认不自动进入远程模型上下文。权限必须同时覆盖正文、文件片段、记忆工具输出和引用展开内容。

### D4 · P1：原生配置需要字段所有权、共享文件锁和跨文件恢复

证据：[生成物原则](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:948)、[原子替换](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:2170)、[并发与锁](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:2229)。

文档只对 `CLAUDE.md` / `AGENTS.md` 明确保留手写区域。但用户已有的 JSON/TOML 工具配置也可能包含自配 MCP、模型设置和第三方扩展。如果把整份原生配置作为生成物覆盖，第一次接入就可能丢失这些内容。

另外，「临时文件 + 原子替换」只保证单个文件的替换。工具 A 写入成功、工具 B 写入失败，或同一工具的规则文件与 MCP 配置只写了一半，仍会形成不一致状态。两个项目可能同时改同一个用户级工具配置，只有项目锁也不足以保护该共享目标。

建议定义 AIDock 托管的 JSON/TOML 字段、规则区块和文件集合，默认保留不属于 AIDock 的内容。同名冲突先展示并让用户选择。锁至少覆盖实际目标文件，采用稳定顺序获取；先完成所有目标的编译、校验与备份，再执行写入，记录事务状态。失败时明确整体恢复或逐目标结果，崩溃后能够继续恢复。预览确认还应绑定源和目标的版本/哈希，避免确认后配置变化却应用另一份内容。

### D5 · P1：v0.20 的知识同步承诺尚未同步到开发计划

证据：[Knowledge + Capability](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:131)、[同步引擎](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:688)、[实施路径旧口径](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1817)、[开发计划阶段 4](D:/GitHub/MyAIDock/docs/AIDock-开发计划.md:146)。

v0.20 明确同步记忆正文与能力配置，但设计 §7.9 的命令注释、§14 第四阶段和开发计划阶段 4 仍写「只同步 Capability」。开发计划开头也仍指向 v0.19。按旧口径实现，最不可再生的知识正文可能不在迁移包里。

建议统一所有迁移条目的口径，并把验收写成可比对的清单：知识正文 id、条目数和内容哈希一致；索引可重建；凭据、日志、会话不随行。还需明确外置项目配置如何打包及在新机重新绑定路径，不能只覆盖 `.aidock/` 随项目 Git 迁移的路径。

其他需要统一的文档契约：

- §7.10 把双向回写列为可选后续，但 §10.9、§19.2 和 Demo 把它展示成当前可选模式。
- §18 把审计、进程隔离、托管区块列为进阶，而开发计划阶段 1 已要求它们作为底座；应统一首期必需范围。
- `plugin.yaml` 和 `mcp.yaml` 示例使用未固定版本的 `npx -y ...`，与 §9.1 的固定版本及哈希要求不一致；需定义安装锁定产物，运行期避免重新解析浮动包。
- §19.6 尚未规定同层同名项同时 enable/disable 时的行为，以及 `config_overrides` 深层字段、数组、删除项的合并规则；`rules` 用纯字符串，却写「替换同名规则」，缺少规则 id。

### D6 · P2：审计应区分「防止修改」与「能检测修改」

证据：[审计存储](D:/GitHub/MyAIDock/docs/AIDock-设计文档.md:1097)。

本地追加文件加哈希链，不能单独保证绝对不可篡改。能修改整个文件的主体也可能重算整条链、删除尾部或替换日志。哈希链需要可信的链头/链尾或外部锚点，才能检测这些变化。滚动留存与 §13.3 的「不可清理」也需要定义明确的归档边界。

建议声明威胁模型：core API 不提供修改历史记录的接口；受隔离插件不能写审计目录；哈希链用于完整性检查；需要更强保证时，对封存段签名并保留可信锚点。界面文案按实际保证描述。

## 二、Demo 的核心行为问题

### R1 · P1：项目技能和 Profile 共用可变全局状态

证据：[项目与技能数据](D:/GitHub/MyAIDock/demo/index.html:1552)、[技能开关](D:/GitHub/MyAIDock/demo/index.html:1981)、[Profile 切换](D:/GitHub/MyAIDock/demo/index.html:3062)。

隔离验证：在 `shop` 禁用 `code-rev` 后，`admin` 引用的同一技能也变成 `on: false`，但 `admin.pending` 仍为 0。商城切到「前端项目」后，Go 网关读到的 `state.profile` 也变成「前端项目」，而该项目没有独立的 Profile 字段。切换 Profile 还没有实际更新对应能力组合。

建议分开不可变的技能定义库、全局默认和每个项目的启用/禁用覆盖。有效状态通过项目配置计算；项目 Profile 与会话临时 Profile 分别存储。修改共享定义时才提示所有受影响项目，项目开关则只影响当前项目。

### R2 · P1：会话和 `@` 引用没有按项目隔离

证据：[会话列表](D:/GitHub/MyAIDock/demo/index.html:2281)、[新建会话](D:/GitHub/MyAIDock/demo/index.html:2404)、[`@` 候选](D:/GitHub/MyAIDock/demo/index.html:2451)。

新建会话没有 `project` 字段，列表只按标题过滤。`@` 记忆候选直接搜索全局数组，没有项目及敏感度过滤。隔离验证在 `gw` 搜索「支付」时，得到商城的 Confidential 条目「支付回调鉴权」。这是候选名称暴露的证据，尚不能据此声称正文已经发送给模型。

建议会话、草稿、文件树和引用候选绑定稳定项目 id。共享引用查询函数统一执行当前项目、跨项目公共知识以及数据等级策略；候选列表和最终引用展开使用同一策略。项目 id 应长期稳定，不宜依赖新机目录名冲突时生成的不同后缀。

### R3 · P1：待应用计数与变更预览脱节

证据：[标记变更](D:/GitHub/MyAIDock/demo/index.html:1930)、[预览与应用](D:/GitHub/MyAIDock/demo/index.html:1935)。

隔离验证：先执行 `doApply()`，再切换一个技能开关，得到 `pending: 1`、`changes: []`，预览内容为「无变更」。`markDirty()` 只累计次数，没有更新差异列表。开关改回原值也继续累计，无法反映净变更。`doApply()` 还直接把 Git 状态设为 clean，而配置应用并不等价于提交或推送。

建议维护上次已应用配置快照，计数和 diff 从当前规范源与该快照比较得到。把「草稿已修改」「待应用」「已编译」「目标已生效」「待提交/同步」分开，应用成功只更新对应状态。Demo 即使没有后端，也应完整模拟这些状态之间的关系。

### R4 · P1：保存记忆忽略敏感度选择

证据：[敏感度下拉](D:/GitHub/MyAIDock/demo/index.html:1426)、[保存函数](D:/GitHub/MyAIDock/demo/index.html:3035)。

弹窗提供四种敏感度，但 `saveMemory()` 没有读取选择值，固定写入 `level: 'public'`，也没有保存来源 MCP。隔离验证确认新记录始终为 Public。

建议给选择器明确 id，保存用户所选等级；默认选 Internal。路由到当前绑定的记忆 MCP，并在原型中区分「待确认」与「正式入库」。不要让选择了 Confidential 或 Restricted 的用户得到 Public 记录。

### R5 · P1：安全门选项没有驱动安装行为

证据：[设置门槛](D:/GitHub/MyAIDock/demo/index.html:1235)、[固定门槛](D:/GitHub/MyAIDock/demo/index.html:1764)、[安装函数](D:/GitHub/MyAIDock/demo/index.html:2818)、[项目内引入 MCP](D:/GitHub/MyAIDock/demo/index.html:3083)。

设置中的最低信任等级只弹提示，实际判断始终使用固定 `TRUST_MIN = 2`。低信任插件虽然显示「需二次确认」，确认按钮仍走同一个直接置 `on = true` 的处理器；隔离验证未触发额外确认，也没有新增审计。缺失信任数据时，安装函数默认给予 L2，容易把未知显示成已过门槛。项目内添加 MCP 的弹窗也没有文档要求的来源与权限信息。

建议原型使用同一策略状态来驱动设置、详情、安装与项目内引入。未知数据显示未验证；低于门槛的显式放行要能演示授权记录。区分「已下载/安装」「已绑定项目」「已启用」「实例运行中」，目前 `on` 混用了其中多种含义。此处评的是原型流程，真实后端仍须单独实现和验收安全门。

### R6 · P2：文本转义、发送等待态及保存反馈需要修正

证据：[分组事件](D:/GitHub/MyAIDock/demo/index.html:1870)、[HTML 转义](D:/GitHub/MyAIDock/demo/index.html:1768)、[发送函数](D:/GitHub/MyAIDock/demo/index.html:2482)、[技能详情保存按钮](D:/GitHub/MyAIDock/demo/index.html:941)。

- 分组名 `O'Reilly` 会生成 `toggleProjectGroup('O'Reilly')`，隔离验证编译该事件时出现 `missing ) after argument list`。HTML 转义不能代替 JavaScript 字符串转义。建议通过 DOM 属性及 `addEventListener` 绑定事件，减少把用户文本插进内联 JS；这也有利于兑现严格 CSP。
- `sendChat()` 到 400ms 后才标记输出中。等待期间连续发送两次会排入两个回复任务，两个任务随后共享同一份 typing 状态。建议发送时立即进入等待态，并按会话、请求 id 管理取消及过期结果。
- 技能详情「保存」仅显示「已保存」，没有更新技能正文；语言切换也仅更新变量和提示。概念原型可以使用模拟数据，但可编辑、可保存的演示应保持状态一致，并在主要位置注明模拟行为。
